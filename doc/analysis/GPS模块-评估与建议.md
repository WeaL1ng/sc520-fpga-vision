## 0. 结论先行

1. **方向可以，但有一句话必须先说清楚**：**GPS 是"标注器"，不是"探测器"。** "发现可降落地点"的全部技术含量在**图像侧**（平整度/纹理/颜色/坡度），GPS 只是给这个结果**贴一个经纬度标签**。**所以必须先做图像侧的降落点检测，GPS 后加。** 反过来先做 GPS，你会得到一个"能显示坐标但没有降落点可标"的系统。
2. **真正的风险不是 GPS 本身（很便宜），而是面积已经到临界点。** 加上 GPS + 降落点检测后，预估 slices 落在 **75%~80%**——贴着警戒线。必须严格执行砍单顺序。
3. **GPS 有三个不显然的价值**（比"显示坐标"值钱得多）：**① 1PPS 时间基准**（把延迟测量从板内相对升级为绝对时间戳）；**② 地面速度作为"可降落"的门控条件**；**③ 让事件日志变成"地理事件日志"**（带坐标+时间，可画在地图上）——这才是"应用场景"的成品形态。
4. **"发信号"这块有个免费的得分升级**：板上有蜂鸣器和双色 LED。发现降落点 → 蜂鸣 + LED + 上报坐标，**这就从"数据上报"变成"根据视频识别结果实现外部控制"，直接命中扩展要求(3) 的字面意思**。成本 ~50 LUT。
5. **两个必须先解决的坑**：~~**DC3 引脚表**（第三次成为阻断项）~~ → **✅ 已解除**（完整引脚表已到手：`9_.../HX1P35B开发板引脚分配汇总.docx`；GPS 建议接线 = `GPS TXD → U1`（= GPIOA_3，J1 第 4 脚）+ 3.3V/GND 用 J1 第 29/30 脚，见 `doc/analysis/板卡资料解锁-资产清单与计划修订.md` §3.3）+ **室内 GPS 收不到星**（答辩现场坐标会是无效值，必须准备"模拟模式"）——**坑 2 仍然完全有效**。

## 1. 最关键的一点：分工要说清楚

```
【图像侧 = 得分主体】                    【GPS 侧 = 贴标签】
平整度 / 均匀度 / 颜色合规 / 面积        →   经纬度 / 高度 / 时间 / 地速
   ↑ 这是"扩展要求(2) 目标检测与识别"        ↑ 这是"应用场景"叙事
     和"扩展要求(1) 视觉增强"的地盘             不构成任何赛题条目
```

**为什么强调这一点**：赛题二的 14 条要求里，**"GPS"和"降落点"一次都没出现**。
- 图像侧的"可降落区域检测"→ 可以挂 **扩展(2) 目标检测与识别**（官方原话"对简单目标（如几何形状或特定物体）进行识别"）、**扩展(1)**、**高阶(2) 目标跟踪与信息标注**
- GPS 侧 → 只能挂 **扩展(3)**（应用场景）和 **扩展(5)**（自主创意），而且**是叙事的配角**

**行动含义**：把 P5 的演示目标从"橙色色块"升级为"**可降落区域**"——这样 P5、降落点检测、GPS、网络上报**是同一个故事的四段**，而不是四个孤立功能。这是本建议里性价比最高的一步。

## 3. GPS 的三个不显然的价值

### 3.1 1PPS 时间基准（最被低估）

GPS 模块的 **1PPS 是 ±1 µs 级的世界时秒脉冲**。

现在端到端延迟的测量方式是：采集域维护一个 ms 计数器，帧首打戳，显示端相减（实施方案 P3 的 `frame_tag`）。**这是"板内相对时间"，只能回答"多少 ms"，不能跨设备对时。**

用 1PPS 之后：
- 每帧的采集时刻可以映射到**绝对 UTC 时间**
- **PC 端收到的每条遥测都带绝对时间戳** → 可以和 PC 本地时间、和录像、和 GPS 轨迹直接对齐
- 延迟测量可以升级为"**从绝对采集时刻到绝对显示时刻**"，比"板内计数相减"更严谨

**答辩价值**："数据可追溯"从这里开始成立——传感器数据、图像事件、飞行轨迹在同一时间轴上。

**实现成本**：1PPS 引脚 + 一个锁存/对时状态机 ≈ **30 LUT**。极便宜。

### 3.2 地面速度作为门控条件

"可降落"的物理前提之一是**平台处于低速**。GPS 的 RMC/GGA 句子里有地面速度（`$GNRMC` 字段 7）。

用它可以做门控：
```
if (gps.speed > 2.0 m/s) → 不判定降落点（正在飞，不是降落时刻）
if (gps.fix_quality == 0)  → 坐标无效，只报图像结果，不报位置
```
这让"降落点判定"从"只看画面"变成"画面 + 平台状态"，逻辑更严谨，也更容易在答辩时讲清楚。

### 3.3 让事件日志变成"地理事件日志"

检测到的事件 + 坐标 + 绝对时间 → 上传 PC → **可以画在地图上**。

这是"应用场景"的成品形态，也是你医疗无人机项目的直接铺垫：
> "无人机巡山，FPGA 实时识别可疑区域/可降落点，自动打上坐标与时间标签并上报地面站。"

## 4. 实现路径（三档，按成本）

### 4.1 G1 —— 原始 NMEA 透传（**推荐**）

```
GPS 模块 (NEO-6M/7M/8M 或 ATGM336H，9600 baud NMEA-0183)
   │ UART TX → FPGA
   ▼
uart_rx（+120 LUT，可与 PC 下行命令共用）
   ▼
塞进遥测流：新增 type = 0x06 GPS_RAW
   体 = 原始 NMEA 字节（一包 1~3 句，约 200~300 B，1 Hz 或 2 Hz）
   ▼
UART / 以太网 → PC → Python 解析 NMEA（pynmea2 或十几行手写）
```

| 项 | 值 |
|---|---|
| FPGA 成本 | **~150 LUT**（UART RX + 小 FIFO + 复用已有的 `tlm_pack`） |
| 依赖 | **DC3 引脚表** |
| 优点 | 极便宜；协议不用改；NMEA 的所有字段（含卫星数、HDOP、速度、航向）都拿到了；PC 端解析零风险 |
| 缺点 | OSD 上无法显示坐标（除非加 G2） |

### 4.2 G2 —— FPGA 内解析最小子集（可选，为了 OSD 显示坐标）

只需解析 `$GNRMC`（推荐，一个句子同时含定位状态、纬度、经度、地速、日期时间）：
```
ASCII 状态机：找 '$' → 匹配 "GNRMC" → 按 ',' 计数分段
  字段 2: 定位状态 A/V
  字段 3/4: 纬度 ddmm.mmmm + N/S
  字段 5/6: 经度 dddmm.mmmm + E/W
  字段 7: 地速（节）
  末尾 *XX 校验和（异或校验，很便宜）
→ ddmm.mmmm 转成 1e-7 度定点数（×10000/60 的常量乘法 → CSD 移位加法）
→ 输出 lat/lon 给 OSD 与遥测 type=0x06（二进制形式，比 ASCII 省字节）
```
| 项 | 值 |
|---|---|
| FPGA 成本 | **~450~600 LUT** |
| 用途 | OSD 显示 `N 26.0745° E 119.2965° ALT 142m`；遥测改用二进制（省带宽） |
| 判断 | **面积紧的话砍掉，用 G1**。OSD 上不显示坐标不影响答辩（PC 上有） |

**建议：先做 G1。等面积实测下来有余量（比如 P1 之后发现比预期省得多），再加 G2。**

### 4.3 G3 —— 用片上的硬核 MCU 解析（**工具链已确认，只差 1~2 天实际验证**）

```
  I2C_Available    : 0     ← 唯一不可用的外设
  QSPI / AHB / APB : 可用
  MCU_RESET_VECTOR : 0x20E00000
```
且 `MCU.v` 的端口就是 `jtag_* / gpio0..7_* / uart0_tx,rx / uart1_tx,rx / qspi1_*`。
**这个 IP 在例程里存在但没有被例化**（`design_top_wrapper.v` 里搜不到）。

如果用它：
```
GPS ──UART0──► MCU（C 代码里解析 NMEA，几百行，极其容易）
                 │ 结果写进一个小寄存器块
                 ▼
              FPGA 逻辑读寄存器 → 遥测 / OSD

```

| 层次 | 内容 | 放哪 | 理由 |
|---|---|---|---|
| **算法层** | 灰度 / 边缘 / 卡通化 / 颜色检测 / 运动检测 / 连通域 / 直方图 | **必须在 FPGA 逻辑** | 这是赛题指标，也是"低延迟"叙事的核心，**绝不下放** |
| **统计与反馈层** | AE/AWB 闭环、阈值自适应、延迟测量 | **FPGA 逻辑** | 基础(4)"光线剧烈变化"是显式评分条款，且这是"全硬件闭环"的演示点 |

→ 这样做可省约 **900 LUT + 4 DSP**：`tlm_pack` + `md_ctrl`（遥测组包）~450 LUT、`osd_render` 排版 ~150 LUT、串口命令解析 ~150 LUT，以及 GPS 的 `GGA.v` **158 LUT + 4 DSP** 可整块省掉；并**白送 2 个 UART**（UART0 接 GPS、UART1 接 PC）。依据 `doc/analysis/增量分析与新思路-2026-09-18.md` §2.2。

**建议：花 1~2 天实际验证**（装 FD → 建 RISC-V 工程 → 跑 **hello world** → 验证与 FPGA 的 **AHB/APB 寄存器读写** → **验证固件与 bitstream 一起固化**）：

| 验证项 | 通过标准 | 不通过的后果 |
|---|---|---|
| 装 FD 并取得授权 | FD 能创建 PH1P35 工程并编译 | 回退 G1/G2，主线无损 |
| RISC-V hello world 跑起来 | 串口能打印 | 同上 |
| MCU ↔ FPGA 寄存器读写 | AHB/APB 读写寄存器块成功（MCU IP 有 `AHB_Available:1`、`APB_Available:1`） | 同上 |
| **固件与 bitstream 一起固化** | 掉电重上电后 MCU 程序自动运行 | ⚠ **上电即跑破功 → 整个 G3 方案不能用** |

- **走独立支线，不排进关键路径**：主线仍按 §4.1 G1 / §4.2 G2 用 FPGA 逻辑做，P3（OSD 文本）先用 FPGA 逻辑交付。

> 注意：MCU 与 FPGA 时钟域不同（MCU 核 300 MHz / AHB 150 MHz），**跨域必须走寄存器 + 双触发器或异步 FIFO**（依据 `doc/analysis/增量分析与新思路-2026-09-18.md` §2.2）。

### 4.5 降落点检测算法（**得分主体，先做这个**）

复用 P5 已经要建的 tile 统计（16×9 = 144 tiles，每 tile 80×80 像素），**每个 tile 增加三个累加器**：

```
① 平整度  flat_score = Σ|梯度| / N        ← 越小越平
   · 梯度用 P2 的形态学梯度（已经在算了，白送）
② 均匀度  var_score  = Σ(luma²)/N - (Σluma/N)²   ← 越小越均匀
   · 需要一个 8bit×8bit → 16bit 的平方累加器（1 个 DSP 或 LUT 乘法）
③ 颜色合规 color_ok  = !水面 && !深阴影
   · 复用 P5 的 YCbCr：水面判据 = Cb 高 & Cr 低 & 亮度高
④ 综合评分 → 选 Top-N tile → 转像素坐标 → 画框 + 标 "LANDING SITE"
⑤ GPS 门控（若接了 GPS）：地速 > 2 m/s 时不判定
⑥ 事件触发 → 蜂鸣器 + LED + 上报 type=0x07 LANDING（含 tile 坐标 + 经纬度 + 时间）
```

| 项 | 值 |
|---|---|
| FPGA 成本 | **~400 LUT**（主要是平方累加器和评分比较器）+ 复用 P5 的 tile 基础设施 |
| 对应赛题 | **扩展(1) 视觉增强**、**扩展(2) 目标检测与识别**、**高阶(2) 目标跟踪与信息标注** |

**⚠ 与运动检测的重叠**：P7 的 `motion_8x8` 和这里的降落点检测**共用同一个 8×8 下采样前端和 tile 统计**。
**合并设计**：一套 tile 统计同时输出"运动 tile"和"平整 tile"，共享累加器 → **省 ~300 LUT**。
**这也是为什么 §2.2 的砍单顺序把 P7 放在第 1 位**——砍掉它损失最小，因为它的基础设施被降落点检测继承了。

### 4.6 协议扩展（在缩窄版协议上加两个 type）

沿用 `网络模块-方案（缩窄版）.md` 的 16 B 遥测头，新增：

**type=0x06 GPS**
```
u8  fix_quality    0=无定位 1=GPS 2=DGPS
u8  sat_count      卫星数

u8  raw_len        后面跟的原始 NMEA 字节数（G1 模式下透传）
u8  raw[]          
```

**type=0x07 LANDING（发现降落点事件）**

## 5. "发信号" → 一次免费的得分升级

你说"发送位置和信号"。如果只是网络上报，那是纯通信，只能挂"自主创意"。但**板上有蜂鸣器和 8 组双色 LED**：

```
发现降落点 → ① 网络/串口上报坐标（type=0x07）
             ② 蜂鸣器短鸣 3 声
             ③ LED 闪烁
             ④ OSD 叠加 "LANDING SITE FOUND  N26.0745 E119.2965"
```

**关键**：第 ②③ 步把它从"数据上报"变成了**"根据视频识别结果实现外部控制"** ——
**这正是扩展要求(3) 的字面意思**（「根据视频识别结果实现**外部控制**」）。

| | 只上报 | **加上蜂鸣器/LED** |
|---|---|---|
| 能挂的条目 | 扩展(5) 自主创意 | 扩展(5) + **扩展(3)** |
| 成本 | 0 | **~50 LUT**（但需要引脚表） |

**50 LUT 换一条扩展要求，这是本方案里性价比最高的一笔。** 而且蜂鸣器/LED 是**板载**的，不引入任何外部器件，也就没有"额外处理器"的争议。
