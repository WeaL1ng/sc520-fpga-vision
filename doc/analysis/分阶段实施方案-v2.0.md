## 2. 四条铁律（都是用真实故障换来的）

### 2.1 铁律一：分时复用换面积的改造，**吞吐必须与资源同时验收**

- **触发条件**：任何把数据通路并行度降低（改成"分时/复用"）的改动。
- **为什么**：`awb` 内 `w155_d512_fifo`（512 深）在满时**静默丢弃写入**
  （`soft_fifo_al_f58e8b3e1f3d.v:77` `wr_en_s = (!full_flag) & we`），**无溢出标志、无报错**。
  丢字在屏幕上的表现就是**撕裂 / 只有一半画面在动**。
- **验收方法**（三步，缺一不可）：

| 步 | 判据 | 工具 |
|---|---|---|
| 1 | `awb` 输出率 **≤ 4.34 拍/字** | `sim/p1b/tb_awb_rate3.v` |
| 2 | **FIFO 丢字 = 0**（`drop_cnt = fifo_wr & fifo_full`） | 同上 |
| 3 | **激励必须是真实突发**：每行 **320 字连发 + 51 拍空档** | 同上（`GAP=51`） |

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\run_d4_ab_launcher.ps1 -Which both
```

- **预算推导**：720p60 = 55.296 Mpix/s ÷ 4 px/字 = 13.824 M 字/s；
  ISP 域 `MIPI_RX_BYTE_CLK = 59.995 MHz`（实测）⇒ **4.34 拍/字**。
- **反面教材**：P1a 只做资源差分（DSP 8→2），漏掉吞吐验收 ⇒ 上板撕裂，损失一个完整构建周期。
- **性能参考（实测）**：厂商原版 AWB = **1.34 拍/字 / 零丢字**（余量 3.2 倍）。

> ⚠ **另一个坑**：按均匀流灌数据会把 FIFO 写侧摊平，得出"平均达标"的**假结论**。
> 真实写侧形态来自 `signal_delay.v:76-80` 的 `rd_valid` 窗口。

### 2.2 铁律二：**改 RTL 前，必须把"现状"与 RTL 逐行核对**

- **为什么**：旧版方案把 AWB 的"8 个并行乘法器"记成了"8 个除法器"，
  直接误导 P1a 改错对象，造成前述事故。
- **做法**：动任何模块前，先看该模块在 `phy.area` 的**逐项分解** + **RTL 逐行确认**，
  并标注证据来源（文件 + 行号）。**方案文档里的"现状"段落一律不可直接采信。**

### 2.3 铁律三：**常量乘法绝不能用 DSP**

- **为什么**：DSP 只有 **40** 个，LUT 有 **21,216** 个。器件策略是"省 DSP、用 LUT"。
- **实例**：`gray_binary_96` 原版写 `R*77+G*150+B*29`，综合器吃掉 **12 个 DSP**
  （全设计 8 → 20，50%）。改成移位加法后 **DSP 回到 8**，代价约 450 LUT。
- **移位加法即严格等式**（二进制逐位分解）：
  ```
  77  = 64+8+4+1     -> (r<<6)+(r<<3)+(r<<2)+r
  150 = 128+16+4+2   -> (g<<7)+(g<<4)+(g<<2)+(g<<1)
  29  = 32−2−1       -> (b<<5)−(b<<1)−b
  ```
  > 移位前先扩到 16 位，否则 `(r<<6)+(r<<3)` 溢出 8 位。

### 2.4 铁律四：**上游模块的 `tuser` / `tlast` 语义必须逐一核对，不能想当然**

- **为什么（2026-09-21，P5 上板故障）**：`target_detect_96` 模块级 5 场景全过、
  Python 独立复算全过、综合布线零违例 —— **上板后目标文字永远是 `NONE`**。
  根因在**上游** `awb.v`：

  ```verilog
  awb.v:369  assign O_tlast = (valid_d1 == 0) && (valid_d2 == 1);  // valid 上升沿，不是行尾！
  awb.v:370  assign O_tuser = I_tuser;   // 组合直通
  awb.v:371  assign O_tvalid = valid_d2; // 有流水延迟 ⇒ 与 tuser 不同拍
  ```

  ⇒ 在 `awb` 输出口上，**`tuser` 到达那一拍落在帧间消隐期（`tvalid=0`）**，
  以 `tvalid && tuser` 作帧结算条件**永不成立**；`tlast` 也不是行尾标记。

- **为什么能长期潜伏**：这个错位对**纯逐像素模块**（`gray_binary_96`）完全无害，
  **只有依赖帧/行结构的模块才会炸**。而对它的测试台是"照着教科书视频时序写的"
  ⇒ **仿真激励里根本不存在这个情形**，L1 全绿也查不出来。
- **规范（做法）**：
  1. 新模块只要依赖**帧/行结构**，先读上游源码核对 `tuser`/`tlast` 语义（**看赋值，不看注释**）；
  2. 核对不清就**一律用"纯拍数自计时"**（按每行拍数 / 每帧行数推导边界），
     `target_detect_96` 有现成写法可抄；
  3. **能被观测的量要引出到 OSD**（诊断构建法，见 P5 报告 §3.5）——
     本轮正是靠诊断行读出 `B00`（拍数 = 0）才一次定位，否则会在"是不是光照不对"
     这条歧路上耗掉几轮上板。
- **配套认知**：`验收标准与证据链.md` 推论 4 —— **L1 的激励本身也是假设**。

> 它是**公共底座**，且**几乎零风险**（纯 HDMI 域查表 + 移位加法，不碰算法域）。

**步骤**

1. **字模 ROM**（8×16 ASCII，`0x20~0x7E` 共 95 字形 = 1,520 B，1 块 ERAM）
   - 沿用 P1b 已验证的 **ERAM 推断写法**（`(* ram_style = "block" *)` + 顺序赋值 reg +
     常量 `case`），**不要用 TD IP Core Generator**（P1b 已验证推断可行）
2. **文本缓冲**：48×8 = 384 字符（1 块 ERAM 或 LUTRAM），
   写口 = 状态机，读口 = 渲染器
3. **渲染器 `osd_render.v`**（纯流水线，**像素率路径上禁止乘除**）
   ```
   x,y → (col,row) → 字符码 → 字模行位图 → 位选择 → alpha
   → out = osd*α + video*(1-α)，α 取 1/4、1/2、3/4 用**移位+加法**
   ```
4. **延迟可视化 `frame_tag.v`**
   ```
   采集域(MIPI_RX_BYTE_CLK)：ms 计数器（sys_clk_50m 计数 × 20µs 刻度）
       每帧 tuser 把计数器值写入 ts_reg[wp]（wp = video_in 写指针）
   显示域：video_out 在 vsync 处按 rp 读出 ts_reg[rp] → 跨域搬**一个标量**
   HDMI 域：latency_ms = now_ms − tag
   OSD：写 "LATENCY: 12 ms"
   ```
   > **要求**：`ts_reg` 用 4 项寄存器阵列（对应 4 帧缓冲），由 wp/rp 索引；
   > 跨域只搬**一个标量**，用握手或双触发器同步，**不要多 bit 直接打拍**。
5. OSD 常驻：`MODE: GRAY | 1280x720@60 | LATENCY: 12 ms`

**门禁**：上板能看到实时变化的 ms 数值（遮挡/移动时应有 1~3 ms 级变化）；
文本无抖动；**slice ≤ 66%**。

**回退**：ms 数值跳变异常 → wp/rp 对齐错了；改用"帧计数差 × 16.67 ms"做粗延迟。

### 阶段 P6 — AE 闭环（5~6 天）→ 高阶(5) + 基础(4)"光线剧烈变化"

> ⚠ **本阶段已删除旧版步骤 4「AWB 重构」**（⛔ 实测证伪，见 §2.1/§2.3）。
> 标题由「AE/AWB 闭环」改为「AE 闭环」。

**目标**：把亮度控制做成闭环。

> **为什么必修**：基础要求(4) 原文写着"**系统稳定性：光线剧烈变化时工作正常**" ——
> 这是**显式评分条款**，而现在是**纯手动按键调 AE**，无任何自动闭环。

**步骤**

1. **亮度统计**（ISP 域逐拍累加，与 P5 的 tap 同域）

2. **AE 步进状态机 `ae_ctrl.v`**（24 MHz 域）
   ```
   若 sum > hi_target: AE -= step
   若 sum < lo_target: AE += step
   死区 ±3%（避免振荡）
   step 自适应：偏差 > 30% 用大步长，接近时小步长
   cnt_clip > 5% 且画面偏亮 → 优先降 AE（高光保护）

   更新节流：最多每 2~4 帧调一次

   ```

   > （初始 80、下限 16、上限 89 ⇒ 只能升 9 步，长按 KEY2 约 0.3 秒就饱和）。
   > 做 P6 时**必须一并处理**：要么扩大 AG 上限，要么把增益补偿放到数字域。
3. **接上已有 I2C 通道**：复用 `uicfgcs500_720p` 的 AE 表机制

   把 `ae_set.v` 改成"自动/手动双模"

**门禁**：① 遮镜头 → 2 秒内变亮恢复；② 开灯直射 → 2 秒内变暗恢复；
③ **连续 1 分钟面对变化场景，画面无可见闪烁/振荡**。

### 阶段 P7 — 运动目标检测（零额外 DDR 带宽）（5~6 天）→ 高阶(4) + **扩展(3)**

> ★ **先做一件几乎免费的事（扩展(3) 外部控制）**：`target_detect_96` 的
> `O_tgt_valid` **已经引到顶层**，接一根线到板载 LED（或蜂鸣器）即可多覆盖一条扩展要求。
> 建议放在 P7 开头做掉，别等到最后。

**架构决定**：**不新增任何 DDR 事务。**
全分辨率帧差要再读 165.9 MB/s，会让用户口占用从 31% 升到 47%，
且单端口仲裁无 transaction tag，容易饿死显示。

> ⚠ **tap 点修正（P5 的实测结论）**：原计划写"HDMI_PIXEL_CLK 域旁路 video_out 显示读流
> （与 P5 共用同一个 tap）"，但 **P5 实际把 tap 放在了 ISP 域** —— 因为 HDMI 域
> 当时只剩 +11.1% 且是**布线拥塞型**（网上延迟占大头）；交付版实测 HDMI 域已被压到
> **+2.3%**，更加不能再往里塞逻辑。**P7 必须同样放 ISP 域**，
> 把运动结果（tile 标志 / 计数）随帧跨域送到 HDMI 域叠加。

**方案：8×8 块平均 + ERAM 存上一帧**
```
① ISP 域取流（与 P5 同域、同 tap 语义）
   每 8×8 块累加灰度 → 160×90 = 14,400 个缩略亮度
② 缩略帧存 ERAM：14,400 × 8 bit = 115,200 bit ≈ 6 块 ERAM（存"上一帧"）
   当前帧用滚动累加器（一块累完就比，不需整帧缓冲）
③ 比较：|cur - prev| > TH → 运动
   建议用 sigma-delta 背景建模代替简单帧差（抗光照突变）：
       bg += (cur > bg) ? +1 : -1      // 只需加减和比较
       motion = |cur - bg| > TH
④ 3×3 形态学（腐蚀→膨胀）去噪，在 160×90 上做，极便宜
⑤ 输出：运动 tile 图 → 包围框（×8 映射回原图）→ OSD 画框 + "MOTION: 1234"
⑥ 帧末把 cur 写入 prev（真双口 ERAM 或乒乓两块）
```

**代价**：约 **+400 LUT + 6 ERAM**，**DDR 带宽增加 = 0**。

**门禁**：挥手 → 出现运动框与计数；静止 → 计数归零、无框；
**缓慢改变光照 → 不应误报**（验证 sigma-delta 生效）。**slice ≤ 76%**。

**回退**：块平均边界效应导致框抖动 → 阈值加滞回（进入 20，退出 12）。

## 6. 验证与调试方法

### 6.1 每阶段必走的验证链

```
改 RTL 前：★ 与 RTL 逐行核对"现状"，并查 phy.area 的模块分解（铁律二）
   ↓
★ 核对上游接口语义：tuser/tlast 看**赋值**不看注释；除非确认无误，
  一律用"纯拍数自计时"（铁律四）
   ↓
RTL 自检（读代码 3 遍 + 检查位宽/时钟域/复位）
   ↓
★ 吞吐验收（仅当本阶段动过数据通路的复用/分时；铁律一）
   ↓
功能仿真（写自检测试台，用 check 计数 + 末尾 PASS/FAIL 汇总）
   ↓
★ 把关键内部量引到 OSD（**诊断构建法**）——L1/L2 全绿也可能上板全错，
  有一个"能读出内部状态"的通道，定位成本从"几轮上板"降到"一次"
   ↓
TD 综合（查 .log 的 ERROR；注意退出码可能仍为 0）
   ↓
P&R + 抽取门禁（面积/各域 Fmax/违例数；`verify_td_reports.py` 会一并报 SWNS 警戒）
   ↓
ChipWatcher 抓关键信号
   ↓
上板看现象 + 拍照存档
```

### 6.2 ★ 本轮的踩坑清单（务必避开）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **TD 读 `.prj` 不是 `.al`** | `HDL-8007 ... is a black box` | 新增/改名源文件后，**`.al` 与 `_Runs/*/*.prj` 都要改** |
| 2 | **构建失败但退出码为 0** | 脚本"成功"了但没产物 | **必须查日志里的 `ERROR`** |
| 3 | **门级除法器网表让仿真超时** | 单次仿真 >600 s | 用 `divider_beh.v`（已与门级逐拍核对）替换 `divider_gate.v`；>600s → ~5s |
| 4 | **ModelSim ASE 无 `vopt`** | — | 用 `vsim -lib work <tb> work.glbl`（**必须带 `work.glbl`**，供应商原语需要） |
| 5 | **`+define+` 名字以数字开头** | 预处理器静默忽略，`ifdef` 全落空 | 宏名必须是合法 Verilog 标识符（如 `D4UNFIXED` 而非 `d4unfixed`） |
| 6 | **PowerShell 5.1 按 GBK 读 `.ps1`** | 中文注释导致语法错误 | 含中文的 `.ps1` **必须带 UTF-8 BOM**；或用纯 ASCII 启动器以 UTF8 读入 |
| 7 | **`Get-Content` 默认 GBK** | 看 UTF-8 文件显示乱码（**文件本身没错**） | 用 `read` 工具或 `-Encoding UTF8` |
| 8 | **悬空的 `td.exe` 锁工程** | 构建卡住 | 按 `StartTime` 判断并结束 |
| 9 | **多比特 CDC 直接打拍** | 采到中间态（如模式 01→10 途中采到 11） | 2-FF 同步 + **帧首锁存** |
| 10 | **常量乘法写成 `*`** | 吃 12 个 DSP | 移位加法（§2.3 铁律三） |
| 11 | **信了上游 `tuser`/`tlast`** | 上板后帧结算**永不发生**（症状：永远 `NONE` / 计数恒 0），而仿真全绿 | 核对赋值语句；不确定就**纯拍数自计时**（§2.4 铁律四） |
| 12 | **诊断量用十进制显示** | 6 位十进制要一整套比较链，压垮 HDMI 域时序 | 诊断量优先**十六进制**（纯位切片，零额外逻辑） |
| 13 | **`$display` / `print` 里带非 GBK 字符** | 脚本在**最后一步**抛 `UnicodeEncodeError`，退出码 1 —— 一个"偶尔跑不通"的守门脚本等于没有守门 | 文件头加 `sys.stdout.reconfigure(errors="replace")`（P5 实际踩到） |
| 14 | **Verilog 拼接（concat）位宽自决定** | `{h, t, (r2 - ...)}` 的第三项含 11 位 `r2` ⇒ 整个拼接 19 位，赋给 12 位时**从左侧截断**，函数恒返回 0 | 先落到中间变量再切片（P5 错误 3） |
| 15 | **`HDL-7225 'xxx' is already implicitly declared`** | Verilog 先按 **1 位隐式线网**使用，再看到 16 位 `reg` 声明 ⇒ 屏上拿到的是 1 位线，显示就是错的（P6 把 HDMI 域寄存器声明写在了 `u_hdmi_mixer` 例化之后） | **声明必须早于使用**；编译日志里出现 "implicitly declared" 一律当错误处理 |
| 16 | **TD 工程文件的 `<File>` 块必须完整** | 只插 `<File Path=...>` 一行不补 `<FileInfo>`/`</File>` ⇒ `PRJ-8601 ERROR: Load project file ... error`，构建在 `read_design` 就挂 | 每个新文件补齐 `FileInfo` + 4 个 `Attr` + `</File>`（`.al` 与两个 `.prj` 都要） |
| 17 | **TB 里断言名用中文 / 超过 32 字节** | 经 `[255:0]` + `%0s` 打印成乱码、甚至**整行消失**（P6 组 1 第一版"看起来全错"有一半是这个） | 断言名用 **ASCII**，中文只写注释；名字寄存器加宽到 `[511:0]` |
| 18 | **在动作发生的同一 posedge 读输出** | 读到的是非阻塞赋值**更新前**的值（P6 T10 误报） | 读之前多等 `@(negedge clk)` |
| 19 | **`$display` 用 `%+0d`** | ModelSim 报 `vsim-PLI-3947 Invalid format specifier '+'` | 用 `%0d`（负值自带负号） |
| 20 | **PowerShell 双引号吃掉反引号** | `python -c "…`MACRO…"` ⇒ 宏没被展开，编译报"未定义变量" | 替换文本里带反引号一律写成 `.py` 文件执行 |

**讲解要点（对评委的话术）**

1. **算法合规且品类多**：4 种算法（灰度/二值化/反色 + 后续卡通化），
   **与官方参考例程（边缘检测）完全不同**；这是赛题明确要求的"不能和参考实例相同"。
2. **延迟数字**（高阶 3）—— FPGA 相对 Python+OpenCV 最有说服力的证据。
3. **资源优化做得实**：OSD 的 2,500 LUT 组合逻辑改成 ERAM；

4. **可靠性来自实测**：曾因 AWB 分时复用导致吞吐不足、上板撕裂，

## 8. 风险与回退路径总表

| 风险 | 触发信号 | 回退路径 |
|---|---|---|
| **分时复用导致吞吐不足** | `awb` > 4.34 拍/字 / FIFO 丢字 / 上板撕裂 | **回退为并行实现**（已有先例：P1a 的 TDM 回退为厂商原版）。脚本 `tools/run_d4_ab_launcher.ps1` |
| **常量乘法吃 DSP** | 全设计 DSP 突然上涨 | 改移位加法；查 `phy.area` 里 DSP 突增的模块 |
| P2.6 上板某模式异常 | 画面不对 | 查 `gray_binary_96` 的 `I_mode` 接线 → 再查帧首锁存的 `S_raw_tuser` 极性 |
| P2.6 Logo 某模式消失 | 模式 0/1 无 Logo | 检查 `u_hdmi_mixer.I_osd_en` 是否为 `1'b1` |
| P3 延迟数值跳变 | latency 乱跳 | wp/rp 对齐错；改用"帧计数差 × 16.67 ms"粗延迟 |
| P4 面积超预期 | slice 涨 >3% | 砍中值滤波；再不行只做"量化 + 边缘" |
| P5 检测框抖动/残留 | 框闪烁或移出后不清 | ✅ **本版未出现**（tile 统计是"每帧从零累加" ⇒ 天然无残留）。若以后出现：2 帧连续命中确认 + 滞回阈值 |
| **P5 板上"永远 NONE"** | 检测器一帧都没结算 | ★ 根因是**上游 `awb` 的 tuser/tlast 与数据不同拍**（组合直通 vs 流水延迟）⇒ 改**纯拍数自计时**。**已写入铁律**：任何依赖帧/行结构的新模块，先核对上游标记语义 |
| **诊断量上 OSD 压时序** | HDMI 域余量骤降 | 诊断量用**十六进制**显示（纯位切片，零比较链）；P3 的十进制比较链就是反面教材 |
| P6 AE 振荡 | 亮度来回摆 | 加大死区（±8%）、加长节流（每 4 帧）、降步长、减少积分器重置 |
| **P6 AE 增益范围不足** | 长按 KEY2 约 0.3 s 就饱和 | lab_topic2 已实测此问题（AG 初始 80/下限 16/上限 89 ⇒ 仅 9 步）；扩大上限或把补偿放数字域 |
| P7 运动误报（光照变化） | 静止时 MOTION 非 0 | 关闭简单帧差，只用 sigma-delta；阈值加滞回；**AE 上任后此项风险上升** ⇒ 先做 P6 再做 P7 |
| **SWNS 已只剩 +0.304 ns**（交付版实测） | 全局 setup 裕量低于自设 0.5 ns 警戒 | 零违例（STNS/HTNS=0）。**P6 加逻辑后必须重建对比**；若转负，给 `u_hdmi_mixer` 的 OSD 判决加一级流水（P3 用过同样手法） |
| **HDMI_SERIAL_CLK 域继续恶化** | 全局 SWNS < 0.5 ns | V4 已从 1.182 降到 0.702 ns（该域成最差路径）；给 `u_hdmi_mixer` 再打一级流水 |
| DDR 域跌破 0.5 ns | `usr_clk` 裕量小 | 删掉 `settings.cfg` 的 `set area_option -packarea` 重跑 |
| 面积超 80% | 门禁失败 | 按 §9 裁剪顺序砍 |
| 新增算法域 125/150 MHz 达不到 | 空壳验证 Fmax < 100 MHz | 退到 100 MHz（÷15）；或不做快速算法域，重算法降到 ISP 域 2× 复用 |
