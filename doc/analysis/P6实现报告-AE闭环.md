## 2. ★★ 现状核对（铁律二）：三个"想当然"全被 RTL 推翻

铁律二要求**动 RTL 前必须把"现状"与 RTL 逐行核对**。本轮核对出四条硬事实，
其中两条与文档/注释矛盾。**结论一律以 RTL 为准。**

### 2.1 AE 的通路（逐行）

`ae_set.v` → `uicfgcs500_720p.v` → `uics500regAE.v` → I2C：

| 环节 | 事实 | 证据 |
|---|---|---|
| 目标值来源 | 按键维护 `r_ae_set` / `r_ag_set`，与已生效值比较后脉冲 `r_ae_req` | `ae_set.v:88-121` |
| 提交门控 | 必须 `I_cam_cfg_done && I_ae_cfg_done` | `ae_set.v:116` |
| 写寄存器 | 曝光 `0x3e00/01/02`（20 位）、增益 `0x3e08/09`（16 位） | `uics500regAE.v:47-51` |
| 增益经过查表 | `SC500GainTbl` 的输入是 **`I_ag - 16`** | `uicfgcs500_720p.v:130` |
| 一次改动的代价 | **5 个寄存器**，100 kHz I2C ⇒ 约 2 ms | `uics500regAE.v:42` |

### 2.2 ★ 出厂默认已经贴着两个执行机构的上限

`ae_set.v:76` + 初始化表 `uics500reg_720p60.v` 解出来是同一组值：

| 量 | 值 | 解码 |
|---|---|---|
| 曝光 | **1990** | 表里 `0x3e00=00, 0x3e01=7C, 0x3e02=60` ⇒ `{0,0x7C,6}` = 0x7C6 = **1990** |
| 模拟增益 | **80** | 表里 `0x3e08=0F, 0x3e09=20` ⇒ `0x0F20` ⇒ 表索引 64 ⇒ AG = 64 + 16 = **80** |

而 `ae_set.v:91` 的 AE 加值条件是 `(r_ae_set < 1990)` —— **默认值就是上限**。
⇒ **AE 一开始就在顶格**，向上零余量。增益也只有 80→89。

### 2.3 ★ 推翻"AG 只能升 9 步"这条流传的说法

原方案写："AG 初始 80 / 上限 89 ⇒ 只能升 9 步"。**这不是问题的本质**：

```
SC500GainTbl 的索引范围 = 0..73        （表里实际写了 74 项）
AG 的钳位范围           = 16..89       ⇒ 索引 = AG-16 ∈ [0,73]
⇒ AG 的 [16,89] **正好覆盖全表**，不存在"上限没写满"的问题。
```

真正的问题是**起点太高**：索引 64（`0x0F20`）= 粗增益 16 倍 × 细增益 1.0 = **16 倍**，
而表的**顶端**只有 20.5 倍（`0x0F29`）。⇒ 向上仅 **+28%**。

### 2.4 ★★ 增益表在第三段被截断了（本阶段最大发现）

把 `SC500GainTbl.v` 的三段按"粗增益 + 细增益"解码：

| 索引段 | 值 | 粗增益（`0x3e08` 低四位） | 细增益（`0x3e09`） | 项数 |
|---|---|---|---|---|
| 0 .. 31 | `0x0320`..`0x033F` | `0x3` ⇒ 4 倍 | `0x20`..`0x3F`（1.0x~1.97x） | **32（写满）** |
| 32 .. 63 | `0x0720`..`0x073F` | `0x7` ⇒ 8 倍 | `0x20`..`0x3F` | **32（写满）** |
| 64 .. 73 | `0x0F20`..`0x0F29` | `0xF` ⇒ 16 倍 | 只写到 `0x29`（1.28x） | **10（断了）** |

前两段都把 `0x20~0x3F` 写满了 32 项，第三段只写了 10 项就停
⇒ **判定为漏写，不是器件上限**。补到 `0x0F3F` 后：

| | 原表顶 | 补全后 |
|---|---|---|
| 最大模拟增益 | 16 × 1.28125 ≈ **20.5 倍** | 16 × 1.96875 = **31.5 倍** |
| 相对默认（16 倍） | +28% | **+97%** |

> ⚠ **这是推理，不是实测**。所以 `ae_ctrl.AG_MAX` 做成参数：
> **默认 89**（只用已验证段），把 111 留给上板 A/B 验证（§8 风险表 R1）。
> 表本身已经补全（多 22 行 case，不占额外资源），**用不用由参数决定**。

### 2.5 ★ 附带的两个"注释不可信"实例

| 位置 | 注释说 | RTL 实际 |
|---|---|---|
| `ae_set.v:99-101` | "AG=48 maps through SC500GainTbl to 0x0f20, approximately 4x" | AG=48 ⇒ 索引 32 ⇒ **`0x0720` ≈ 8 倍**（`0x0F20` 对应 AG=80） |

## 3. 架构：三个模块 + 一处参数

```
   ISP 域 (MIPI_RX_BYTE_CLK ≈ 60 MHz)          24 MHz 域 (D1)
   ┌────────────────────────────┐  每帧一组  ┌──────────────────────────┐
   │ u_luma_stats               │  标量      │ u_ae_ctrl                │
   │  · ΣY(32b) · clip(20b)     │ ─────────► │  比例 + 死区 + 自适应步长 │
   │  · avg(8b)  · tog(1b)      │ 准静态多比特│  + 方向反转阻尼           │
   │  帧末锁存 + 翻转标志        │ + 翻转标志 │  + 高光保护              │
   └────────────────────────────┘            └────────────┬─────────────┘
                ▲                                          │ 自动目标
                │ 接 awb 的 96 bit 输出（旁观者，无反压）    ▼
        ┌───────┴────────┐                   ┌──────────────────────────┐
        │  u_awb         │                   │ u_ae_set（自动/手动双模） │
        └────────────────┘                   │  → uicfgcs500_720p → I2C │
                                             └──────────────────────────┘
                                                          │
                                             OSD: `A 07C6 G 59 L 6E`（HDMI 域）
```

### 3.1 `luma_stats.v`（新增，ISP 域）

| 设计点 | 做法 | 理由 |
|---|---|---|
| **放哪个域** | ISP 域（`axi4s_video_aclk`） | 亮度统计要在**像素率**上做（每拍 4 个像素求和）。HDMI 域交付版只剩 **+2.3%** 余量，塞进去就是自找违例（P5 已因此把检测搬到 ISP 域） |
| **帧边界** | **纯拍数自计时**：320 拍/行 × 720 行 = 230,400 拍，最后一拍编号 230,399 | 铁律四：`awb.v` 的 `O_tuser` 是组合直通、`O_tvalid` 有流水延迟 ⇒ **两者不同拍**，用 `tvalid && tuser` 做帧结算永不成立（P5 上板"永远 NONE"就是这么来的） |
| **亮度公式** | `Y = (77R + 150G + 29B) >> 8`，全部移位加法 | 与 `gray_binary_96` **同一个式子** ⇒ "AE 看到的亮度"就是"灰度模式看到的亮度"，不会出现两套亮度打架；铁律三：常量乘法不用 DSP |
| **平均亮度** | `avg ≈ ((ΣY>>10) × 18642) >> 24` | 921600 = 900×1024，把 /900 换成"乘倒数再右移"。**★ 算在 `ae_ctrl`（24 MHz 域）而不是这里** —— 见 §7.2 的布线实测教训 |
| **控制回路用什么** | **直接用 ΣY 与常量阈值比**，不用 avg | 回路上一个除法器都没有；avg 只给 OSD 显示 |
| **跨域** | 帧末锁存整组 + 翻转 `O_tog`；读侧 2-FF 同步 + 边沿捕获 | 准静态多比特（与 P5 同款，已在板上验证） |

### 3.2 `ae_ctrl.v`（新增，24 MHz 域）

**控制律：比例 + 死区 + 自适应步长 + 方向反转阻尼。**

| 机制 | 参数/做法 | 为什么 |
|---|---|---|
| 偏差分区 | far(>100%) / mid(>50%) / near(>30%)，**全部用常量比较** | 不走除法；`far` 时 AE 步长 256、AG 步长 8 |
| 死区 | **±3%** | 防振荡的第一道防线 |
| **不做积分项** | —— | 执行机构（曝光/增益）本身带记忆，被控量对执行量**没有稳态误差**，比例+死区就够。**没有积分器 ⇒ 没有积分饱和 ⇒ 场景突变不需要"重置积分器"**（原方案里的这一条因此删掉，见 §10） |
| 方向反转阻尼 | 本次方向与上次相反 ⇒ 步长**减半** | 抗"过冲—回摆"的第一手段（比拉长节流更有效） |
| **先动谁** | 变亮：**先加曝光，再加增益**；变暗：**先减增益，再减曝光** | 曝光是"多收光"（信号噪声同比例，SNR 不变）；增益是"放大已有信号"（噪声一起放大，SNR 变差） |
| **高光保护** | `clip > 全画面 2%` ⇒ **无条件变暗**（不看 ΣY） | "画面中心暗 + 窗户过曝"会把均值骗过去，继续提亮就把高光烧成一片白 —— AE 最经典的翻车点 |
| 节流 | 每 **2** 个新统计帧才允许动一次 | I2C 一次要写 5 个寄存器 ≈2 ms，不能每帧都写 |
| 命令不堆积 | 上一目标未提交（`I_ae_cur != O_ae`）⇒ 不下发新目标 | 防止 I2C 队列被冲垮 |
| 钳位 | AE `[2,1990]`、AG `[16, AG_MAX]` | AE 上限是 VTS=1000 的法律上限 |

**初值选择**：`S_ae_t = 1990`、`S_ag_t = 80` —— **就是出厂默认值**。
⇒ 装上 P6 之后，**默认画面与今天完全一样**，不会出现"升级完反而变暗/变亮"。

### 3.3 `ae_set.v`：自动 / 手动双模（**手动路径一个字节都没改**）

```verilog
w_ae_set = I_auto_en ? I_ae_auto : r_ae_set;   // r_ae_set 仍是按键维护的手动目标
w_ag_set = I_auto_en ? I_ag_auto : r_ag_set;
```

- 下游"提交 + I2C 握手"逻辑（`r_ae`/`r_ag`/`r_ae_req`/`cfg_done` 门控）**完全不动**
  ⇒ 自动与手动共用同一条写传感器通路，不会出现"自动能用但手动失效"。
- 自动模式下**屏蔽手动按键对目标的修改**（否则长按会悄悄改掉手动目标，
  切回手动时画面突变，很难排查）。
- 手动 AG 上限由端口 `I_ag_max` 给（与 `ae_ctrl.AG_MAX` **同一个常量线**）
  ⇒ 不会出现"自动能上 111、手动只能 89"这种自相矛盾的可观测行为。

### 3.4 按键手势（互不冲突，全部在 OSD 上可观测）

| 手势 | 行为 |
|---|---|
| 短按 KEY1 | 图像模式 0→1→2→3→4→0 |
| 长按 KEY1 | （透给 `ae_set`）手动调 AE/AG |
| **短按 KEY2** | **切换 AE 自动 / 手动**（P6 新增） |
| 长按 KEY2 | （透给 `ae_set`）手动调 AE/AG |

> 为什么用"短按 KEY2"：红线1 之后**这个手势一直是空的**（KEY1 短按专职切模式，
> KEY2 短按没有任何功能）⇒ 不占用任何既有手势，也不与长按调 AG 冲突。
> `key_mode_ctrl` 只多了一个单拍脉冲输出 `O_auto_tog`。

### 3.5 OSD 诊断行（区域 (256,144)，16 槽）

```
A 07C6 G 59 L 6E
│ │    │ │  │ │
│ │    │ │  │ └─ 平均亮度（十六进制，0x00~0xFF）
│ │    │ │  └─── 'L'
│ │    │ └────── 模拟增益（十六进制；十进制 89 = 0x59）
│ │    └──────── 'G'
│ └───────────── 曝光值（十六进制；上限 1990 = 0x7C6）
└─────────────── 'A' 自动 / 'M' 手动
```

**为什么显示这四个量**（而不是显示"AE 正在工作"这种自夸）：

- `A/M` —— 证明"当前确实是自动"，也是短按 KEY2 的可见反馈；
- **曝光值** —— 闭环的主要手段，**饱和时一眼看出**（1990 = `07C6` 顶格）；
- **增益值** —— 本次**唯一还有余量的手段**（80→89），它是否往上涨，
  就是"闭环真的在动"的直接证据；
- **平均亮度** —— 被控量本身，收敛与否看它是否稳定。

**全部用十六进制**：纯位切片 ⇒ 零比较链 ⇒ 不压 HDMI 域时序（P3 的 `LATENCY`
除法链就是反面教材）。

**位置校验**：`python tools\verify_osd_layout.py` 现在抽 **7 个区域、21 对**，
全部不重叠、不越界 ✅（新行放在 (256,144)，正好在动态 `CNT` 文本下沿之下）。

> ⚠ **诚实说明**：过曝像素数 `clip` **已经引出到顶层并接到 `hdmi_mixer`，但当前
> 16 槽格式里没有显示它**（16 槽刚好被 `A/M + 曝光 + 增益 + 平均亮度` 占满）。
> 高光保护的可观测证据目前来自 **L1 的 T4 断言**（"均值偏暗 + 过曝超限 ⇒ 必须变暗"）；
> 上板时它表现为"对着窗户/灯拍，画面不会为了提亮把高光烧白"。
> 要把它搬上屏，只需把该区从 16 槽扩到 24 槽（区域 (256,144)-(639,159) 同样不重叠），
> 留给 P8 的自检页一起做。

## 5. ★ 验证抓出的真 bug（L1 的价值所在）

### 5.1 ★★ bug 1：节流决策用了**上一帧**的统计量

**现象**：`tb_ae_ctrl` 组 1 的逐条断言**整体错开一帧** ——
T2 期望 `AG +8` 却是 `80->80`；接着 T9a 的观测里出现了 T2 的动作（`80->88`）。
"看起来像控制器全错"。

**排查**：加临时调试台逐拍打印内部量，看到关键一行：

```
t=49000 edge=1 valid=1 thr=1     <- 节流允许动作
t=51000 thr=0 ... upd=0          <- 节流确实清零了，但**没动作**
```

⇒ 节流放行了，但 `w_can_move` 为假 —— 因为**决策用的 `S_sum_q` 还是上一帧的旧值**。

**根因**：捕获与决策写在同一个 `always` 块、同一个时钟沿里：

```verilog
if (w_tog_edge) S_sum_q <= I_stats_sum;      // 本拍才把新值写进寄存器
...
if (w_tog_edge && S_sum_valid) begin         // 同一拍就用 S_sum_q 决策
    ... w_can_move ...                       // ⇒ 用的是**旧值**
```

**修法**：捕获时置位 `S_pending`，**下一拍**才用刚捕获的数据决策：

```verilog
if (w_tog_edge) begin
    S_sum_q   <= I_stats_sum;   // 捕获
    S_pending <= S_sum_valid;   // 下一拍决策
end
...
if (S_pending) begin ... end    // 决策用的是**新值**
```

> **为什么这个 bug 值得单独记**：它对**闭环收敛**几乎无害（只是整体慢一帧，
> 组 2 照样收敛），如果只做"看它能不能收敛"的测试，**永远发现不了**。
> 是组 1 那种"每条控制律单独钉死"的断言把它逼出来的。

### 5.2 ★ bug 2：`O_dir` 被"无动作"的决策清零 ⇒ 诊断量失效

**现象**：T4 高光保护的**动作是对的**（AG 确实降了 8），但读 `O_dir` 得到 0 而不是 3。

**根因**：`O_dir` 在"节流没放行"和"放行了但不需要动"两个分支里都被清零。
而节流是**每 2 帧才放行一次** ⇒ 中间那一帧必然把方向冲成 0
⇒ 屏上/调试抓到的多半是 0，**这个诊断量等于没有**。

**修法**：`O_dir` 只在**真正动作**时更新（粘住上一次动作的方向），
手动模式才清零。语义也更清楚：**"上一次实际动作的方向"**。

### 7.2 ★★ 第 1 版的失败与修复（本阶段最有价值的一条工程教训）

**第 1 版**：`verify_td_reports.py` 报 SWNS **+0.101 ns**（低于自设 0.5 ns 警戒线），
而且 **`MIPI_RX_BYTE_CLK` 的 Fmax 从上一版的 77.954 MHz 掉到 60.361 MHz
（余量 +29.9% → +0.6%）** —— ISP 域直接变成最紧的域。

**先取证再改**（不凭"我觉得是那个加法树"动手）：从 `pr.timing` 抽出该 Path Group
的最差路径，逐级看延迟分解：

| 累计延迟 | 级数 | 位置（`luma_stats.v` 行号） |
|---|---|---|
| 6.5 → 9.3 ns | 4..7 | **112**：`luma77()` 的移位加法（77/150/29） |
| 10.0 → 10.8 ns | 8..9 | **137**：`y_beat = y0+y1+y2+y3`（4 点求和） |
| 11.0 → 13.5 ns | 10..13 | **152**：`w_sum_nxt = S_sum + y_beat`（32 位累加） |
| 14.4 ns | 14 | **163**：`w_s10 = w_sum_nxt[31:10]` |
| **16.307 ns** | 15 | **165**：`w_avg_acc`（平均亮度的 **6 项 33 位移位加法树**） |

`Data Path Delay = 16.307 ns`（cell 10.441 = 64% / net 5.866 = 36%），周期 16.668 ns。

**根因**：平均亮度虽然"每帧只用一次"，但它**组合依赖像素率信号**（`S_sum`），
所以它**就在像素率路径上**。第一个 `luma77` 结果要在同一拍里穿过
"亮度 → 求和 → 累加 → 平均值"整条链。

**修法**：把平均亮度整个搬到 `ae_ctrl.v`（**24 MHz 域**，周期 42 ns）。
它在那边只用于 OSD 显示，与死区判决毫无关系（判决用 ΣY 与常量阈值比），
所以放在哪个域**对功能没有任何影响**，但对时序影响巨大。

**效果**（见 §7.1）：SWNS **+0.101 → +1.175 ns**（比 cart8diff 的 +0.304 还好），
ISP 域 **+0.6% → +22.0%**，HDMI 域 **+4.2% → +9.7%**。

> ★ **这条值得升格为经验**：**"每帧只用一次" ≠ "可以随便放"。**
> 判断一个组合逻辑在不在关键路径上，要看它**依赖不依赖像素率信号**，
> 而不是看它**多久被用到一次**。
> 另外，这次修复**没有牺牲任何功能**，反而把全局时序一起改善了 ——
> 因为逻辑从 60 MHz 域挪到 24 MHz 域，工具在布局时把它放在了更宽松的位置。

## 11. ★★ 2026-09-23 上板复盘：闭环**卡在双上限**，根因是缺少饱和钳位

### 11.1 现象（用户上板照片直接读出）

```
A 07C6 G 59 L 93      ← 曝光 1990（上限）、增益 89（上限）、平均亮度 147（目标 112）
B E0 W 00000 C 79/80  ← 全画面零个暖色像素（橙色目标就在画面正中）
```

**决定性矛盾**：`L=147` 远高于死区上限 115 ⇒ 闭环**应该**往下调增益，
而增益偏偏顶在上限 89 —— 也就是 **"想往下调却没调"**。

### 11.2 根因：目标推进只判"能不能动"，**不做钳位**

```verilog
wire [15:0] w_ae_up = w_ae_can_up ? (S_ae_t + w_st_ae) : S_ae_t;   // ← 没钳位！
wire [15:0] w_ag_dn = w_ag_can_dn ? (S_ag_t - w_st_ag) : S_ag_t;   // ← 没钳位！
```

| 方向 | 例子 | 后果 |
|---|---|---|
| 往上 | `S_ag_t=88`（< AG_MAX=89 ⇒ 判定"能动"）而步长 8 ⇒ 目标 **96 > 89** | 越界；写到传感器的增益查表索引变成 80（24 倍），**与参数表意图不符** |
| 往上 | `S_ae_t=1980` 而步长 256 ⇒ 目标 **2236 > 1990** | **非法曝光**（超过 VTS=1000 允许的最大行数） |
| 往下 | `S_ae_t=200` 而步长 256 ⇒ `200-256` 在 16 位无符号下**下溢成 65480** | ① 把 65480 写出去；② `w_committed = (I_ae_cur == O_ae)` 因为传感器端不可能等于 65480 而**永远为假** ⇒ **闭环永久冻结** |

最后一行正是屏上看到的"卡在双上限、不再调节"。

### 11.3 修法：饱和加/减 + 把饱和状态显示出来

```verilog
function [15:0] sat_add; input [15:0] a,b,hi; begin
    if (a >= hi) sat_add = hi;
    else if ((hi - a) < b) sat_add = hi;      // hi-a 不下溢（a<hi）
    else sat_add = a + b; end
endfunction
function [15:0] sat_sub; input [15:0] a,b,lo; begin
    if (a <= lo) sat_sub = lo;
    else if ((a - lo) < b) sat_sub = lo;      // a-lo 不下溢（a>lo）
    else sat_sub = a - b; end
endfunction
```
★ 注意 `sat_sub` **不能**写成 `(a - b) < lo` —— 那正是下溢本身，判断会失效。

**同时新增 `O_sat[1:0]` 并显示在 OSD 首行第 2 槽**：

| 字符 | 含义 |
|---|---|
| `+` | 有执行机构**顶在上限**（想变亮但没余量） |
| `-` | 有执行机构**抵在下限**（想变暗但没余量） |
| 空格 | 正常，闭环还有余量 |

⇒ 那天的 `A 07C6 G 59 L 93` 以后会显示成 **`A+07C6 G 59 L 93`**，
**一眼就能区分"在正常调节"与"卡在极限"**，不必再靠心算比对数值。

### 11.4 为什么这个 bug 之前的 L1 没抓到（诚实记录）

`tb_ae_ctrl` 组 2 的闭环收敛测试里，AG 一路涨到 89 时步长恰好是 1
（偏差已进入 near 档），所以**刚好落在上限上没有越界**；
组 1 的 T2 是 `80→88`（步长 8，88 ≤ 89）也没有越界。
⇒ **测试用例的取值恰好避开了越界区间** —— 这类"边界差一点"的 bug
只有专门构造"接近上限 + 大步长"的用例才会暴露。

**已补的回归用例（下一步加进 `tb_ae_ctrl`）**：
`S_ag_t=88 + far 步长 8 ⇒ 必须饱和到 89（不得变 96）`、
`S_ae_t=200 − far 步长 256 ⇒ 必须停在 AE_MIN（不得下溢）`。

## 13. ★★ 2026-09-27 结案：**暗场景拉不亮已解决**，且"停在 95"**不是 bug**

### 13.1 L4 实测数据（`lab4_ag111K`，SHA256 `8249B9B0`）

| 场景 | `G`（AG） | `L`（平均亮度） | `K`（过曝像素数） | 判定 |
|---|---|---|---|---|
| **暗场景**（AG 上限提到 111 后） | **`6F`=111** | **89** | **0**（另一张 46） | ✅ 一路加亮，无过曝 |
| **亮场景**（柜子/白墙/反光） | `6F`=111 | 55 | **`47A4`=18,340** | 高光保护**正好触在门限上** |
| 对照：AG 上限 89（旧版） | `59`=89 | 29~44 | 0 | 无余量可加 |

`CLIP_PCT` 默认 2% ⇒ 门限 = 921600×2% = **18432 = `0x04800`**。
亮场景读数 **18340 与 18432 只差 92（0.5%）**。

### 13.2 ★ 结论一：`AE_AG_MAX = 111` 采纳为默认

- 增益换算（查表实算）：AG=89→`0x0F29`→**20.5 倍**；AG=111→`0x0F3F`→**31.5 倍（+54%）**；
- 传感器**接受** `0x0F30~0x0F3F`（手动与自动都到过 111，画面正常）⇒
  `SC500GainTbl.v` 的补全表**有效**；
- 效果：暗场景 **L 从 29~44 提升到 89**（目标 112），**且无过曝、检测无误**。

### 13.3 ★★ 结论二：**更正 §12 的错误判断 —— "停在 95" 不是 bug**

§12 我曾推断"自动目标到 111、提交停在 95 ⇒ 握手死锁"。
§12.5 已因"`+` 是或条件、不能证明 AG 到顶"而作废该推断。
**现在给出真正的原因（有数据）：**

```
暗场景：K = 0 或 46  ⇒ w_clip_over = 0 ⇒ 不禁加亮 ⇒ 环路一路爬到 111 ⇒ L = 89
亮场景：K = 18340 ≈ 门限 18432 ⇒ w_clip_over 触发 ⇒ **禁止继续加亮** ⇒ 停在某个平衡点
```

⇒ **"停在 95" 是我的高光保护在正常工作**：画面里高光越多，它越早停；
暗场景里它不拦。**不是死锁，不是提交路径问题，没有任何 bug。**

**这是一次深刻的教训**：我在 §12 从一个**误读的诊断位**出发，
推出"一个子虚乌有的 bug"，还写进了报告。**中间只有一步是可靠的**
——即"再去测一个能判定的量"（§12.5.3 建议接 `clip`），
而正是这一步把我自己的错误推断推翻了。
⇒ **在证据不足时，正确的动作不是"再想想"，而是"再加一个能判定的观测量"。**
