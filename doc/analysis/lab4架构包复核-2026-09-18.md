## 2. 🔴 高：`I_button` 用的不是板载按键，新功能上板按不动

**这是本次复核发现的最严重问题。**

| 证据 | 内容 |
|---|---|
| `pin.adc`（lab4 复用 lab1） | `I_button[0] = N2`、`I_button[1] = J14` |
| `top_skeleton.sv:90` 注释 | `inout wire [1:0] I_button, // 按键，低有效 (N2 / J14)` |
| **`doc/analysis/_extract/DX_HX1P35B引脚分配汇总.txt` §十三「4组按键」** | **`KEY1=D5`、`KEY2=A9`、`KEY3=B9`、`KEY4=C7`** |
| 同表 §（DC3 扩展口） | **`N2`/`J14` 属 DC3 排针（GPIOA_19 / GPIOB_12），不是按键** |

**影响**：

- `N2`/`J14` 是**外扩排针**，板上没有按键接在上面。若悬空，靠 `PULLUP` 读到恒 `1`（释放态）——
  **短按永远不会发生 ⇒ `mode[1:0]` 永远是 `2'b00` ⇒ 边缘检测与 OSD 开关这两个本轮新增的核心演示功能，上板完全失效。**
- `key_mode_ctrl.v` 的去抖/长短按 FSM 本身没问题（我复核了，见 §5），**问题纯粹在引脚**。

**⇒ 行动项（必须做）**：把 `pin.adc` 改为 `KEY1/KEY2 = D5 / A9`。
**并且**：由于 `top_skeleton.sv` 声明"外部端口集合零变更"，改引脚**不违反**该约束（引脚位置不是端口集合），
但应在文档里明确记录这次改动。

> 依据来源：`doc/analysis/_extract/DX_HX1P35B引脚分配汇总.txt` 第 131-136 行。
> 这张表在既往分析里已被引用过（`增量分析与新思路` §3.1 与 `板卡资料解锁` §3 都写过 KEY1~4 = D5/A9/B9/C7），
> **但 lab4 的架构包没有继承这条修正。**

## 3. 🟡 中：`connection_matrix.md` §2.3 的地址单位说法与实测不符

**文档原文**：

> 帧缓存地址空间（4 缓冲，**16bit 半字单位**）
> | 0 | `25'd0` | …

**复核（第三轮已证实）**：`video_in` 每拍地址 `+8`，而一拍是 **128 bit = 16 B** ⇒ **地址单位 = 2 B**。
验证自洽性：`MC_ADDR_WIDTH 25 × 2 B = 64 MiB`，与器件容量精确相等 ✓。

**⇒ 应改为"2 字节单位"**（"16bit 半字"本身没错，但容易被读成"半字寻址"而与 +8/拍 的组合推错）。
建议直接写：**地址单位 = 2 B；每拍 +8 ⇒ 16 B/拍；帧槽 7,000,000 × 2 B = 14 MB**。

## 6. 与 P1a（AWB 重构）的关系：**兼容，但需补一道手续**

`module_partition.md` §2.3 把 `awb` 列入"**逐字节复用（零改动）**"。
而本会话此前定的 P1a 是**要重构 `awb`**（合并两个 `divider`，约省 750 LUT；乘法器分时 8→2 DSP）。

**两者不冲突**，原因：AWB 是 `isp_top` 内部模块，重构**不改任何外部接口**，
因此不动 `top_skeleton.sv` 的契约。但要补两件事：

1. **把 `awb` 从"零改动"移到"本轮修改模块"**，并登记为一条新的架构风险
   （参考实现 `32_cs500_mipi_hdmi` 的 `awb2.v` 用的是"整帧累加 + 帧末除法"，可对照）。
2. **P1a 的收益对 §5 资源预算有正贡献**（−750 LUT 量级），
   而 §5 目前的余量只有 27%（≈5800 slice）——**省下来的正好可以给后续扩展腾位置**。

> ⚠ 另一个顺序问题：`module_partition.md` §4 说"本轮刻意不新增任何 RAM/ROM"。
> 若将来要把 Logo 搬进 ERAM（第三轮的 P1b），会**新增 6 块 ERAM**（40 → 46/108）。
> ERAM 占用率仍只有 42.6%，**不违反"不新增 RAM"的初衷**（那条约束是为 slice 余量设的），
> 但**应在文档里显式豁免**，否则会与 §4 的字面表述冲突。

>
> **(A) `settings.cfg` 从未定义 `sp` ⇒ P&R 阶段从不重读 `pin.adc` 与 `.sdc`**
>
> `F:\al\scripts\DefaultFlow.tcl:80` 用 `if { [info exists sp] }` 作为"是否读 ADC/SDC"的开关。
> **四个 lab 的 `syn_1` 与 `phy_1` 的 `settings.cfg` 全都没有 `set sp`**（已逐一核对）。
> 后果：约束只在综合第一段读一次，此后全部来自网表内嵌的那一份；
> **P&R 阶段对 `.sdc` / `pin.adc` 的任何修改都不生效**。
> 实证：改了 `.sdc` 后重跑 P&R，WNS 分毫不变（仍 −111 ps），且 P&R 日志里完全没有 SDC 行。
> 修法：加 `set sp 1`（本次已加）。

> **(B) `.sdc` 把 `pll_clk_24m` 与 `HDMI_PIXEL_CLK` 归为同一同步组**
>
> 原厂模板第 16 行把两者放进**同一个** `-group`，即声明"互相同步"。lab1–lab3 无碍
> （没有逻辑跨这两域），lab4 新增的 `key_mode_ctrl` 才暴露出来：
> ```
> Path Group     : pll_clk_24m -> HDMI_PIXEL_CLK
> Slack          : -0.111 ns      (共 2 Viol Endpoints / 3 Total)
> Logic Level    : 0              ← 零级逻辑！
> Data Path Delay: 0.529 ns
> Budget         : 0.653 ns       ← STA 挑中了一对只差 0.653ns 的无关边沿
> ```
> **"逻辑级数 0 却违例"是"这是约束问题、不是逻辑太慢"的铁证。**
> 修法：`set_false_path -from [get_clocks {pll_clk_24m}] -to [get_clocks {HDMI_PIXEL_CLK}]`（最小范围，本次已加）。
> 效果：Setup WNS **−111 ps / 2 FEPs → +8 ps / 0 FEPs**。
