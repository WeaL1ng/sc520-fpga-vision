## 1. 现状逐行分析（`awb.v`）

### 1.1 数据流

```
I_tdata[95:0] (4 px RGB888) → 寄存 2 拍 → I_tdata_d0/_d1
                              │
        ┌─────────────────────┴──────────────────────┐
        │ 累加支路（求增益）                          │ 像素支路（应用增益）
        ▼                                            ▼
  rgb_sum  → sum_r/g/b[0]                     signal_delay（ERAM，50 拍）
  （仅通道 0）                                  → data_d0 / valid_d0
        │                                            │
        ▼                                            │
  2 × divider（48/32 位，PIPLE=50）                   │
  → in_r_x1 / in_b_x1 → in_r_r1 / in_b_r1（20 bit 增益）│
        └──────────────────┬─────────────────────────┘
                           ▼
              8 个 20×8 乘法器（R×4 + B×4）→ R_new_r1..r4 / B_new_r1..r4
                           ▼
                  O_tdata[95:0]（4 px RGB888）
```

### 1.2 确认的四个问题

| # | 问题 | 证据 | 收益 |
|---|---|---|---|
| **A** | ~~3 个累加器通道完全是死逻辑~~ | ~~`sum_r[1..3]`/`sum_g[1..3]`/`sum_b[1..3]` 被累加，但只有 `[0]` 被送到除法器~~ | ❌ **已实测为 0 收益**（综合器早已优化掉），见 §3.1 |
| **B** | **8 个乘法器是全并行直译** —— R/B 各 4 个，因为一拍有 4 像素 | `awb.v` L299–313 共 8 条 `in_r_r1 * rgb888_r_d1[n]` / `in_b_r1 * rgb888_b_d1[n]`；`phy.area` 报 8 DSP | ⭐ **8 → 2 DSP**（4 倍分时）**这是真收益** |
| **C** | **两个 `divider` 各占约 750 LUT** —— 合计 **1,523 LUT + 2,168 ripple + 5,487 FF**，占 `u_awb` 的 **87%** | `phy.area`：748 + 775 LUT | ⭐ **合并为 1 个**（顺序算 R 再算 B）**这是最大单点** |
| **D** | **定点标度可疑** —— 饱和判定写成 `R_new_r1[27:24]`（28 位的高 4 位），而取的是 `[23:16]`，中间 `[15:8]` 未用 | `awb.v` L337、L339 | 需核对语义（见 §4 风险 R1） |

### 1.3 为什么 8 个乘法器是浪费

像素率的实测事实（第三轮 §1.3）：

```
ISP 结构吞吐上限        : 1 个 4-pixel beat / 2.5 拍
720p60 实际负载         : 55.3 Mpix/s → 13.8 M beat/s → 0.23 beat/clk (@59.995 MHz)
每 beat 平均可用拍数     : 1 / 0.23 ≈ 4.3 拍
```

⇒ **每个 4-pixel beat 平均有 4.3 拍可用**，而 8 个乘法完全可以在 **4 拍内用 2 个乘法器**算完（每拍算 1 个 R + 1 个 B）。
**⇒ 这正是"用时间换面积"的标准场景，且余量足够。**

## 2. 重构方案

### 2.1 目标结构

```
I_tdata[95:0] ──┬─→ 增益累加（只留 1 组 sum_r/g/b）→ 1 × divider（复用，先算 R 再算 B）
                │                                       │
                │                                       ▼
                │                              gain_r / gain_b（帧内恒定）
                │                                       │
                └─→ 像素缓冲（保持原有 signal_delay 对齐）│
                            │                           │
                            ▼                           ▼
                  分时复用 2 个乘法器（4 拍算完 4 个像素的 R 与 B）
                            ▼
                  O_tdata[95:0]（4 px RGB888，格式不变）
```

### 2.2 关键设计决定：**必须保持"4 像素/输出字"的格式不变**

**这是本设计最重要的一条约束，也是我暂停改 RTL 的直接原因。**

`awb` 的下游是 `data_96bit_to_128bit`（`isp/data96_128/data96_128.v`），它是一个
**4:3 装箱器**：每 4 个输入 beat 产出 3 个输出 beat，内部用 `S_cnt` 0…3 对 96 bit 字做**跨字拼接**：

```verilog
'd1: O_128b_data <= {S_96b_data_1d,        I_96b_data[95:64]};
'd2: O_128b_data <= {S_96b_data_1d[63:0],  I_96b_data[95:32]};
'd3: O_128b_data <= {S_96b_data_1d[31:0],  I_96b_data      };
```

⇒ **它假设每个输入 beat 都是"4 个像素 = 96 bit"。**

**因此：分时复用乘法器之后，仍然必须把 4 个乘积攒回同一个 96 bit 字输出，不能改成"每拍 1 像素"。**
否则 `data_96bit_to_128bit` 的 `S_cnt` 节拍与像素数不再对应，DDR 行突发（240 beat = 一整行）会错位。

### 2.3 分时状态机（4 拍一拍字）

```
// 输入侧：收到一个 valid 字后，锁存并进入 4 拍处理
reg [1:0] ph;                  // 0..3
reg [95:0] word_r;             // 锁存的输入字（已在 signal_delay 对齐后）
reg [7:0]  prod_r [0:3], prod_b [0:3];

always @(posedge I_clk) if (valid_d1) begin
    word_r <= data_d1; ph <= 2'd0; busy <= 1'b1;
end else if (busy) begin
    // 1 个乘法器算 R，1 个算 B，同拍处理第 ph 个像素
    prod_r[ph] <= gain_r * word_r[ph*24 +: 8];      // 真乘法：DSP #1
    prod_b[ph] <= gain_b * word_r[ph*24 +: 8];      // 真乘法：DSP #2
    if (ph == 2'd3) begin busy <= 1'b0; out_valid <= 1'b1; end
    ph <= ph + 2'd1;
end
```

**代价**：输出相对输入多 **约 4 拍**延迟。
**但因为 `signal_delay` 已经是 50 拍、且帧率远低于像素率，这 4 拍可以用"整体加深 4 拍"吸收**——
注意 `I_tuser`/`O_tlast` 的对齐也要同步加 4 拍（见 §4 风险 R3）。

### 2.4 预期收益（待 P&R 实测，**不要预设面积数字**）

| 指标 | 改前（lab3 实测） | 目标 |
|---|---|---|
| DSP | **8** | **2**（省 6） |
| `u_awb` LUT | 1,752 | 待实测（累加器 −3/4、除法器 −1） |
| `u_awb` ripple | 2,292 | 待实测 |
| lab2 最紧路径 slack | 1.451 ns | **≥ 3 ns**（打断 14 级 ADDER 链） |
| 4 个域门禁 | — | 见 §6 |

## 4. 风险清单（必须先想清楚）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| **R1** | **定点语义未确认** | `in_r_r1` 初值 `20'h10000`（=1.0 若为 16.16 定点），但输出取 `R_new[23:16]`，而 `R_new` 是 28 位。若 `in_r=1.0` 且 `R=255`，则 `R_new` 应 ≈255 → 说明 `in_r` 实际是 8.12 或类似标度。**重构前必须先把标度关系用仿真或数值推导确认**，否则会改出颜色错误 | 写一个最小 testbench，用已知 RGB 值验证改前改后输出**逐位一致** |
| **R2** | **除法器输出时序** | `divider` 的 `done` 在 `start` 后约 `PIPLE=50` 拍。当前 `.start(I_tvalid_r1)` 每个 valid 拍都重触发，`done` 会周期性到达。改成"每帧一次"后，`done` 只在帧末来一次——**要确认增益在下一帧开始前已稳定** | 帧消隐期有数千拍，余量充足；但需确认 `sum` 的复位点在 `I_tuser`（帧首），增益在帧末可用 |
| **R3** | **流水线深度 +4 拍需全链对齐** | `O_tlast = (valid_d1==0) && (valid_d2==1)`、`O_tuser = I_tuser`（**直接透传，未延迟！**）。改动后这两个信号的语义必须重新核对 | 对齐验收方法：自检模式下叠 1 像素棋盘，确认无水平/垂直偏移 |
| **R4** | **间隙吞吐** | 若上游 ISP 在某段真的连续满速（行有效窗口内峰值 0.29~0.4 beat/clk），4 拍/字的分时**不够**（需 2.5 拍/字） | **先用 2 个 DSP、2 拍/字**（每拍算 2 个 R + 2 个 B）⇒ 正好满足 2.5 拍上限，且仍省 4 个 DSP。**这是更稳的选择** |
| **R5** | **`I_tready`/`O_tready` 是直通** | `assign I_tready = O_tready;` —— 反压直接透传，但上游 `isp_top` 的 `tready` **本来就是悬空的**（第三轮 §9 已记录：`isp_top` 端口方向写反、`S_ISP_O_tready` 未驱动）。⇒ **AWB 实际上无反压能力**，不能靠 tready 减速 | 分时必须在"像素间隙"里完成，不能指望反压 |

> **⚠ R4 改变了首选方案**：考虑到行有效窗口内峰值可能到 0.4 beat/clk（即 2.5 拍/beat），
> **"4 拍/字"有丢数据风险**；**"2 拍/字（2 DSP，每拍 2 个 R + 2 个 B）"才与结构上限匹配**。
> **⇒ 推荐 2 DSP 方案（省 6 → 4 个 DSP 的保守版是 4 DSP / 2 拍）。**
> 最终取哪一档，取决于 §5 的实测。

## 5. 必须先确认的一件事（这就是暂停点）

**`video_in` 的 510 深 FIFO 能吸收多少背压，决定了 AWB 能否安全降到"2 拍/字"。**

事实（第三轮 §3.2）：

```verilog
// video_in.v:140（RTL 注释原文）
// fifo的深度是512，实际的深度是510，因此需要注意每次读出的长度避免是256，
// 否则连续两次读写会引起fifo读空，丢失数据
// video_in.v:148
else if(S_fifo_rd_num >= 'd240 && (!I_video_out_rd_busy) && (!S_fifo_rst))
```

⇒ 写通道是**"攒够 ≥240 个 128-bit 字（=960 像素）才向 DDR 突发"**。
**如果 AWB 把 ISP 输出率压低，这个 FIFO 会被填满/填不满，表现为撕裂或丢行，而不是优雅降速。**

**因此步骤 2 之前需要一个"量化输入间隙"的实测**：
数出 `I_tvalid_r1` 在**连续 N 个行有效窗口**内的最长连续有效拍数。
- 若最长连续 < 2 拍 ⇒ 2 拍/字安全
- 若最长连续 ≥ 3 拍 ⇒ 只能用 4 拍/字，或改用"4 DSP / 1 拍"折中

**实现方式（半天）**：在现有 lab3 里加一个只有计数器的调试模块，
统计 `I_tvalid` 的最长连续 run-length，通过原有 `S_hdmi_debug_status` 或 UART 读出。
**这一步不需要动 AWB，风险为零。**
