> ### ① ❌ F1「Logo 实测吃掉约 2,495 个 LUT6」—— **该数字 TD 从未报出过**
>
> 2,495 是**用位密度反推的估算**（`6,387 × 25 bit ÷ 64`），本报告却写成了"实测"，
> 并据此在 §2.2/§6/§7/§8 层层推出"面积几乎全由 Logo 贡献"的结论。
>
> **TD 报告的真实口径**（逐份核对过）：
>
> | 报告 / 阶段 | `u_anlogic_logo_rom` | `u_hdmi_mixer` 整模块 |
> |---|---|---|
> | `syn_1/*_rtl.area`（RTL 级） | **38,479 个 `gate`**（**注意不是 LUT**；该报告全设计 `#Total_luts` 仅 **4,530**） | 38,802 gate |
> | `syn_1/*_gate.area`（gate 级） | **不在层级表中（已被吸收）** | **2,313 LUT** |
> | `phy_1/*_phy.area`（布线后，官方） | **54 LUT** | **2,572 LUT** |
>
> ⇒ **"6,387 项 → 2,495 LUT"这个换算不成立**：把 gate 数、位密度估算和最终 LUT 数混为一谈了，
> 而 gate 级该模块**已经被综合器吸收掉**，无法单独计量。
>
> **唯一可信的口径是 lab 之间的差分**：`u_hdmi_mixer` **46 LUT(lab1) → 2,572 LUT(lab3) = +2,526**；
> 其中 `u_anlogic_logo_rom` 单列只有 **54 LUT**。
> ⇒ **这 2,526 LUT 里，多少属于 Logo 位图、多少属于 `hdmi_mixer.v` 里的手写点阵字库
> （`F_logo_text_bits`/`F_hex7seg`/`F_cn16_row`/`F_dyn_char_bits`/`F_osd_char16_row` + `osd_char_lib`）、
> 多少属于像素率路径上的常量除法（`/24`、`/15`、`/8`），TD 的报告分不出来。**
>
> ### ② ⚠ F2「面积和时序的恶化 **98%** 来自这张 Logo」—— **比例无依据**
>
> F2 用的是同一个 2,495，所以"98%"同样不成立。
> **可靠的只有**：Sobel 很便宜（`edge_detect_96` = **286 LUT + 68 ripple + 155 FF**，lab1→lab2 仅 +568 slices）；

> **"贵在哪一部分"需要自己动手拆，不能引用本报告的 98%。**
>
> ### ③ ✅ 但「把 Logo 搬进 ERAM」**仍然应该做**，且价值更高 —— 理由换成**时序**
>
> Logo 通路是 `always @(*)` 纯组合：`坐标 → 常量乘 160（占 1 个 DSP）→ 16K 稀疏 LUT → 命中判决 → O_hdmi_data 选择器`，

> 延迟 14.565 ns vs 预算 13.333 ns、**扇出 522**。**
> ⇒ **搬进 ERAM（同步读、输出寄存）是唯一能真正砍断这条组合链的改法。**
>
> **收益的正确表述**：主收益是 **时序**（`HDMI_PIXEL_CLK` → ≥1.5 ns）；
> 确定的附带收益是 **DSP 9→8** 与 **ERAM +6**；**面积收益待 P&R 实测，不要预设数字。**

### 0.5 勘误与增补（基于并行检索代理提出的两个关键问题，已用 RTL 逐行核实）

#### 勘误 C1：**片内集成 512 Mbit (64 MB) DDR2；但实测跑 DDR2-533，不是 DDR2-1066**（🚨 第三轮更正）

> **本节原稿有两处错，已在第三轮核实并更正**（见 `核验与纠偏-2026-09-18第三轮.md` §N-a）。
> 原稿正确的一半：**片内集成、x16、512 Mbit = 64 MB、CL=7/CWL=6、用户口 128 bit @ 66.667 MHz = 1,066.7 MB/s**。
> 原稿错的一半：**速率等级**与**引脚峰值带宽**。

| 项目 | 实测值 | 证据 |
|---|---|---|
| DDR 类型 | **`PH1P_DDR_TYPE = Integrated`（片内集成）** | `.params_ddr2.txt` |
| IP **配置**的速率等级 | `DDR2-1066`（`PH1P_SPEED_BIN`、`PH1P_DDR_SPEED : 1066.00`、`tCK : 1876`） | `.params_ddr2.txt` |
| 🚨 **实际运行频率** | **CK = 266.667 MHz**（tCK = **3750 ps**），双沿 = **533 Mbps/pin** ⇒ **DDR2-533** | `final_timing.rpt` 的 `ddr_clk` = 266.667 MHz；由分频反算见下 |
| 时序参数 | CL = 7，CWL = 6 | `.m_params_ddr2.txt` |
| 位宽 | **x16**（DQ_WIDTH 16，DQS 2，DM 2） | `.params_ddr2.txt` |
| 容量 | **512 Mbit = 64 MB**（BK 4 × ROW 2^13 × COL 2^10 × 16 bit） | `BK_NUM=2`(→4 banks)、`ROW_WIDTH=13`、`COL_WIDTH=10`、`DQ_WIDTH=16` |
| 控制器用户口 | **128 bit @ 66.667 MHz = 1,066.7 MB/s** | `MC_DATA_WIDTH=128`、`MC_ADDR_WIDTH=25`、`usr_clk 66.667` |
| **引脚峰值带宽** | 266.667 MHz × 2 × 16 bit = **8.53 Gbit/s = 1,066.7 MB/s** | 由上推算 |

**🚨 为什么实际是 DDR2-533 —— IP 配置与硬件接法不一致：**

```
IP 参数要求参考时钟 100 MHz：  PH1P_REF_CLK : 100.0000 ; PLL0_REFCLK_FREQ : 100.0
但 wrapper 实际接的是 50 MHz：  ph1p35_324_ddr_wrapper.v:79  .ref_clk ( I_sys_clk )   ← I_sys_clk = 50 MHz
IP 自己的分频：                REFCLK_DIV=3 → FBKCLK_DIV=32 → CLK2_DIV=2 → CLK3_DIV=21
⇒ VCO = 50 ÷ 3 × 32 = 533.33 MHz
⇒ ddr_clk = 533.33 / 2  = 266.667 MHz   ✓ 与 final_timing.rpt 完全一致
⇒ mcu_clk = 533.33 / 21 =  25.397 MHz   ✓ 同上
```
⇒ **参考时钟只有配置值的一半，所有输出频率随之减半。** 这也是设计**自洽**的原因：
`usr_clk 66.667 MHz × 128 bit = 1,066.7 MB/s` = `266.67 MHz × 2 × 16 bit` —— **两侧刚好相等**。

**结论（替换原稿的结论）**：
- ❌ **原稿"引脚峰值 2,133 MB/s"作废**（那是按配置值 533.3 MHz 算的，实际只跑到一半）。
- ⭐ **正确值：引脚峰值 = 用户口 = 1,066.7 MB/s，1:1，没有任何余量差。**
- 基线流量 387 MB/s = **36.3%**（引脚与用户口同为一个分母）。
- **⇒ 重要推论（方向不变，但理由更强）**：既然引脚与用户口相等，**瓶颈从"用户口仅是引脚的一半"变成了"整个存储子系统只有 1,066.7 MB/s 这一次上限"**。
  帧差法加读一份会到 **51.9%**（重算值，原稿写 57%）。
  真正的风险**不在总带宽，在仲裁**：① 单端口**写优先**硬仲裁（`design_top_wrapper.v:627-630`）；
  ② 读写侧有**双向互锁 busy**（写让读、读让写）⇒ 极端拥塞下可能变成**互锁活锁**而非饿死。
  这与 §6.3-G"零额外带宽"方案的推荐一致，也**抬高了第三轮"新思路 E（区域快门）"的价值**——它正是区分这两种失败模式的实验。
- ✅ **地址单位与容量：原稿这一段是对的，已复核。** `video_in` 每拍地址 `+8`、一拍 128 bit = 16 B ⇒ **地址单位 = 2 B**；
  25 bit × 2 B = **64 MiB**，与器件容量精确自洽；帧槽 `7,000,000 × 2 B = 14 MB`/槽，4 槽 = **56 MB < 64 MB** ✓。
- `ph1p_ddrphy_board_delay.vh` 中 `AC0_BD = DX0_BD = 110 ps`（其余 0）→ 有真实物理走线延迟，
  说明"Integrated"指的是**集成控制器/PHY + 短距封装内/板上 DRAM**，不是"全在片内无引脚"。

#### 勘误 C2：ISP 像素域的时间复用余量是 **2×**，不是 4×

检索代理的疑问：720p60 只要 55.3 Mpix/s（含消隐 74.25 Mpix/s），而"4 px/拍"是否意味着 4 倍时间复用余量？**逐行核实 `raw10_unpacket_2lane.v` 后的准确答案如下：**

```
D-PHY 输出        : 16 bit @ 59.995 MHz (= 960 Mbps = 2 lane × 480 Mbps)   ← 链路满速
csi_unpacket_2lane: 合并成 32 bit，valid 每 2 拍来一次（源码用 3'b101 检测）
raw10_unpacket    : 5 个 valid 拍为一个循环，其中 4 拍各产出 1 个 40 bit(4 px) 字，
                    第 5 拍不产出 (S_cnt==3'd4 → S_raw10_wr_en <= 0)
   ⇒ 结构极限 = 16 px / 10 拍 = 1 个 4-pixel beat / 2.5 拍
```
- **结构性上限**：**1 beat / 2.5 clocks**（由"40 bit 像素 / 16 bit 每拍"决定，**与 lane 速率无关**，是几何常数）
- **传感器实际负载**：1280×720×60 = **55.3 Mpix/s** → 13.8 M beats/s → **平均 0.23 beat/clk**
- 若传感器只在行有效窗口内连续发送（HTS 1600 / 有效 1280 → 窗口占 80%），峰值约 **0.29–0.4 beat/clk**
- **⇒ 安全的时间复用倍数是 2×（每 beat 用 2 拍），不是 4×。** 4 拍/beat 只有 0.25 beat/clk 的处理能力，在行有效窗口内会**跟不上而丢数据**。

#### 增补 L1（本次分析新增的最大架构杠杆）：**启用 PLL 上闲置的 C2/C3 输出，建一个"快速算法域"，拿到约 9× 的计算复用**

- `ip_source/PLL/PLL.v` 的 VCO = **1,500 MHz**，输出 = 1500 / N。当前只用了 C0(÷15=100 MHz)、C1(÷63=23.81 MHz)、C4(÷20=75 MHz)、C5(÷4=375 MHz)；**`clk2_en`、`clk3_en`、`clk6_en` 全部接 0（未使用）**。
- 只需在 PLL IP 里打开 **C2（÷10 = 150 MHz）** 或 **C3（÷12 = 125 MHz）**，**不需要多占一个 PLL**（PLL 占用仍为 3/6）。
- 在 125 MHz 域中，13.8 M beats/s 只占 **0.11 beat/clk ⇒ 每个 beat 有约 9 拍可用**；在 150 MHz 域约 10.9 拍。
- **用法**：把重算子（5×5 双边滤波、连通域标记、帧差、形态学、直方图）做成**单个共享硬件实例 + 输入/输出弹性 FIFO（CDC）**，在该域里分时复用 4~8 次。
- **等价效果**：这些算子的 LUT/DSP 成本可近似**除以 4~8**。这是全项目最大的架构杠杆。
- **风险与建议**：当前设计的 slices 已 70%，125–150 MHz 是否可达**必须实测**。建议**先做 100 MHz（÷15，可复用 C0 那一路的配置经验）→ 验证 → 再上 125 MHz**；任何情况下都要先跑一次"仅加时钟域 + FIFO"的空转 P&R 来测 Fmax。

#### 增补 L2：DSP 是真正稀缺的资源，**常量乘法绝不能用 DSP**

- 器件只有 **40 个 DSP**（已用 9 个，空闲 31 个），但 4 px/拍 × 3 通道 = **一级就 12 个乘法器**；两级可变系数乘法链就吃掉 24/40 = 60%。
- **规则**：
  - **可变系数乘法**（AWB 增益、投影加权）才用 DSP，并且尽量靠时间复用降到 3~4 个实例；
  - **常量系数乘法**（3×3/5×5 卷积核、量化、色彩矩阵）一律用 **CSD（正则有符号数字）移位-加法** 在 fabric 里做——一个 8 bit × 常量通常只要 1~3 个 LUT6；
  - 滤波器的对称系数可以先"配对相加再乘"，把乘法次数再减半。
- 反例警示：官方 OSD 里 `S_logo_y * LOGO_W` 这个**常量为 160 的乘法**居然占用了 1 个 DSP（lab3 比 lab1 多 1 个 DSP），完全可以用 `y*128 + y*32` 两次移位加法实现。

### 2.4 评分标准的准确理解（题面 2.6 —— 这是最容易误读的一节）

原文要点：
- 基础扩展项与高阶挑战项**均不设单项固定分值**，按**技术难度**和**完成质量**综合评分。
- "完成相同数量扩展要求的情况下，高阶挑战项可获得更高分数。"
- "**稳定完成 1 项扩展功能可获得一定分值；完成 2 项且效果良好，可获得扩展部分一半以上的分值；完成多项高阶挑战且系统运行稳定、展示效果突出，可获得较高分；整体完成度高、创新性强者可获得满分或接近满分。**"
- 基础要求独立 4 条评分，其中 **(4) 明确写了"系统稳定性：系统长期运行无花屏、无缓存溢出，光线剧烈变化时工作正常"**。

> **战术含义**：
> 1. **"稳定"是显式得分维度**——"光线剧烈变化时工作正常"直接指向 **AE/AGC 必须真的工作**（这正好是进阶要求 5，一箭双雕）。
> 2. 分值随"数量 × 难度 × 展示效果"递增，**不随资源占用递减**，但 slide 26 又说"不依据资源大小评分，推荐以优化的逻辑和最低的功耗来实现"——所以**"资源优化"要作为叙述亮点讲，而不能作为得分目标去牺牲稳定性**。
> 3. 想拿高分必须"**整合为一个镜像**"+"**上电即跑**"+"**现场演示效果突出**"。

### 3.4 DDR 带宽预算（已按 §0.5-C1 勘误修正）

**容量/物理（实测自 DDR IP 参数文件）**

- 控制器用户口：**128 bit @ 66.667 MHz = 8.53 Gbit/s = 1,066.7 MB/s**（仅引脚带宽的 50%，**这才是约束我们的口径**）

### 3.5 三个"隐藏事实"（决定后续所有设计自由度）

**H1. ISP 像素域的时间复用余量是 2×（不是 4×），但可以用 PLL 闲置输出换取 ~9×**
- D-PHY 输入能力：16 bit @ 59.995 MHz = 960 Mbps = 96 Mpix/s（RAW10）
- `raw10_unpacket_2lane` 的结构极限：**1 个 4-pixel / 40-bit beat 每 2.5 拍**（与 lane 速率无关的几何常数）
- 传感器实际负载：1280×720×60 = 55.3 Mpix/s → **平均 0.23 beat/clk**；行有效窗口内峰值约 0.29~0.4 beat/clk
- **⇒ 在 60 MHz 的 ISP 域里，每 beat 安全可用 2 拍（2× 复用）；用 4 拍会在行有效窗口内跟不上。**
- **⇒ 真正的杠杆是增补 L1**：打开 PLL 闲置的 C2/C3 得到 125~150 MHz 的"算法域"，用弹性 FIFO 跨域，**每 beat 可用约 9~11 拍**，重算子成本近似除以 4~8，且**不额外占用 PLL**。
- 同时注意 **增补 L2**：40 个 DSP 是稀缺资源，常量系数乘法一律走 CSD 移位-加法。
- 域内 Fmax 实测（lab3）：MIPI 域 113.6 MHz — 说明"简单逻辑"能跑到 113 MHz，但 125/150 MHz 必须实测验证。

**H2. 面积真正紧的是 slices 和 LUT6；ERAM / FF / DSP / PLL 都很宽裕**

| 资源 | lab3 占用 | **空闲** | 适合放什么 |
|---|---|---|---|
| slice reg (FF) | 31.53% | **68%** | 流水线打拍几乎免费 |
| ERAM | 40/108 | **68 块** | 字模 ROM、文本缓冲、缩略帧、直方图、行缓冲 |
| DSP | 9/40 | **31 个** | 乘法务必交 DSP |
| PLL | 3/6 | **3 个** | 新增时钟域（如精确 24 MHz MCLK、74.25 MHz 像素钟） |
| LUTRAM | 408/… | 大量 | 小 FIFO、窗口延迟链 |

**H3. OSD 的"面积怪象"根因被定位并可精确修复**
- 综合器把 `anlogic_logo_rom` 的稀疏 `case`（**6,387 个非零项 × 25 bit**）映射成**纯组合**逻辑，因为它是 `always @(*)` 的 `case`，没有任何 RAM 推断提示。**这一点确定成立**，也是它压死 HDMI 域时序的原因。
- 🚨 **但"159,675 bit ÷ 64 ≈ 2,495 LUT、与实测 2,526 LUT 吻合度 98.8%"是巧合，不能作证据。**
  64 bit/LUT6 是"一个 LUT6 当 64 bit 存储"的理想值，而综合器对该稀疏表的实际映射方式不同；
  TD 的实测值是：RTL 级 **38,479 个 gate**、gate 级**被吸收**、布线后该模块单列 **54 LUT**。
  **⇒ 面积收益必须 P&R 实测，不要用位密度估算。**
- 改成 ERAM ROM 的容量算术（**这部分是可靠的**）：13724 × 8 bit = 109,792 bit ÷ 20,480 bit/块 ≈ **6 块 ERAM**（`tools/gen_logo_mif.py` 已按裁剪包围盒 + 8 bit 调色板算过）。
- 更优：保留无损则用 10 bit 索引（579 色）→ 约 9 块 ERAM。ERAM 结构注意：**1 slice = 2 × ERAM20K + 1 个 FIFO 控制器，ERAM20K 固定 20 Kbit**；且**地址与数据输入必须与时钟同步**，否则工具不做时序分析、内容可能随机翻转。

### 3.6 摄像头配置链（从代码反推的权威信息）

- **I2C 从地址 = `8'h6c`**（7 bit 即 0x36）
- 参考钟 23.8095 MHz，I2C 速率 = 23.81 MHz / 240 ≈ 99 kHz（`CLK_DIV = 24000000/100000-1`）
- **720p60 寄存器表共 116 项**（`uics500reg_720p60.v`，另附 1080p30 表 `uics500reg_1080p30.v`）：
  - `0x3208=0x05 / 0x3209=0x00` → 宽 1280；`0x320a=0x02 / 0x320b=0xd0` → 高 720
  - `0x320c/0x320d = 0x0640` → HTS 1600；`0x320e/0x320f = 0x03e8` → VTS 1000
  - `0x3220 = 0x01` → **传感器内部开启 VBIN + HSUB**（垂直 binning + 水平子采样），直接输出 720p
  - `0x4837 = 0x42` → 注释标为 **480 Mbps/lane**
  - `0x0100 = 0x01` → stream on；stream on 后延时 240,000 个 24 MHz 周期 ≈ **10 ms**
- **曝光/增益寄存器映射**（`uics500regAE.v`）：16 bit 曝光 `AE` 拆成 `0x3e00={4'h0,AE[15:12]}`、`0x3e01=AE[11:4]`、`0x3e02={AE[3:0],4'h0}`；增益 `AG` → `0x3e08=AG[15:8]`、`0x3e09=AG[7:0]`
- **增益码表**（`SC500GainTbl.v`，输入 = AG−16，范围 0~73）分三段：`0x0320~0x033F`、`0x0720~0x073F`、`0x0F20~0x0F3F`（每段 16 档细调）；默认 `AG=80 → 0x0F20`
- **AE/AG 默认值：AE=3000、AG=80**；按键范围：**AE 2~2246，AG 16~89**
- **按键行为**：`I_button[1:0]`（顶层接 `{I_button, 2'b11}`）→ 低有效；btn0 减 AE，btn1 加 AE；**没有 AG 按键**（btn2/3 被拉死）
  → 即**"按键调节曝光"是纯手动 AE，不是自动曝光**。**进阶要求 5 的"自动曝光"完全没有实现。**

## 6. 方案思路与建议

### 6.1 总体策略

**核心判断：不要新增"另一套完整引擎"，而是"把一条链路的资源腾出来，再挂上去。"**

三步走：
1. **第一步（必修，纯赚）**：把 Logo 位图从 `case` 搬进 ERAM，顺带把 `hdmi_mixer` 的 OSD 逻辑流水线化。目标：**slices ≤ 60%、HDMI 域余量 ≥ 1 ns、DDR 域余量 ≥ 1.5 ns。** 这一步不减少任何功能。
2. **第二步（拿分主力）**：在腾出的空间里挂上"卡通化 + 颜色目标检测 + 延迟可视化 + 运动检测 + FPGA 内自动曝光 + 多算法切换 + 动态 OSD 文本"。
3. **第三步（工程化）**：把 `isp_top` 里除 demosaic/AWB 之外的算法通路统一成一个**共享行缓冲 + 算法槽（MUX）**，真正做到"一套窗口引擎服务所有算法"，并用 shadow 寄存器实现无撕裂切换。

### 6.3 关键技术方案详述

#### A. Logo/位图 ROM 搬进 ERAM（P0，最高杠杆）

**问题**：`anlogic_logo_rom.v` 是 `always @(*) case(I_addr)` 的稀疏表（6,387 项 × 25 bit），综合器把它铺成**纯组合**逻辑，落在只剩 0.103 ns 的 HDMI 域 —— **这才是必须先修它的理由**。
（原写"≈ 2,495 LUT6"是位密度估算，**不是实测**，见顶部核验块。）

**做法（三选一，推荐第 2 个）**
1. 用 TD 的 **Block Memory Generator IP** 生成一个 15 bit 地址 × 25 bit 数据、**初始化文件 `.mif`** 的 ROM。流程项目里已有先例（`blk_mem_gen_demosaic`、`blk_mem_gen_zhenghe`、`config_data.mif`）。
2. **推荐（已由 `tools/gen_logo_mif.py` 实现）**：**裁剪包围盒 + 8 bit 调色板索引** → 深度 13,724 × 8 bit = 109,792 bit ≈ **6 块 ERAM**，再配一个 255 色调色板（≈96 LUT）。好处：① 占用最小；② 颜色可**运行时改写**（换主题色、做渐变/淡入淡出）；③ 便于把 Logo 换成任意位图。若要求无损用 `--bits 10`（579 色全保留，约 9 块 ERAM）。
3. 不裁剪、保留完整 160×160：160×160×8 = 204,800 bit ≈ **10 块 ERAM**（比方案 2 多 4 块，没必要）。

> ⚠ **ERAM 硬性约束**：地址与数据输入**必须与时钟同步**，否则工具不做这些路径的时序分析、**内容可能随机翻转**。
> ⇒ ROM 的 Output Register **必须选 OUTREG（同步读）**，不能选 NOREG。

**流水线改造（与上面同时做）**
```
行基址寄存器：每行 hsync 更新一次 row_base = y * ROW_STRIDE（或用 1 个 DSP 做一次乘法，每行只算一次）
逐像素：     addr = row_base + S_logo_x   ← 一次加法
             → ERAM 读（同步读，天然打一拍）
             → OSD 命中判决打一拍
             → 输出选择打一拍
```
- 消掉像素率路径上的乘法器与 **扇出 95 的加法器网络**
- 消掉 4 处 `case(S_pf_col)` 的 16 路重复译码（可合并为一个 4→1 的位选择，或用一个小 ERAM 存字模行数据）
- `/10'd24`、`/10'd15`、`/10'd8` 改成**预计算查表**（局部坐标只有 24 / 15 / 8 个取值，用 LUTRAM 存商）

**预期收益**：slices 70.00% → **≈58%**；HDMI 域余量 0.103 ns → **预计 ≥2 ns**；DDR 域余量随拥塞缓解回升（建议实测）。

#### B. 动态 OSD 文本子系统（P0，公共底座）

官方 OSD 只能用硬编码 `function` 字模，**无法显示动态数值**。所有"显示算法名/坐标/延迟 ms/目标数量/帧率"的需求都依赖它。

```
① 字模 ROM（ERAM，8×16 或 16×16，96 个 ASCII + 若干汉字）
   - 汉字"安路"可继续用现有 16×16 字形
   - 用 IP 生成 + .mif 初始化（不要用 case！见 A）
② 文本缓冲 RAM（如 40 列 × 16 行 × 8 bit = 5,120 bit，1 块 ERAM 或 LUTRAM）
   - 由 FPGA 状态机 / 板载 MCU / UART 写入
   - 写口与显示读口分离（简单双口）
③ 渲染器（纯流水线）
   x,y → (col,row) → 字模地址 → 行位图 → 位选择 → alpha
   全部按拍寄存，禁止在像素率路径上出现乘除
④ 半透明：out = osd*a + video*(1-a)，a 取 1/4、1/2、3/4 用移位+加法实现
```

**代价**：≈250 LUT + 2~4 ERAM（对照：现在的硬编码方案已花 2,526 LUT 且不可扩展）

#### D. 延迟可视化（P1）

```
采集域：MIPI_RX_BYTE_CLK 下维护 ms 计数器（或 sys_clk_50m 计数 × 20us 刻度）
        在 tuser（帧首）把计数器值锁存进一个"帧标签 FIFO"（深度 = 4~8，对应帧缓冲数）

        延迟 = 当前 ms 计数 − 帧标签（注意 mm 计数器跨域要格雷码或双触发器同步）

**要点**：计数器必须**单调递增且位宽足够**（32 bit @ 1 ms = 49 天，够用）；跨域读要用握手/格雷码，不要直接多 bit 打拍。

#### E. 卡通化（P1，对应扩展要求 1）

官方原话：*"实现视频图像风格化处理或视觉增强功能，如边缘提取与区域填充（卡通化处理）等"*；PPT slide 20 给的建议链路是 `MIPI → RAW10 解包 → ISP 基础处理 → 边缘检测 → 区域填充/颜色量化 → DDR2 → HDMI`。

**推荐实现（在 ISP 域，96 bit = 4 px/拍）**
```
① 灰度化（已有）：gray = R/4 + G/2 + B/4   ← edge_detect_96.v 里现成的 8 bit 无溢出写法
② Sobel 梯度幅值（|Gx|+|Gy|，无开方）—— 可复用/改写 edge_detect_96 的 3×3 窗口与行缓冲
③ 颜色量化：R' = (R>>4)<<4 + 8（16 级），G'、B' 同理 → 产生"色块"效果，只要移位
④ 区域填充：不做真连通域，用"量化色 + 边缘覆盖"即得到卡通观感
   若要做更好的区域平滑：3×3 中值或 (5×5 盒式均值) 后再量化（多周期加速器，见 H1）
⑤ 边缘叠加：edge ? 黑 : 量化色
```
**代价**：边缘通路 ≈ 300 LUT（Sobel 实测只要 286 LUT，参考！）+ 量化 100 LUT + 一个 3×3 行缓冲复用（0 新增，若与 Sobel 共用）。**总计 ≈ 600 LUT + 复用行缓冲。**

> ⚠ 注意红线：如果直接复用 `edge_detect_96.v`，边缘检测部分与例程"相同"。建议：(a) 把边缘检测改为 **Prewitt / Scharr / 形态学梯度（膨胀−腐蚀）** 中的一种，(b) 或者把 Sobel 保留为"模式之一"，**主展示模式用形态学梯度或 Laplacian**。

#### F. 颜色目标检测 + 包围框（P1，一次覆盖扩展(2) + 高阶(2)）

**不要做完整连通域标记（two-pass union-find 在 720p 上很贵）。用投影统计**：

```
① 颜色分割（每拍 4 像素并行）：对目标色做 YCbCr 或归一化 RGB 判决
   - 用 YCbCr 更稳：Y = (77R+150G+29B)>>8, Cb = ..., Cr = ...
   - 阈值判决 → 4 bit 目标掩码/拍
   - 建议同时支持 2~3 类颜色（橙/红/蓝），用 2 bit 类别标签
② 行投影：每行统计掩码为 1 的像素数 + 最左/最右 x → 得到该行的 [xmin,xmax,count]
③ 帧级累积（行缓冲不参与）：
   - 逐行更新全局 xmin/xmax/ymin/ymax（用寄存器，每行一次）
   - 每行把 xmin/xmax 与全局合并 → 得到包围框
④ 更稳的做法：把画面分成 N×M 个 tile（如 16×9），每 tile 统计命中数 → 得到"目标热力图"
   - tile 级统计资源极小（16×9 = 144 个计数器），抗噪好，天然给出"多目标"
⑤ OSD：包围框（4 条线）+ 文本缓冲写 "TARGET: ORANGE (x1,y1)-(x2,y2) N=123"
```
**代价**：≈800 LUT + 2 ERAM（tile 统计 + 框线生成）+ 复用文本子系统。

**扩展要求 2 的"识别"**：加一个简单的形状判决（长宽比、填充率 = count/(w×h)、宽高阈值）即可区分"圆形/方形/条形"，产生"类别"文字。

#### G. 运动目标检测 —— 零额外 DDR 带宽方案（P2，强烈推荐）

**问题**：帧差法要读上一帧。全分辨率读会再吃掉 221 MB/s（总 57%），且单端口内存有饿死显示的风险。

**方案（推荐）**：
```
① 旁路显示读通道：video_out 本来就要把每一帧的每个像素读出来给 hdmi_mixer
   → 在 hdmi_mixer 输入侧（HDMI_PIXEL_CLK 域）分出一路，计算 8×8 块平均亮度
   → 1280×720 / 8×8 = 160×90 = 14,400 个缩略像素
② 缩略帧存 ERAM：14,400 × 8 bit = 115,200 bit ≈ 6 块 ERAM（存"上一帧"）
   再加当前帧的累加器（160×90 × 8~12 bit ≈ 9~14 块 ERAM，或用 1 个行缓冲滚动）
③ 比较：|cur − prev| > TH → 运动；配合 3×3 形态学（腐蚀→膨胀）去噪
④ 输出：① 运动区域框（在缩略图上求包围框，再 ×8 映射回原图）
        ② 运动像素计数（OSD 显示 "MOTION: 1234")
⑤ 更新：每帧末把 cur 写入 prev（真双口 ERAM，或乒乓两块）
```
**关键优势**：
- **DDR 带宽增加 = 0**（复用显示读，不新增任何 DDR 事务）
- **面积小**：≈400 LUT + 8~12 ERAM
- 时域可做**背景建模**（running average / sigma-delta）而非简单帧差，抗光照突变
  `bg += (cur > bg) ? +1 : -1`（sigma-delta，只需加减和比较）

**风险**：若显示暂停（没读 DDR），统计也会停。可在 OSD 上显示"统计暂停"标识，或改为直接旁路 ISP 输出（不经过 DDR）——**但那样就变成"与显示无关的运动检测"，反而更实时**（检测的是采集侧帧差，延迟更低）。**两条路都可，建议做"旁路 ISP 输出"版本，更简单也不依赖显示读**：把 8×8 块平均放在 ISP 域（30% 占空比，资源充裕），直接和 ERAM 里的上一帧比。

> 这个方案把"高阶要求 4（硬件运动目标检测）"的成本从"争抢 221 MB/s DDR 带宽"降到"8~12 块 ERAM"，是本报告的第二大杠杆。

#### K. 共享行缓冲 + 算法槽（P3，架构收尾）

现状：`edge_detect_96` 自带 2 个行缓冲（LUTRAM），卡通化若再加 Sobel 就再来一份。正确做法：
```

#### L. 快速算法域 + 独享算子分时复用（增补 L1，最大架构杠杆）

**动机**：ISP 域只有 2× 安全复用余量（§0.5-C2），但重算子（5×5 双边/形态学、连通域、帧差、直方图）若按 4 px/拍全并行，LUT 和 DSP 都吃不消（DSP 尤其稀缺，见 §0.5-L2）。

**做法**
```
① 在 PLL IP 中使能闲置的 C2 / C3 输出（当前 clk2_en / clk3_en 都接 0）
   VCO = 1500 MHz → C2 = ÷10 = 150 MHz，或 C3 = ÷12 = 125 MHz
   ★ 不额外占用 PLL（仍为 3/6）
② 在 ISP 域（60 MHz）与该算法域之间加一对弹性 FIFO（异步，容量 ≥ 1 行）
③ 重算子做成【单个】硬件实例，在该域里分时复用 N 次处理一个 4-pixel beat
   在 125 MHz：13.8 M beats/s 占用 0.11 beat/clk → 每 beat 约 9 拍可用 → N 可取 4~8
④ 输出经 FIFO 回到 ISP 域或直接进 DDR 写通道
```

**收益**：算子面积近似 **÷ (N)**。举例：
- 5×5 双边滤波若全并行需 ~12 DSP + 数千 LUT；改为 1 个实例复用 8 次 → **~2 DSP + 数百 LUT**
- 3×3 中值滤波（9 元素排序网络）全并行约 400 LUT；复用 4 次 → ~150 LUT
- 连通域 / 投影统计的逐行处理可直接复用

**风险与步骤（必须按序）**
1. **先只加时钟域 + FIFO（不加重算子），跑一次 P&R 测该域 Fmax**。若 125 MHz 达不到，退到 100 MHz（÷15）甚至 75 MHz（= 现有 HDMI 像素钟，但会引入与 HDMI 域耦合）。
2. 跨域 FIFO 必须用异步 FIFO IP（工程里已有 `w40/w128/w155_d512_fifo` 先例），**禁止多 bit 直接打拍**。
3. 增加的 CDC 会带来新的时序约束，`.sdc` 里要显式声明 `set_clock_groups -asynchronous`（现有 `.sdc` 已经用这种方式处理跨域）。
4. 该域是**新增加的独立域**，不会恶化现有三个吃紧的域（HDMI 75.59 / DDR 69.33 / MIPI 113.6）——**这是一条"另开战场"的扩容路线，比在现有域里硬堆组合逻辑安全得多。**

**建议**：把"卡通化的形态学梯度"和"目标检测的 tile 统计"作为第一个试验品，成本低、效果直观，适合验证这条路线。
