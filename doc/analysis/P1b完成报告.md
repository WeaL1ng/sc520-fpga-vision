## 2. Logo ROM 的 ERAM 推断：成功

这是 P1b 的技术前提，也是最大的不确定性（方案里我列为风险 R1）。

**实测证据**（`_phy.area` 层级报告，列序：logic lut / ripple / seq / **eram** / dsp）：

| 实例 | logic lut | ripple | seq | **eram** | dsp |
|---|---|---|---|---|---|
| `u_hdmi_mixer` | 278 | 127 | 266 | **8** | 0 |
| └ `u_logo_rom_eram` | 10 | 0 | 20 | **7** | 0 |

- **`u_logo_rom_eram` 占 7 个 ERAM 块** ⇒ 综合器**确实把它识别成存储**，而不是展开成 LUT
- 与工具预估的 6 块吻合（13,724 × 8 bit = 109,792 bit ÷ 20 Kb ≈ 6 块，实际 7 块含地址寄存器开销）
- **`u_hdmi_mixer` 整个模块只剩 278 LUT** —— 对比 P1a 时的 **2,572 LUT**，降幅 89%
- 全设计 ERAM 43 → **51**（+8），占用 47.22%，**远低于 108 块上限**

> **结论：`(* ram_style = "block" *)` + 同步读常量 case 的写法，TD 能推断出 ERAM。**
> 因此**不需要用 TD IP Core Generator 生成 ROM IP**（也就避开了 GUI 操作的麻烦）。
> 这条经验对后续 P3/P4/P5 的存储需求同样适用。

## 3. 改了什么

### 3.1 新增 `logo_rom_eram.v`（581,045 B，13,775 行）

由 `tools/gen_logo_rom_v.py` 从 `tools/logo_rom/` 素材自动生成：

| 项 | 值 |
|---|---|
| 端口 | `I_clk / I_rst_n / I_addr[13:0] / O_idx[7:0]` |
| 深度 × 位宽 | 13,724 × 8 bit（调色板索引，0 = 透明） |
| **延迟** | 比旧 ROM **多 1 拍**（`addr_reg` → 同步读） |
| ERAM | **7 块**（实测） |
| 初值 | 无（常量 case，不需要 `initial` / `.mif` / IP 文件） |

**为什么用常量 `case` 而不是 `reg` 数组 + `initial`**：Verilog-2001（`.v` 默认）**不接受 `initial` 块**，
TD 会报错；而常量 case 无需初值、纯文本可版本控制。

### 3.2 `hdmi_mixer.v` 四处改动

| # | 改动 | 效果 |
|---|---|---|
| 1 | Logo ROM 例化换成 `logo_rom_eram` | 组合 LUT 网 → ERAM |
| 2 | Logo 区域改为**裁剪区** 146×94 @(7,34)，ROM 深度 13,724 | ROM 从 160×160 缩小 |
| 3 | **行基址寄存器**替代 `S_logo_y * LOGO_W` 乘法 | **省 1 个 DSP**，消除扇出 150 的长网 |
| 4 | 地址计算改用 **`_1d` 坐标**（提前一级） | 吸收 ROM 的 1 拍延迟，Logo 与 `S_video_data_2d` 保持对齐 |

加上内置的 **256 色调色板函数**（`logo_palette_rom`，索引 0 = 透明）。

### 3.3 编译列表

三处（`.al` + `syn_1.prj` + `phy_1.prj`）把 `anlogic_logo_rom.v` 替换为 `logo_rom_eram.v`，各 1 处。

## 4. 关键技术细节：流水线为什么这样接

### 4.1 原设计的问题（实测最差路径，13.3 ns 预算）

```
S_x_2d/S_y_2d ──y*160(DSP 2.7ns)──► 组合 ROM 查找(6.1ns, 12 级 LUT) ──► O_hdmi_data(R)
                                     ▲ 全部挤在同一个周期
```

逐段量出的构成（`slack=+0.010 ns` 那条）：

| 段 | 累计 ns | 增量 |
|---|---|---|
| 时钟网络 | 1.97 | 1.97 |
| DSP 乘法 `y*160` | 5.29 | 3.32 |
| 扇出网（fo=150） | 6.65 | 1.36 |
| **组合 ROM 查找（12 级 LUT）** | **12.75** | **6.10** |
| 裕量 | | **0.010** |

### 4.2 改后

```
第 N   拍: S_x_1d/S_y_1d ──行基址加法──► ROM 地址（ROM 内部寄存）
第 N+1 拍: ROM 输出索引 ──调色板──► S_logo_pixel_r（寄存）
第 N+2 拍: S_x_2d/S_y_2d 判定 hit ──► O_hdmi_data(R) 与 S_video_data_2d 同拍选择
```

**对齐推导**：`S_x_2d/S_y_2d` 与 `S_video_data_2d` 是同一拍（原设计如此）。
地址在 `_1d` 级（早一拍）算好，ROM 在下一拍出数据 —— 正好落在 `_2d` 级。
⇒ **Logo 与视频同拍，无 1 像素偏移**，且**视频通路的 2 级延迟完全未动**
（满足 `risks.md` R-09"不得改变该 2 级延迟结构"）。

### 4.3 ✅ 该推导已被实测证实（2026-09-20 补充，多软件验证）

上面这条对齐原本只是**推导**。现已用 ModelSim 功能仿真 **实测证实**：

```
expected: x=7   y=34   w=146   h=94      <- 直接由 logo_pixel.mif + logo_palette.vh 算出
measured: x=7   y=34   w=146   h=94      <- 两次仿真逐像素做差得到
delta   : dx=+0  dy=+0  dw=+0  dh=+0
[PASS] Logo position and size match exactly - no 1-pixel shift
```

**方法（三个互相独立的实现交叉验证，不依赖任何假设）**：

| # | 工具 | 做什么 |
|---|---|---|
| ① | **ModelSim** | 编译 `hdmi_mixer` + `logo_rom_eram` + `osd_char_lib` + TB，跑**两次**仿真（`+osd=0` / `+osd=1`），导出 1280×720 逐像素文本 |
| ② | **ModelSim** | 断言两次运行的 DE 有效像素数**精确等于 921,600**（=1280×720），确认帧完整 |
| ③ | **Python** | 直接从 `logo_pixel.mif` + `logo_palette.vh` 算"期望包围盒"；再把两次仿真的**差集**当"实测包围盒"，两者比对 |

**为什么用"两次仿真做差"**：`I_osd_en` 只控制 Logo（安路 Logo + 动态文字），
状态条与模式数字不受它影响 —— 所以两次的唯一差异就是 OSD 内容。
这样**完全避开了对"背景像素编码"的假设**，做差得到的区域是精确的 OSD 覆盖区。

**数据自洽性**：窗口内 6,293 个差异像素**全部命中调色板颜色**（0 个例外）；
窗口外 888 个差异正是"安路 CNT"动态文字（在 x=375..575, y=120..145）。
⇒ **没有丢失或偏移任何 Logo 像素。**

**一键复现**：

```powershell
powershell -ExecutionPolicy Bypass -File .\sim\p1b\run_p1b_logo_check.ps1
```

> `hdmi_mixer` 的依赖只有 3 个**纯 RTL** 模块，不需要安路的加密 IP，
> 所以这段逻辑可以在 ModelSim 里完整仿真 —— 这是能做成这次验证的前提。

## 7. 过程中踩的坑（值得记住）

| # | 坑 | 教训 |
|---|---|---|
| **1** | **`td_stage.ps1` 路径硬编码**，第一次跑 P1b 时误对**冻结的原目录**发起综合 | 已加 `-ProjectRoot` 参数；**多目录作业时，脚本参数化是必须的** |
| 2 | 生成器端口声明写错（删端口时留下多余逗号、`output wire` 却又在时序块赋值） | 生成代码必须过一遍编译器；`output wire` + 过程赋值 = 非法 |
| 3 | 用 PowerShell 字符串替换往大文件里**插入函数**，插入点算错导致**模块结构重复** | **不要用脚本做结构插入**；用有唯一性校验的 `edit` 工具。这次靠源目录副本才恢复 |
| 4 | 替换函数体时丢了 `end` / `endfunction`，报出一堆"unexpected end"级联错误 | 级联报错要**找首个错误**（编译器报的行号不是根因） |
| 5 | 手工转录 256 条调色板不可靠 | 改成从源文件解析 + **逐条比对校验**（256/256 一致） |
| 6 | `opt_rtl` 需 11m21s > 单次工具调用 600 s 上限 | 需用**后台作业 + 期间轮询**（作业若立刻返回，子进程会被回收）。本次综合只用了 3 分钟，未触发 |
| 7 | `Get-Content` 默认按 GBK 读 UTF-8 无 BOM 文件 → 乱码 | 读中文文档用 `read` 工具或 `-Encoding UTF8` |
| 8 | Python 打印 emoji 时 GBK 编码失败 | 生成器日志保持纯 ASCII |
