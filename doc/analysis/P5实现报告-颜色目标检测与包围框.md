## 1. 算法：tile 投影统计，不做完整连通域标记

```
① 色度       Cb = (128B −  43R − 85G) >> 8 + 128     ← CSD 移位加法，零 DSP
             Cr = (128R − 107G − 21B) >> 8 + 128
② 颜色分类   warm = (Cb <= 115) && (Cr >= 160)       ← 亮度无关 ⇒ 抗光照变化
③ tile 统计  画面切 16×9 = 144 个 80×80 tile；
             tile 内命中像素数 >= 12 才认为该 tile"有目标"（噪声抑制）
④ 包围框     对所有合格 tile 求 min/max → ×80 映射回像素坐标
⑤ 叠加       画 4 条 2 像素宽边线 + 文字 "BLK 0312,0208"
⑥ 形状判决   长宽比 >= 2.5 ⇒ BAR，否则 BLK
```

**为什么不做完整连通域标记（two-pass union-find）**：720p 上要整帧行缓冲 + 等价表，
面积和时序都吃不消。tile 投影统计用 **tile 量化的精度**换掉了整帧缓冲 —— 代价是
包围框外扩到 tile 边界（±80 像素），对"框住一个物体"的展示目的完全够用，而且
**诚实**：报告和 OSD 都不假装它是像素级精确框。

### 1.1 为什么用 YCbCr 而不是直接 RGB 阈值

Cb/Cr **与亮度无关**。P6 会引入 AE 自动曝光（亮度会大幅变化），RGB 阈值会随曝光漂移，
色度阈值不会。实测参考点（8 bit）：

| 颜色 | 整数式 (Cb,Cr) | BT.601 浮点式 | 判定 |
|---|---|---|---|
| 橙 (255,128,0) | (42, 202) | (43, 202) | **暖 ✓** |
| 红 (255,0,0) | (85, 255) | (85, 256) | **暖 ✓** |
| 白 / 灰 | (128, 128) | (128, 128) | 排除 ✓ |
| 蓝 (0,0,255) | (255, 107) | (256, 107) | 排除 ✓ |
| 黄 (255,255,0) | (0, 148) | (0, 149) | 排除 ✓（Cr=148 < 160） |
| **肤色 (200,150,120)** | **(104, 155)** | (105, 155) | **排除 ✓（Cr=155 < 160）** |

> 肤色那一行是关键：手/脸最容易造成误检，而它恰好卡在阈值下方。**验证脚本把
> "整数式 vs BT.601 浮点式"两种算法都跑一遍做交叉验证**，确认系数没写错 ——
> 这条已经作为 `check_target_detect.py` 的固定检查项。

### 1.2 零 DSP、零除法、零有符号运算

色度用 **+32768 偏置**技巧彻底避开有符号算术：先加偏置再逐项相减，被减项都非负
且之后不再加 ⇒ 运行值 ≥ 最终值 ≥ 128，**无符号 16 位不会下溢**。

系数分解（严格等式）：43=32+8+2+1  85=64+16+4+1  107=64+32+8+2+1  21=16+4+1

十进制位（给 OSD 用）：千位一次比较，百/十位比较链，个位 `余数 − 10·十位`（10=8+2）。

## 2. ★ 架构决策：检测放 **ISP 域**，只把标量跨到显示域

方案原文（§"阶段 P7"）写"HDMI_PIXEL_CLK 域旁路 video_out 显示读流（**与 P5 共用同一个
tap**）"。**实测否决了这个位置**：

| 域 | P4c 布线后 Fmax | 余量 | 备注 |
|---|---|---|---|
| `MIPI_RX_BYTE_CLK`（ISP） | 70.631 MHz | **+17.7%** | |
| `HDMI_PIXEL_CLK`（显示） | 83.340 MHz | **+11.1%** | 最紧，且关键路径是**布线拥塞型**（网上延迟占大头） |

本模块实测 **1,141 logic lut + 206 seq**（gate 级）。压进余量最小、且已经拥塞的显示域
是自找麻烦。**改成**：

```
awb_O_* ──┬── gray_binary_96 ──┐
          ├── cartoon_96      ──┼── mux(模式 0..4) ──► DDR ──► HDMI
          └── target_detect_96 ─┴─► 只取标量 ──跨域──► hdmi_mixer 画框+文字
```

| 好处 | 代价 |
|---|---|
| 1,141 LUT 落在 +17.7% 的域，紧域只多了 476−405 = **+71 LUT**（画框+文字） | 框比画面**滞后约 2 帧（≈33 ms）**—— DDR 4-BANK 帧缓冲的结构延迟 |
| 复用既有格局（与 `gray_binary_96`/`cartoon_96` 并联），**不新增任何 DDR 事务** | 恒定滞后，不是抖动；对 60 fps 演示可接受 |
| **标量**（每帧一组）跨域，不需要"标签随像素走"的机制 | |

**实测代价 = +617 slice（66.59% → 69.49%）、`HDMI_PIXEL_CLK` 余量 11.1% → 6.1%。**

### 2.1 跨域做法：准静态多比特 + 翻转标志

`design_top_wrapper.v` 里用"ISP 域每帧翻转标志 → HDMI 域 2 拍同步 → 边沿捕获整组"。

**为什么安全**：数据每帧只变一次（由 tuser 锁存），一帧内完全静止（≈16.7 ms）；
写侧在数据变化的同一拍翻标志，读侧经 2 拍同步后才看到翻转 —— 此时距数据变化已过
2~3 个 HDMI 周期（≈40 ns），而数据还要再静止 ≈16.6 ms ⇒ **捕获瞬间绝不会撞上数据跳变**。
这比乒乓省触发器，且**前提条件写在代码注释里**：若将来这些量变成"每拍都变"，
必须改乒乓（参考 `frame_latency.v`）。

## 3. ★ 抓出的 4 个真错（本节价值最高）

前 3 个是**独立验证**（模块级仿真 + Python 复算）抓出的，第 4 个是**上板**才暴露的 ——
两层的分工恰好印证了证据阶梯：低层能挡住大部分错，但**"模块级全绿"不等于功能实现**。

沿用本项目"多软件交叉"的做法：`tb_target_detect_96.v` 灌合成图案，
`tools/check_target_detect.py` **从图案定义重新实现一遍算法**（不复用 RTL 任何函数，
且色度用整数式 + 浮点式双算），逐帧比对包围框/tile 数/形状/十进制位。

**5 个场景全过**：

| 场景 | 图案 | 期望 | 实测 |
|---|---|---|---|
| A | 橙块 x∈[320,479] y∈[160,319] | bbox (320,160)-(479,319)、tiles=4、BLOCK | ✅ |
| B | 同几何，**蓝** | valid=0（不检出） | ✅ |
| C | 同几何，**肤色** (200,150,120) | valid=0（Cr=155 < 160） | ✅ |
| D | 橙长条 x∈[80,719] y∈[400,479] | bbox (80,400)-(719,479)、tiles=8、**BAR** | ✅ |
| E | 无目标 | valid=0 | ✅ |

### 错误 1（最隐蔽）：列计数永久错开一拍 ⇒ **凭空多出一个假 tile**

第一版在 `tuser` 那一拍既丢掉它的累加、又把列计数复位了 —— 而 `tuser` **本身就是新帧的
第 0 拍**。于是 `tile_x` 永远慢一拍，每个 tile 吃到右邻居的 4 个像素。目标高 160 行时，
邻居 tile 白拿 4×80 = 320 个命中 ≫ 阈值 12 ⇒ **左边多一个假 tile**
（实测 x_min=240 而非期望 320、tiles=6 而非 4）。

> **光看"有没有框"根本发现不了这个。** 修法：引入 `P_*`（帧首强制为 (0,0) 的位置量），
> 并让帧首那一拍**正常参与累加**。

### 错误 2：无目标时包围框输出 `(0,0)-(79,79)` 而不是 0

`valid=0` 时虽是 don't-care，但接口语义应当明确（否则以后画框可能冒出一条边）。
修法：无目标时显式清零。

### 错误 3（Verilog 位宽陷阱）：`dec3` 恒返回 0

```verilog
dec3 = { h, t, (r2 - ((t << 3) + (t << 1))) };   // ← 拼接宽度变成 4+4+11 = 19 位！
```

**拼接（concat）的每个操作数都是"自决定位宽"**：第三个式子含 `r2`（11 位）⇒ 整个拼接
19 位，赋给 12 位的 `dec3` 时**从左侧截断**，有效位全丢 ⇒ 函数恒为 0。

**现象极具迷惑性**：包围框、tile 数、形状**全对**，只有十进制位全是 0。
定位过程：层次化打印 `x_rest=320 / x_lo=000` ⇒ 锁定函数 ⇒ 在函数内 `$display` 出
`h=3, r2=20, t=2, ones=0` 全对但 `ret=000` ⇒ 确认是拼接截断。

**修法**：先落到 11 位的中间变量 `r3`，再取 `r3[3:0]` 切片。坑已写进源码注释。

### 错误 4（★ 上板才发现，唯一"仿真查不出"的错）：`awb` 的 `tuser` / `tlast` 与数据**不对齐**

**现象**：上板后目标文字永远是 `NONE 0000,000`，拿橙色物入镜也不变。
而模块级 5 场景全过、综合零违例、时序零违例。

**排查**：做**诊断构建**（见下节）把检测器内部量引到 OSD，读回来**全是 0**：

```
B00 W00000 C00/00
```

`B`（拍数 ÷ 1024）为 0 ⇒ **检测器一帧都没结算过** ⇒ 判定 `is_ff = I_tvalid && I_tuser`
**从未成立**。

**根因（必须读 `awb.v` 才能知道）**：

```verilog
awb.v:369  assign O_tlast = (valid_d1 == 0) && (valid_d2 == 1);  // valid 上升沿，**不是行尾**
awb.v:370  assign O_tuser = I_tuser;                             // tuser **组合直通**
awb.v:371  assign O_tvalid = valid_d2;                           // tdata/tvalid 有流水延迟
```

⇒ 在 `awb` 输出口上，**`tuser` 到达那一拍正好落在帧间消隐期（`tvalid=0`）**，
以 `tvalid && tuser` 作帧结算条件**永不成立**；而 `O_tlast` 根本不是行尾标记，
以 `tlast` 推进行计数也**永不推进**。

> ⚠ **这个坑对同级模块同样存在**：`cartoon_96` 也用这个 tuser 做帧复位（只错开一拍，
> 幅度小得多），所以**卡通模式此前也从未被目视确认过**。凡是**依赖帧/行结构**的模块
> 都不能信这个 tuser。

**修法**：结构**完全由拍数自计时推导**，不依赖 `I_tuser` / `I_tlast`
（与 `cartoon_96` 用 `x_grp` 回绕推算行边界同一套做法）：

```
行尾      = 最后一个 tile 列的第 20 拍到达时
tile 行末 = 行尾 && line_in_tile == 79
帧末      = tile 行末 && tile_y == 8      ← 在**帧末**结算（原为"下一帧帧首"）
```

**上板确认**：诊断行读出 `B E0`（224 × 1024 = 229,376 拍/帧 ≈ 320 × 720 ✓）、
`W 0C800`（51,200 个暖色像素），并且**红框出现** ⇒ 自计时修复在硬件上被证实。

> **教训（应升格为铁律）**：**上游模块的 `tuser` / `tlast` 语义必须逐一核对，不能想当然。**
> "tuser 组合直通 + tvalid 流水延迟"是一个看起来合理、实际错位的组合；
> 它对**纯逐像素模块**（`gray_binary_96`）完全无害，所以能长期潜伏 ——
> **只有依赖帧/行结构的模块才会炸。**

### ★ 诊断构建法（不是"错"，是本轮**最有效的手段**；也是 P8 自检页的雏形）

**问题**：板子上"永远 NONE"有**两种完全不同**的原因，屏上表现却一模一样：

- (A) 颜色判据从不成立（真实光照/AWB 把橙色洗白）；
- (B) 帧结算 / 跨域捕获从未发生（本次就是 B）。

⇒ 把检测器内部量**引到 OSD 上直接看**，一次上板就能定性，不必反复猜。

**做法**（`target_detect_96` 新增 3 个诊断输出）：

| 输出 | 含义 | 正常值 |
|---|---|---|
| `O_dbg_beat_k` | 本帧拍数 ÷ 1024 | **`0xE0`/`0xE1`**（= 320 拍/行 × 720 行） |
| `O_dbg_warm` | 本帧"暖色"像素总数 | 有目标时应 ≫ 0 |
| `O_dbg_cb/cr` | 帧中心 (640,320) 探测像素的 Cb/Cr | 用来按**实际光照**定阈值 |

**★ 关键技巧：用十六进制显示，而不是十进制。**
十六进制**只是位切片**，不需要比较链/除法 ⇒ **零额外逻辑**、不压 HDMI 域时序；
而十进制 6 位数需要一整套比较链（P3 正是在这里踩过时序坑）。字库里大写 `A`~`F`
与 `0`~`9` 本来就有，直接可用。

**OSD 格式**（当前上板版本，共 16 槽）+ 三版本指纹：

| 版本 | SHA256 前 8 位 | 诊断行内容 | 用途 |
|---|---|---|---|
| `p5dbg` | — | `NNNN` 全 0 | 确认"检测器没结算"（`B00`） |
| `p5fix` | — | `B E0 W 0C800 C 80/80` | 确认自计时修复 |
| **`cart8diff`（当前）** | **`78F27C6D`** | 同上（随场景变化） | 交付版 |

```
B E0  W 0C800  C 80/80
│ │   │ │      │ │
│ │   │ └──────┴─ 暖色像素数（十六进制，5 位）
│ └───┴─ 拍数 ÷ 1024（十六进制，2 位）  ← 流结构健康检查
└─────── 中心探测像素的 Cb / Cr（十六进制）
```

**保留诊断行为"自检读数"的理由**（已决定保留）：

1. 它是"检测真的在工作"的**可见证据** —— 答辩时比口头说明有力；
2. 它是**方案 P8 自检页的雏形**（P8 要做全链路状态位 + 帧计数 + 模式 + LATENCY）；
3. 本轮正是靠它定位了上面那个 `tuser` 错位（`B00` 是唯一线索）。

> ⚠ **演示布景提醒**：诊断行显示 `W ≈ 49000`（占画面 5%）时，说明**场景本身**
> 就满屏暖色（夕阳、暖色灯光、水面反射），框会去框最大的暖色区。
> **拿饱和橙色物体放在冷色背景（白墙 / 灰桌面 / 蓝天）前**，框才会干净地只框住目标。
> 这是布景问题，不是功能问题。

## 4. OSD 叠加

### 4.1 包围框

4 条 2 像素宽边线，**只在 `I_tgt_valid=1` 时画** ——"移出画面必须无残留"是本阶段的
专门验收项。比较用"边界 + 线宽"而不是减法，避免无符号下溢。

### 4.2 文字区 `BLK 0312,0208`（13 槽 × 16 = 208×16）

| 项 | 值 |
|---|---|
| 位置 | **(256, 80)** |
| 内容 | 形状（4 槽：NONE/BAR/BLK）+ X 四位十进制 + `,` + Y 三位十进制 |
| 颜色 | 目标文字琥珀 `#ffd040`；包围框红 `#ff2040` |

### 4.2b 诊断行（16 槽 × 16 = 256×16，**与上面同一块区域**）

| 项 | 值 |
|---|---|
| 位置 | 同 **(256, 80)**（复用同一区域，切换显示内容，不额外占位） |
| 内容 | `B xx  W xxxxx  C xx/xx`（**全部十六进制**，见"诊断构建法"一节） |
| 为何十六进制 | **纯位切片 ⇒ 零比较链 ⇒ 不压 HDMI 域时序**；十进制 6 位要一整套比较链（P3 的反面教材） |
| 字库 | 字库本来就有大写 `A`~`F` 与 `0`~`9`，直接可用 |

**位置必须与既有区域互不重叠**（P3 就在这里踩过坑：第一版放 (16,48) 压了 Logo 下缘
137×16 像素）。`tools/verify_osd_layout.py` 现在抽 **6 个区域、15 对**全部不重叠 ✅。

**十进制位刻意放在 ISP 域算**（`target_detect_96` 里），HDMI 域只做"槽位→字符码"查表 ——
因为 P3 的教训就是"帧率信号直接进像素级组合云"会把 HDMI 域时序拉垮。

**输出优先级**：`OSD > 状态条 > 模式数字 > 目标框 > 延迟文本 > 目标文字 > 视频`。
目标框放在延迟文本之上（框可能横穿文本区，视觉上框更重要）；目标文字放在最靠近视频
的一层，避免它遮住任何既有元素。

### 4.3 诚实标注

OSD 显示的形状是 **NONE/BAR/BLK**，**不冒充"目标个数"**。`O_tile_cnt`（合格 tile 数）
是"噪声抑制后的像素面积代理"，不是目标数量 —— 真正的计数需要连通域标记，本版刻意不做。

**已知边界**：圆形与方形都会判成 BLK（只用长宽比区分长条）。要支持圆形需要看首/末
tile 行的弦宽或四角，**本版未实现**，已记录在模块头注释。

## 8. ★★ 2026-09-23 上板复盘：屏上"明明有橙色却 `W 00000`"的根因是**过曝**

### 8.1 证据（用户上板照片，OSD 诊断行直接读出）

| OSD 读数 | 含义 |
|---|---|
| **`W 00000`** | 全画面**零**个暖色像素 —— 而画面正中就是一大块饱和橙色物体 |
| `C 79/80` | 中心探测点 Cb=121 / **Cr=128（正好中性）** ⇒ 该点在白色桌面上，合理 |
| `A 07C6` | 曝光 = 1990 = **上限** |
| `G 59` | 模拟增益 = 89 = **上限** |
| `L 93` = 147 | 平均亮度 **147**，远高于闭环目标 112（死区上限 115） |

⇒ 一句话：**曝光与增益双双顶在最大值，整幅画面过曝，颜色被"洗白"了。**

### 8.2 为什么过曝会让判据失效（算一遍就知道）

| 颜色 | Cr 计算 | Cr | 判据① `Cr>=160` |
|---|---|---|---|
| 饱和橙 (255,128,0) | (128·255 − 107·128 − 21·0)>>8 + 128 = 74+128 | **202** | ✅ 暖 |
| **过曝橙 (255,230,200)** | (32640 − 24610 − 4200)>>8 + 128 = 14+128 | **142** | ❌ **判不出来** |
| 白 (255,255,255) | (32640 − 27285 − 5355)>>8 + 128 = 0+128 | 128 | ❌ |

⇒ **判据本身没错，是"过曝把色度压平了"**。这也解释了为什么 P5 当初上板能出框
（那时曝光没被推满），而 P6 上任之后就不行了 —— **是 P6 的 AE 把画面推过曝的**。

### 8.3 修法一（治本）：AE 不许卡在双上限

在 `ae_ctrl.v` 里发现并修掉一个真 bug：**目标推进没有饱和钳位**
（`S_ae_t + step` / `S_ag_t - step` 只判"能不能动"、不钳位），
往下调时 `200-256` 会在 16 位无符号下**下溢成 65480**，
既写出非法曝光、又让 `w_committed` 永远不成立 ⇒ **闭环永久冻结**。
详见 `P6实现报告-AE闭环.md` §11。

### 8.4 修法二（兜底）：新增**对过曝免疫**的判据②

```
warm = (Cb <= CB_MAX && Cr >= CR_MIN)                    // 判据①：正常曝光
     || (R >= R_CLIP && R >= G + RG_MARGIN && R >= B + RB_MARGIN)  // 判据②：过曝兜底
```
默认 `R_CLIP=250, RG_MARGIN=16, RB_MARGIN=24`。

**为什么它有效，而且不会把原来排除掉的东西放进来**：

| 颜色 | R 贴顶? | R−G | R−B | 判据② | 结论 |
|---|---|---|---|---|---|
| 过曝橙 (255,230,200) | ✅ 255≥250 | 25 | 55 | **命中** | ✅ 检出（正是要救的场景） |
| 过曝白 (255,255,255) | ✅ | 0 | 0 | ✗ | ✅ 不误检 |
| 黄 (255,255,0) | ✅ | 0 | 255 | ✗ | ✅ 不误检 |
| 蓝 (0,0,255) | ✗ | − | − | ✗ | ✅ 不误检 |
| **肤色 (200,150,120)** | ✗ 200<250 | 50 | 80 | ✗ | ✅ **仍由判据① 的 Cr=155<160 排除** |

★ 关键：门槛 **`R >= 250`** 把"肤色/白/黄"全挡在判据②之外 ——
它们只有在**真正过曝**（R 已经被削平到 255）时才会进来，而那一刻判据①已经失效，
正需要它兜底。

> ⚠ **诚实边界**：过曝到"橙与白都变成 255"时，**任何**颜色判据都无能为力
> （信息已在传感器端丢失）。判据②能救的是"R 顶了但 G/B 还没顶"这一档。

### 8.5 一个实现细节陷阱（两边都踩过）

判据② 起初写成 `(r - g) >= RG_MARGIN`：
- 在 **Verilog** 里 8 位无符号相减，`r < g` 时**下溢成大数** ⇒ 比较**误判为真**，
  白/黄会被错误放进"暖色"；
- 在 **Python** 模型里同样写法会得到负数 ⇒ 结果又不一样。

⇒ 正确写法是 **`r >= g + MARGIN`**（加宽到 9 位再比，无下溢）。
这条也写进了 `check_target_detect.py` 的注释。
**"两种语言各错一半、结果还能互相印证"是最危险的情况** —— 所以两侧都改了。

## 9. ★★ 2026-09-26 上板复盘：**亮橙照片能认、普通橙色臂章不认**

### 9.1 现象

| 目标 | 结果 |
|---|---|
| 手机屏幕上的亮橙照片（背光、高饱和） | ✅ 出框 |
| **普通橙色臂章**（室内光、哑光布面） | ❌ 不出框 |

### 9.2 定位：`CR_MIN = 160` 这个门槛定得太高

把几种"橙"代进判据算一遍（`Cr = (128R − 107G − 21B)>>8 + 128`）：

| 颜色 | Cb | **Cr** | 旧判据 `Cb≤115 && Cr≥160` |
|---|---|---|---|
| 手机亮橙 (255,128,0) | 42 | **202** | ✅ 认出 |
| **哑光臂章 (170,125,100)** | 107 | **152** | ❌ **差 8 就认不出** |
| 更暗的普通橙 (150,115,95) | 104 | **147** | ❌ |
| 阴影里的橙 (120, 65, 35) | 103 | **157** | ❌ |
| 肤色 (200,150,120) | 104 | **155** | ❌ ← **当初设 160 就是为了挡它** |

⇒ **160 把"普通室内光下的哑光橙"和肤色一起挡掉了。**
而手机照片是背光高饱和（Cr 202），所以只有它能过 —— 现象完全对得上。

### 9.3 为什么不敢直接把门槛降下来：黄色

纯黄 (255,255,0) 的 **Cr = 148**，正好卡在门槛附近。
降门槛就会把黄色放进来，而"黄色不误检"是原来验过的判据。

### 9.4 ★ 改法：用 **Cb 下限**挡黄色，把 Cr 门槛让出来

黄色的**真正特征**不是 Cr，而是 **Cb ≈ 0**（非常偏蓝的负向）；
橙色的 Cb 落在 **42~107**。⇒ 新增 `CB_MIN = 30`，把黄色交给 Cb 挡：

```
by_chroma = (Cb >= CB_MIN=30) && (Cb <= CB_MAX=115) && (Cr >= CR_MIN=146)
```

| 颜色 | Cb | Cr | 新判据 | 结果 |
|---|---|---|---|---|
| 手机亮橙 | 42 | 202 | ✅ | 认出 |
| **哑光臂章** | 107 | 152 | ✅ | **认出（本次要修的就是它）** |
| 阴影里的橙 | 103 | 157 | ✅ | 认出 |
| **纯黄** | **0** | 148 | ❌（被 Cb≥30 挡） | 不误检 ✅ |
| 白 / 灰 | 128 | 128 | ❌（被 Cb≤115 挡） | 不误检 ✅ |
| 蓝 | 255 | 107 | ❌ | 不误检 ✅ |
| **肤色** | 104 | 155 | ✅ | ⚠ **会误检（见 9.5）** |

### 9.5 ⚠ 一个**改不掉**的限制（必须如实说明）

**哑光橙 (Cb=107, Cr=152) 与肤色 (Cb=104, Cr=155) 在 Cb/Cr 平面上几乎重合**
（各差 3 个 LSB）。它们本来就是**同一色调、饱和度重叠**的颜色 ——
**任何矩形或线性判据都无法把这两者分开**，这是判据形式本身的极限，不是参数没调好。

所以在当前设置下：

| | 结果 |
|---|---|
| 哑光橙臂章 | ✅ **能认**（赛题要的就是"认出指定目标"） |
| 手 / 脸入镜 | ⚠ **也会被认出来**（框会把手一起框进去） |

**二者不可兼得**：想要排肤色就把 `CR_MIN` 改回 160，代价是哑光橙又认不出。
本设计**选择认目标**，并把这一条写进报告的"已知边界"。

> **演示建议**（能显著改善观感，且零成本）：
> · 把臂章**放在冷色背景上**（白墙/灰桌面/蓝布），不要一直用手举着；
> · 冷色背景 + 短时间入画 ⇒ 即使手偶尔被框进去，框的主体仍然是臂章；
> · 需要"只框臂章"时，把臂章摊平在桌面上、从上方拍（画面里没有皮肤）。

| **把光调暗** | ❌ **又不认了** |

### 10.2 ★ 根因：**我此前"Cb/Cr 与亮度无关"的说法是错的**

> 纠正 §1.1 与 §9 里的表述：`Cb/Cr` 只有在**除以亮度之后**才与亮度无关。

`Cr − 128 = (128R − 107G − 21B)/256` 是**色差幅度**；
漫反射下 R/G/B 都正比于照度 E ⇒ **色差幅度也正比于 E**：

| | 128R−107G−21B | Cr−128 | 判据① `Cr≥146`（即 Cr−128≥18） |
|---|---|---|---|
| 臂章亮 (170,125,100) | 6285 | **24.5** | ✅ |
| **同一臂章暗一半 (85,62,50)** | 3142 | **12.3** | ❌ **差 6** |

同一块布、同一个颜色，只是变暗，判据就失效 —— 因为**固定门槛实际上同时比较了"颜色"和"亮度"**。

### 10.3 修法：判据③ **比值判据**（把亮度除掉）

用现成的 G 当亮度代理，判 `(Cr−128)/G`：

| 颜色 | (Cr−128)/G | |
|---|---|---|
| 臂章亮 (170,125,100) | 24.5/125 = **0.196** | ✅ |
| **臂章暗 (85,62,50)** | 12.3/62 = **0.198** | ✅ **变暗后不变** |
| 肤色 (200,150,120) | 27.5/150 = **0.183** | ❌ |
| 肤色暗 (140,105,84) | 19.2/105 = **0.183** | ❌ |
| 纯黄 (255,255,0) | 20.9/255 = 0.082 | ❌ |
| 白/灰 | 0 | ❌ |

门槛取 `49/256 = 0.1914`（夹在 0.183 与 0.196 之间）。**零乘法**：
```
(Cr−128) > (49/256)·G   ⟺   cr_raw > 49·G + 32768,   49·G = (G<<5)+(G<<4)+G
```

### 10.4 ★ 实现时踩的第二个坑（**同一个错误又犯了一次**）

判据③ 第一版我还加了 `Cb` 的绝对上下限（想挡黄色）。结果**变暗的橙色反而判不出来**：

```
亮臂章 (170,125,100) → Cb = 107   ≤ 115 ✓ 在范围内
暗臂章 ( 85, 62, 50) → Cb = 118   > 115 ✗ 被误挡
```
因为 **`Cb−128` 与 `Cr−128` 一样也正比于色差幅度**，变暗后 Cb 趋向中性 128。
⇒ **在"比值"判据里再用绝对 Cb 门槛，等于把刚除掉的干扰轴又加回来。**

而 `Cr/G` 比值本身已经把黄(0.082)/白(0)/灰(0)/蓝(负) 全排除了 —— 不需要 Cb 帮忙。
**去掉 Cb 门槛后，变暗的臂章才真正被检出。**

### 10.5 L1/L2 复验（12 个场景）

| 场景 | 图案 | 期望 | 实测 |
|---|---|---|---|
| **J** | **变暗臂章 (85,62,50)** | **应检出** | ✅ 检出 |
| C | 肤色 (170,140,120) | 不应检出 | ✅ 不检出 |
| K | 变暗肤色 (140,105,84) | 不应检出 | ⚠ **检出**（见 10.6） |
| L | 饱和肤色 (200,150,120) | 会检出（边界） | 检出（如实标注） |

> **顺带纠正一处场景取值错误**：原来场景 C 用的是 (200,150,120)，其 Cr=155 ≥ 146
> ⇒ 模型会得出"肤色被检出"。但**用户上板实测"手臂不误检"**是事实 ⇒ 实测肤色 Cr < 146。
> 已把场景 C 改成 (170,140,120)（Cr=144），**让模型服从事实**，
> 并保留 (200,150,120) 作场景 L 标明"偏饱和肤色会检出"这条边界。

### 10.6 ⚠ 仍然存在的弱点（必须如实说明，且**需要实测数据才能定**）

比值判据的固有风险：**除以很小的 G 会把比值放大**。例如很暗的肤色
`(100,70,55)` ⇒ (144−128)/70 = **0.229 > 0.1914** ⇒ 会被误检。
但**真实的肤色值我没有实测**（上板 OSD 的 `C xx/xx` 就是为此准备的诊断量），
所以这一条**只能用实测数据来定**：

> **请做一次 10 秒的测量**：把**手臂**放在画面正中，读 OSD 诊断行的 `C xx/xx`；
> 再把**臂章**放在画面正中，读同一个字段。两个 (Cb, Cr) 一报出来，
> 我就能把门槛定在两者中间（而不是像现在这样夹在"我以为的肤色"和"臂章"之间）。

**当前设置的取舍**：优先保证"**变暗的臂章能认**"（这是赛题要的目标），
代价是**很暗的肤色可能被误检**。若上板发现手臂开始出框，把 `CR_RATIO_NUM`
由 49 往上调（每 +8 约提高门槛 0.03），或把 `CR_MIN` 调回 160。

## 11. ★★ 2026-09-26 第三次上板：**框位置整体偏下** + 坐标行缺失

### 11.1 两个问题

| # | 现象 | 性质 |
|---|---|---|
| 1 | 红框比目标**整体偏下**（约一个 tile 行以上），框的宽度也不对 | **真 bug**（框架相位） |
| 2 | OSD 上**没有坐标** | **功能缺口** —— 进阶要求② 明确要求"坐标叠加" |

> 问题 2 是我自己造成的：当初为了上板定位，把"形状+坐标"那一行**换成了诊断行**，
> 定位完没有换回来。诊断行是我的工具，**坐标是赛题要求** —— 必须是要求优先。

### 11.2 ★ 问题 1 的根因：自计时的**帧相位**是任意的

`target_detect_96` 的帧/行边界是**纯拍数自计时**（铁律四要求，因为 awb 的
`tuser`/`tvalid` 不同拍）。但"从第几拍开始数"取决于**复位释放那一刻摄像头正在哪一行**：

```
复位释放 → 开始数 230400 拍 = 一帧  ⇒ 本模块的"第 0 行"= 摄像头的任意一行
⇒ 上报的 y 坐标带一个**任意常数偏移**（x 同样）
```

**为什么仿真和诊断位都没发现**：
- 诊断位 `B E0` 只能证明"每帧 230400 拍"，**证明不了相位对**；
- 原来的 TB **总是从帧的第 0 拍开始灌数据** ⇒ 相位天然正确，
  这个 bug 在 L1 里**不可能出现**。

### 11.3 修法：用 `I_tuser` 做**帧相位对齐**（并说清它与铁律四的关系）

```verilog
wire w_align = I_tvalid && I_tuser && (ALIGN_ON_TUSER != 0);
wire [3:0] P_tile_x = w_align ? 4'd0 : tile_x;      // 对齐那一拍强制当成 (0,0)
wire [4:0] P_col    = w_align ? 5'd0 : col_in_tile;
wire [3:0] P_tile_y = w_align ? 4'd0 : tile_y;
wire [6:0] P_line   = w_align ? 7'd0 : line_in_tile;
```

**★ 铁律四没有被违反**，这里要说清楚：
- 铁律四禁止的是拿 `I_tvalid && I_tuser` 当**帧结算**条件 —— 因为 awb 的
  `O_tuser` 组合直通、`O_tvalid` 流水延迟，**两者不同拍**，那个与条件**永不成立**；
- 这里只把 tuser 当**帧首脉冲**（单比特、每帧一次）用来**对齐计数器**。
  它与数据的流水深度差几拍，只带来 **≤ 几个像素**的固定偏差（远小于原来任意上百行）。

**★★ 一个必须避免的陷阱：对齐那一拍不能丢弃。**
若丢掉那一拍，每帧就少算一拍 ⇒ 帧边界**每帧漂移 1 拍（=4 像素）**，
1 秒漂 240 像素，画面会越来越歪。所以做法是**把那一拍强制当作 (0,0) 正常处理**，
一拍不丢 ⇒ 不漂移。

### 11.4 ★ 补上了"本来就该有"的 L1 用例：**相位偏移启动**

TB 新增两个开关：
```
+phase=N   先灌 N 拍（不发 tuser）把计数器推到帧中间，模拟复位释放的任意相位
+tuser=0   关掉 tuser 对齐（对照组 = 旧行为）
```

| 用例 | 包围框 | 判定 |
|---|---|---|
| `+phase=0` | `(320,160)-(479,319)` tiles=4 BLOCK | ✅ 基准 |
| **`+phase=1500`（对齐开着）** | `(320,160)-(479,319)` tiles=4 BLOCK | ✅ **与基准完全一致 ⇒ 修复有效** |
| `+phase=1500 +tuser=0`（旧行为） | `(0,160)-(1279,399)` tiles=6 **BAR** | ❌ **在仿真里复现了板上的症状** |

> 最后一行是这次最有价值的证据：**旧代码在相位偏移下确实给出错误的框**，
> 而且错法（位置偏、宽度拉满、形状误判成 BAR）与上板照片一致。

### 11.5 补回坐标行：`BLK 0312,0208`（区域 (256,176)）

| 槽 | 内容 |
|---|---|
| 0..3 | 形状：`NONE` / `BAR ` / `BLK ` |
| 5..8 | X 四位十进制 |
| 9 | `,` |
| 10..12 | Y 三位十进制 |

- 十进制位**仍在 ISP 域算好**（`O_tgt_x_d*`/`O_tgt_y_d*`），HDMI 域只做"槽位→字符码"查表
  ⇒ 零除法、零比较链（P3 的 LATENCY 除法链是反面教材）；
- 区域 (256,176) 与既有 8 个区域**都不重叠**（`verify_osd_layout.py` 现在抽 **8 个区域、28 对**）；
- **诊断行保留**（它定位过两次真 bug），两者各占一行。

### 11.6 ★ 这次也纠正了一条方法论

**"模块级自计时正确"必须包含"相位无关性"**，而不仅仅是"每帧拍数正确"。
原来的 L1 只验了后者。现在 `+phase` 用例把前者也钉住了 ——
**并且它是用"关掉修复后能复现板上症状"来证明自己有判别力的**（而不是只验"改了之后还是对"）。

## 12. ★★ 2026-09-27 第四次上板：**暗光下框占满屏/偏低**，根因是噪声而非相位

### 12.1 现象与排除

| 观察 | 结论 |
|---|---|
| 暗光（`L 28`≈40、AG=89 已到顶）下框占满整个画面高度、`BLK 0320,000`（`y_min=0`） | ❌ 假阳性 |
| `W 0F4B8` ≈ **3.3 万**个"暖色像素" | 而真实的彩色物体面积远小于此 ⇒ **不是真颜色** |
| 手掌贴近镜头 | `NONE`、不出框 ⇒ **手没有被误检**（我上一轮"暗肤色被比值判据误检"的判断**据此撤回**） |
| 运动框 / 坐标行 | 正常 ⇒ **不是相位问题**（§11 修的是另一个真 bug） |

### 12.2 根因：**零星色度噪声**越过了 tile 门槛

- `Cb/Cr` 的**幅度正比于照度**（§10.2 已纠正过一次）。画面只有 32 的亮度时真实色度几乎为零，
  但 **AG=89（16~20 倍模拟增益）把色度噪声一起放大**；
- 而 tile 判据是 **80×80 = 6400 个像素里有 12 个暖色就算合格（0.19%）** —— 对噪声**毫无抵抗**。

### 12.3 修法：`TILE_HIT_TH` **12 → 512**

原理是**几何的、不依赖任何我猜的颜色值**：

| | 每 tile 命中数 | TH=12 | TH=512 |
|---|---|---|---|
| 真实橙色物体（成片，满铺 tile） | 6400 | 合格 | **合格** ✅ |
| 暗光色度噪声（零星） | ≈6 ~ 320 | **误报** ❌ | **挡住** ✅ |

`512 = 6400 的 8%`，落在"成片"与"零星"之间。

### 12.4 ★ 一个连带陷阱（差一点静默失效）

**`hit_col` 原本是 `reg [7:0]`、`hit_new` 饱和在 255** ⇒ 门槛设 512 时
`hit_new >= 512` **永远为假**：检测会**彻底失效，而且不报任何错**。
⇒ 必须同时把命中计数器加宽到 **13 位**（一个 tile 最多 6400 < 8192，**不需要饱和逻辑**）。
**"改一个参数"的说法是我上一条的错误估计**，实际是一次位宽变更。

### 12.5 判别力证据（`tools/check_tile_hit_th.py`，独立脚本）

```
P1 实心目标 6400 命中：TH=12 合格 / TH=512 合格   ⇒ 提阈值**不误杀目标**
P2 噪声密度扫描：
     0.5%  ⇒ 每 tile  32 命中 : TH=12 **合格(误报!)** / TH=512 挡住
     1.0%  ⇒ 每 tile  64 命中 : TH=12 **合格(误报!)** / TH=512 挡住
     10%   ⇒ 每 tile 640 命中 : 两者都合格（噪声已"成片"，512 挡不住）
P3 判别力成立：**能复现旧行为**（TH=12 下噪声达标 = 复现照片①的满屏框）——
   只验"改了之后还是对"是没有判别力的（§11.6 的同一标准）
交叉校验：512 需要物体覆盖 tile ≥ 8%；真实臂章/橙块是整片覆盖 ⇒ 余量充足
```

**⚠ 诚实边界**：若目标在画面里很小（覆盖单个 tile 不足 8%），512 会把它一起挡掉。
另外噪声密度一旦高到"成片"（≥10%），512 也挡不住 —— 那说明该从源头治（AE 不要
把暗场景增益拉满，或对色度先做空间平滑），而不是继续抬阈值。

### 12.6 L4 结果

**2026-09-27 上板确认：框的位置正常，暗光下的满屏/偏低框消失**
（用户目视："问题好像都解决了，框的位置正常了"）。
⇒ 这条同时把 12.5 里"512 能挡住零星噪声"这半边**用实测补上了**，证据强于纯仿真。

### 13.6 这轮的方法论收获

**"给我一个能显示我需要的量的诊断读数"比"再多改几轮判据"价值高得多。**

就一次性拿到了"臂章 Cb=120 / 手掌 W=0"这两个决定性的数，并且**得出了"不要动"这个结论**。
⇒ **诊断能力不够时，改判据只是在猜；诊断能力够了，"不改"才是一个有依据的结论。**
