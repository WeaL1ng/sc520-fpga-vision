## 1. C2 详解：真正的关键路径在 MIPI/ISP 域（本轮最重要的发现）

### 1.1 lab3 与 lab2 的最差路径都在 MIPI 域

**lab3**（`final_timing.rpt` L101–L109，最差 setup，slack 7.869 ns 是**该域内最差**）：

```
Begin Point : u_isp_top/u_demosaic/raw_matrix_3x3_buffer_d/zhenghe_d/valid_width_reg[6].clk
End Point   : u_isp_top/u_demosaic/raw_matrix_3x3_buffer_d/zhenghe_d/addrb_reg[10].cea
Constraint  : MIPI_RX_BYTE_CLK  16.668 ns  (59.995 MHz)
Data Path   : 8.483 ns  (cell 3.338 (39%) / net 5.145 (61%))
Logic Level : 9  (LUT3=3 LUT6=2 ADDER=2 LUT4=1 LUT2=1)
```

**lab2**（`final_timing.rpt` L101 起，slack **1.451 ns**，全设计最紧）：

```
Begin Point : u_isp_top/u_awb/mult5_syn_165        ← AWB 的乘法器/AWB 逻辑
End Point   : u_isp_top/u_edge_detect_96/O_tdata_reg[48]
Constraint  : MIPI_RX_BYTE_CLK  16.668 ns
Data Path   : 14.883 ns (cell 6.179 (41%) / net 8.704 (59%))
Logic Level : 14  ( ADDER=10  LUT5=2 LUT6=1 LUT4=1 )
```

> **lab2 是最紧的（1.45 ns < lab3 的 7.87 ns 在各自域内的裕量比）**，而**起点是 `u_awb`**。
> `awb` 的实测资源：**1,741~1,752 LUT + 2,292 ripple + 6,038~6,066 FF + 8 DSP**，
> 其中两个 `divider` 实例分别 **748 / 775 LUT + 各 1,084 ripple + 2,788 / 2,699 FF**。

### 1.2 为什么这改变优先级

既有文档把 P1 定义为"Logo→ERAM + OSD 流水线化"，论据是"HDMI 域只剩 0.103 ns"。

**核验后的真实图景**：

| 域 | 约束频率 | Fmax | SWNS | 谁在压它 |
|---|---|---|---|---|
| `MIPI_RX_BYTE_CLK` | 59.995 MHz | 113.6 MHz | 7.869 ns | `demosaic` 的 zhenghe 组合链（lab3）；`awb` DSP→`edge_detect`（lab2，**1.45 ns**） |
| `usr_clk` | 66.667 MHz | 69.3 MHz | 0.576 ns | 路径在 **DDR PHY IP 内部**（`ddr_init/state_cnt`→`wphase_ctl/wdq_load_r`），线延迟 88%、扇出 347 |
| `HDMI_PIXEL_CLK` | 75.002 MHz | 75.6 MHz | 0.103 ns | 15 级逻辑（lab3 最差域内的逻辑级数最高） |
| `HDMI_SERIAL_CLK` | 375.094 MHz | 429.2 MHz | 0.336 ns | TMDS 串行域 |

**三条独立结论**：

1. **HDMI 域确实紧（0.103 ns），但它不是"唯一的"紧**。`usr_clk` 0.576 ns、`HDMI_SERIAL_CLK` 0.336 ns 同在警戒线以下。
   ⇒ **门禁必须同时卡 4 个域**（`run_regression.ps1` 的 `$CriticalClockPatterns` 已经含有这四个，这一处写对了）。
2. **`MIPI_RX_BYTE_CLK` 名义上有 7.87 ns，但它的 Fmax 是 113.6 MHz —— 也就是说这条链路本身能跑到 113 MHz。**
   这直接推翻了一个隐含假设（见 §1.3）。
3. **AWB 是全设计唯一同时"最耗面积 + 最耗 DSP + 压在关键路径起点"的模块。**
   ⇒ **P1 的正确内容应当是"Logo→ERAM（为时序）**＋**AWB 重构（为面积/DSP/关键路径）"两件事一起做**，
   而不是只做 Logo。

### 1.3 由此得到的第一个高价值新思路：**把 ISP 全链路提速到 112.5 MHz，用时间换面积**

**事实链**：

- `MIPI_RX_BYTE_CLK` 的 **Fmax = 113.649 MHz**（lab3 实测，TD 推导 `derive_clocks`），而当前只跑在 **59.995 MHz**。
- 该域的**结构吞吐**是 **1 个 4-pixel beat / 2.5 拍**（既有文档 §0.5-C2 已正确算出）。
- 传感器实际负载：1280×720×60 = 55.3 Mpix/s → **0.23 beat/clk**（@59.995 MHz）。
- **⇒ 在 112.5 MHz 下，每 beat 有 ≈ 1.9 拍可用；也就是说"每 beat 允许 2 拍处理"是安全上限。**
- 更关键：**当前设计在 59.995 MHz 下，每 beat 事实上已经用了约 4.3 拍**（1/0.23），
  **但这条链路能跑到 113 MHz** ⇒ **把时钟提到 ~112 MHz，不增加任何面积，就直接拿到 1.9 倍的运算余量**。

**但这条"提速"不是免费的，必须先跨过一道坎**：lab2 最紧路径 slack 只有 **1.451 ns @ 16.668 ns**。
即 ISP 链路当前 Fmax ≈ 61.5 MHz。**要提到 112 MHz，就必须先把 AWB 的 14 级 ADDER 链打断。**

**⇒ 正确的因果顺序是：**

```
先做 AWB 重构（打断 14 级链、去掉 8 个除法器）
   ↓
此时 ISP 链路的 Fmax 从 ~61 MHz 升到接近 113 MHz
   ↓
【可选】把 ISP 域从 59.995 提到 112.5 MHz（只是改 PLL/SDC 约束，不改 RTL）
   ↓
拿到 ~1.9 倍运算余量 ⇒ 后续所有算法都可以"少并行、多分时"
```

> **与既有文档的关系**：既有文档的"新思路 L1（启用 PLL 闲置 C2/C3 建 125~150 MHz 算法域）"
> 需要**多一个时钟域 + CDC + 弹性 FIFO**，成本与风险都不低。
> **本轮修正**：**不必新建域** —— `MIPI_RX_BYTE_CLK` 本身就是 D-PHY 硬核输出，
> 它的频率由 D-PHY 硬核决定、Fmax 已实测 113.6 MHz。**在同一个域内提速，省掉全部 CDC 开销。**
> 但要注意：**该域频率由 D-PHY 硬核的分频决定，改频需要改 D-PHY 配置（`BYTE_NUM` / 分频比），
> 且会连带改变 `csi_unpacket_2lane` 每 2 拍一个 valid 的节拍** —— 这一点必须先做小实验验证，不能直接改。

> ⚠ **诚实标注**：`MIPI_RX_BYTE_CLK` 的 59.995 MHz 来自 D-PHY 硬核实测输出，
> **我尚未验证"能否把它配置成 112.5 MHz 同时保持 4-px/beat 的正确节拍"**。
> 这需要改 `mipi_dphy_rx_ph1p_mipiio_wrapper.sv` 的配置并上板验证（或至少跑一次时序）。
> **在验证之前，这条思路的定位是"待验证的高杠杆项"，不是"已确认可用"。**

## 2. C1 详解：Logo 那 2,495 个 LUT 是怎么被高估的

### 2.1 三个不同口径的报告，数值完全不同

| 报告 | 阶段 | `u_anlogic_logo_rom` | `u_hdmi_mixer`（整模块） |
|---|---|---|---|
| `syn_1/camera_to_dsi_display_rtl.area` | **RTL 级** | **38,479 gate**（`#Total_luts` 全设计只有 4,530，**不是 LUT 计数**） | 38,802 gate（其中 Logo 38,479 + `osd_char_lib` 95） |
| `syn_1/camera_to_dsi_display_gate.area` | **gate 级** | **不在层级表中（已被吸收）** | **2,313 LUT** |
| `phy_1/camera_to_dsi_display_phy.area` | **布局布线后（官方 lab3）** | **54 LUT**（`logic lut` 列） | **2,572 LUT** |
| `phy_1/...`（本机 TD 6.2.1 SP1 重跑） | 布局布线后 | **36 LUT** | **2,530 LUT** |

### 2.2 结论

1. **`rtl.area` 里的 38,479 是"gate"（基本门）计数，不是 LUT6。**
   既有文档（以及 `tools/gen_logo_mif.py` 生成的 `report.txt`）把
   `6387 项 × 25 bit = 159,675 bit ÷ 64 bit/LUT6 = 2,495 LUT6` 当成了实测值，
   **但 TD 从没报过这个数**。这是**经验估算被写成了"实测"**。
2. **到 gate 级，`u_anlogic_logo_rom` 作为独立模块已经消失** —— 说明综合/映射阶段
   把这块稀疏 ROM 做了大量优化（6387 项只占 16,384 地址空间的 39%，且有连续段可压缩）。
   **RTL 的 gate 数与最终 LUT 数之间没有可用的换算关系。**
3. **唯一可信的口径是 lab1↔lab3 的差分**：
   - `u_hdmi_mixer`：lab1 **46 LUT** → lab2 **6 LUT**（几乎旁路）→ lab3 **2,572 LUT**
   - 全设计 slices：lab1 12,358 → lab2 12,926（**+568**，纯 Sobel，`edge_detect_96` 自身 286 LUT + 155 FF）
   - **lab3 14,852（+1,926 vs lab2，+2,494 vs lab1）**
   ⇒ **OSD 的增量是"lab1→lab3 的 +2,494 slices"，其中 `u_hdmi_mixer` 自身 +2,526 LUT。**
4. **⇒ 因此 `logo_rom_README.md` §0 的"净收益 ≈ −2,399 LUT6"应当标为"未经证实"。**
   合理的区间是：**把整块 OSD（Logo + 动态文本）搬进 ROM 化实现，gate 级目标 ≤ 1,000 LUT**，
   相对 lab3 的 2,530 LUT 有 **~1,500 LUT 的空间**，但**必须用一次 P&R 实测确认**。

### 2.3 但"搬进 ERAM"这件事**仍然应该做**，理由换成时序

`hdmi_mixer.v` 里 Logo 通路是**纯组合**：

```verilog
always @(*) begin                       // L560 起，全组合
    ...
    S_logo_addr = S_logo_y * LOGO_W + S_logo_x;   // L619 常量乘 160 → 用掉 1 个 DSP
    if(S_logo_pixel[24]) begin                    // 6387 项稀疏 case 的组合输出
        S_osd_hit   = 1'b1;
        S_osd_color = S_logo_pixel[23:0];
    end
    ...
end
```

**这条链是：坐标计数器 → 常量乘 → 稀疏 16K LUT → 命中判决 → `O_hdmi_data` 选择器**，
全部塞在一个 75 MHz（13.333 ns）周期里。**这就是 HDMI 域 SSLACK 只剩 0.103 ns 的直接原因。**

**改成 ERAM（同步读、输出寄存）之后**：

- 组合链从"乘 + 16K 稀疏 LUT + 判决"缩到"一次加法 + ERAM 同步读"；
- **同时**把常量乘 160 从 DSP 里拿掉（lab3 比 lab1 多的那 1 个 DSP 就是它）；
- **以及**把 `hdmi_mixer.v` 里 4 处重复的 16 路 `case(S_pf_col)` 和像素率路径上的
  `S_pf_scale_x / 10'd24`、`/ 10'd15`、`/ 10'd8` 三处常量除法一并清掉
  （局部坐标只有 24/15/8 个取值 → 应改为查表）。

**⇒ 建议把 `logo_rom_README.md` 的"预期收益"表改成以时序为主目标、面积只写"待实测"：**

| 指标 | 改前（lab3 官方实测） | 目标 | 证据强度 |
|---|---|---|---|
| `HDMI_PIXEL_CLK` SWNS | 0.103 ns | **≥ 1.5 ns** | 时序结构上必然改善（组合链断裂） |
| slices | 14,852 (70.00%) | **待实测**（原文档写 ≤12,500 无依据） | 需 P&R |
| DSP | 9 | **8** | 常量乘 160 被移除，确定 |
| ERAM | 40 | **46**（+6，ROM depth 13724 × 8 bit = 109,792 bit ÷ 20,480 = 5.36 → 6 块） | 容量算术，确定 |

## 3. 本轮新增的硬件层事实

### 3.1 `video_out` 是双向握手的（风险降级）

```verilog
// design_top_wrapper.v:635
video_out u_video_out(
    .O_video_out_rd_busy ( S_video_out_rd_busy  ),   // 显示侧忙 → 送给 video_in
    .I_video_in_wr_busy  ( S_video_in_wr_busy   ),   // 写入侧忙 → video_out 让路
    ...
);

// video_in.v:49
assign O_video_in_wr_busy = S_ddr_wr_valid;
```

⇒ **写侧让读侧、读侧让写侧，两条 busy 互锁。**
既有文档"单端口仲裁没有 transaction tag，唯一真实风险是写饿死读"的判断**应降级**：
RTL 里已经有互让机制。

⚠ **但要注意新的风险**：互锁在极端拥塞下可能变成**互相让路导致双方都降速**（活锁/效率塌陷），
而不是饿死。**这一点必须在 P7（帧差）立项前用"零争用窗口"实测区分**——
既有文档的"新思路 E（区域快门）"恰好就是为这个实验准备的，**价值因此上升**。

### 3.2 `video_in` 的整行突发缓冲（既有文档未记录）

```verilog
// video_in.v:140 (RTL 注释原文)
// fifo的深度是512，实际的深度是510，因此需要注意每次读出的长度避免是256，
// 否则连续两次读写会引起fifo读空，丢失数据

// video_in.v:148
else if(S_fifo_rd_num >= 'd240 && (!I_video_out_rd_busy) && (!S_fifo_rst))
```

⇒ **写通道是"攒够约 240+ 个 128-bit 字（≈960 px）才突发"**，且被显示忙信号门控。
**含义**：如果新算法在 ISP 域引入长延迟或反压，**会先撑爆这个 510 深的 FIFO**，
表现为**撕裂/丢行**而不是"降低帧率"。**调试时看到画面横向错位，先怀疑这里。**

### 3.3 帧缓冲地址布局与真实空间

```verilog
// video_in.v:40-43 与 video_out.v:43-46 完全一致
localparam IMAGE_BASE_ADDR_0 = 25'd0;
localparam IMAGE_BASE_ADDR_1 = 25'd7000000;
localparam IMAGE_BASE_ADDR_2 = 25'd14000000;
localparam IMAGE_BASE_ADDR_3 = 25'd21000000;
```

| 项 | 值 |
|---|---|
| 地址位宽 | 25 bit → 32 M 字 × 16 B = **512 MB 寻址空间**（但器件只有 64 MB） |
| 帧步长 | **7,000,000 字 × 16 B = 112 MB**？→ ⚠ **注意单位**：`O_ddr_user_addr` 是**字地址**，128 bit/字 ⇒ 每帧 7,000,000 × 16 B = **112 MB**，4 帧 = 448 MB **超出 64 MB** |
| 实际占用 | 每帧有效 1280×720 × 16 B/4px = **3.686 MB**；4 帧 = 14.7 MB |

> ⚠ **这里有一处需要澄清的矛盾**：若 `O_ddr_user_addr` 按 128-bit 字寻址，7,000,000 字 = 112 MB/帧，4 帧 448 MB ≫ 64 MB。
> **更合理的解释是该地址按"16-bit 半字"或按 DDR 的 32-bit 粒度映射**，物理上 7,000,000 单元 ≈ 3.5 MB 或 1.75 MB。
> **既有文档 §0.5-C1 写的是"4 帧基址间距 14 MB × 4 = 56 MB < 64 MB ✓"，与本轮读到的 7,000,000 步长不一致。**
> **⇒ 行动项：打开 `mc_to_user_interface.v` 确认 `I_ddr_user_addr` 到 `mc_app_addr` 的单位换算，再定论。**

### 3.4 真实时钟约束来源（既有文档没有记录）

`rtl_vendor/.../td_project/camera_to_dsi_display.sdc`（**仅 17 行**）：

```tcl

create_clock -name {mipi_rx_ck_pad} -period 4.167 [get_nets {IO_rx_clk_pad_p}]

1. **`user_source/constraints_source/timing.sdc` 是 0 字节空文件** —— 真正生效的是 `td_project/camera_to_dsi_display.sdc`。

   （当前 CDC 由 `w128_d512_fifo`、`w155_d512_fifo`、`w40_d512_fifo` 三个 Soft_FIFO 承载，都是明文 IP。）

### 5.3 数据面上一个被忽略的杠杆：**算法中间态放 ERAM，不要绕 DDR**

| 资源 | 总量 | 已用（lab3） | 空闲 |
|---|---|---|---|
| ERAM（20 Kbit/块） | **108 块 = 2,160 Kbit = 270 KB** | 40 块（37%） | **68 块 = 1,360 Kbit = 170 KB** |
| 帧缓冲 | 4 × 7 MB 分配，每帧实际用 3.686 MB | 14.7 MB 有效 | **64 MB 中约 49 MB 空闲** |
| DSP | 40 | 9（22.5%） | 31 |

**170 KB 空闲 ERAM 能装什么**：

- 1280×720 单通道 8-bit 灰度整帧 = **921.6 KB** → **装不下**
- 640×360 单通道 8-bit = 230 KB → **装不下**（但差的不多）
- 320×180 8-bit = **57.6 KB** → **约 24 块 ERAM，装得下，还剩 44 块**
- 160×90 8-bit = **14.4 KB** → **约 6 块 ERAM**
- 一行 1280 px 的 3 行窗口 8-bit = **3.84 KB** → 极便宜

**⇒ 结论**：**帧差法（P7）不需要读 DDR 的上一帧** —— 
把上一帧的 **1/8 缩略亮度（160×90，14.4 KB，6 块 ERAM）**存在片上，
就在 ISP 域本地完成帧差，**零 DDR 读带宽、零跨域搬运**。
这与既有文档"新思路 A（160×90 缩略图做 CCL）"共用同一份基础设施，**边际成本接近 0**。

⚠ **但要诚实**：既有文档已提出"在显示读通道旁路 + ERAM 存上一帧 1/8 缩略亮度"。
**本轮的增补是把它从"可选优化"提升为"应该作为默认方案"**，理由是 ERAM 有 170 KB 空闲、

`src/uifdma/uifdma_axi_ddr.v` 第 327–374 行把 `ddr_ip u_ddr_phy` **所有端口都接成了 `()`**（空连接），

```

⇒ **该工程没有 `.area` / `.qor` / `final_timing.rpt`**（综合都没过）。
唯一的时序数据是 `td/test_Runs/best_result/test_phy.ts`：

### 9.6 架构对比的正确表述

`32_cs500` 与 `lab_ex3` 都是 **DDR 做帧缓存**（这一点既有文档说对了），差别在**总线抽象层**：

| | `lab_ex3`（赛题主线） | `32_cs500` |
|---|---|---|
| DDR 接入 | 手写 `video_in`/`video_out` + `mc_to_user_interface` 直连 DDR **原生 MC 用户口**（128 bit、240 拍突发） | `uiFDMA` 走 **AXI4 256-bit**，`uidbuf` 做 2D stride（每行一次传输，60 拍） |
| 帧槽 | **4 槽**，`rp = wp+2 mod 4`，25 bit 地址 + `addr+=8`/拍（单位 2 B） | **3 槽**，槽距 `2^25` = 32 MB，`read = write − 2` |
| ISP | 完整：demosaic(BGGR) + AWB + 宽高变换 | 极简: `raw8_2_rgb888` + `awb` + 黑边，**无 OSD** |
| 突发长度 | 240 beat × 16 B = 3840 B = **整行** | 60 beat × 32 B = 1920 B = **1920 个 RAW8 像素 = 整行** |
| 可编译 | ✅ 有完整报告 | ❌ **SYN-8511 综合失败** |

⇒ **结论：`32_cs500` 不能作为"另一套可跑的架构"来对比，只能作为 RTL 素材库。
主线应继续以 `lab_ex3` 为基础。**

### 9.7 顺带确定的两件事

1. **`awb2.v` 用的是"整帧累加 + 帧末除法"思路**：`den={acc_red,1'b1}`、`num={acc_green,13'b0}`，
   增益是 **16 bit 4.12 定点**（初值 `16'h1000`=1.0），逐像素 `r_in_r * r_acc_r`，取 `[19:12]` 并饱和到 `0xFF`。
   **⇒ 这就是 §5.2 里 P1a "AWB 重构"要的目标形态，已有一个可参考的实现（只是它用了 2 个 `div_u42_u30`）。**
2. **`fs_cap.v`（73 行）是干净的异步复位/边沿捕获原语**：4 级 `ASYNC_REG` 同步器 + 上升沿脉冲。
   **⇒ 可作为 P3 里"跨域只搬一个标量"（延迟时间戳）的实现模板。**

## 10. 把"最差路径"这条链彻底钉死（本轮最关键证据的合流）

前几节分别得到：① lab3 最差路径在 MIPI 域（7.869 ns）；② Logo 通路是纯组合。
**下面是第三个独立证据，三者完全一致。**

### 10.1 综合（gate）阶段 HDMI 域**根本没有收敛**，而根因就是 `u_hdmi_mixer`

`syn_1/gate.qor` + `camera_to_dsi_display_gate.timing`：

```
Setup WNS : -1296 ps      TNS : -21458 ps      违反端点 : 24 / 2808
（全部落在 HDMI_PIXEL_CLK 域）

最差路径 Begin : u_hdmi_mixer/mult0_syn_59.clk
        End   : u_hdmi_mixer/O_hdmi_data_reg[19].d
        数据延迟 14.565 ns  vs  预算 13.333 ns      ← 超 1.232 ns
        构成：cell 5.965 (40%) / net 8.600 (60%)
        逻辑级数 14（LUT6=6  LUT5=4  LUT2=2  DSPMULT=1）
        Max fanout 522                                  ← 注意这个扇出
```

**三个要点**：

1. **起点是 `u_hdmi_mixer/mult0`** —— 就是 `S_logo_y * LOGO_W` 那个"常量乘 160"的乘法器（占 1 个 DSP）。
2. **终点是 `O_hdmi_data`** —— 就是 §2.3 里那句
   `if(S_osd_hit) O_hdmi_data <= S_osd_color; else ...` 的 OSD 覆盖选择器。
3. **扇出 522** —— 这是 `S_osd_hit / S_osd_color` 这条组合链被广泛使用的直接证据。

### 10.2 三个阶段的故事（全部来自 TD 报告原文）

| 阶段 | Setup | Hold | 说明 |
|---|---|---|---|
| **综合（gate）** | **WNS −1.296 ns / TNS −21.458 ns，24 端点违反** | WNS +0.114 ns，0 违反 | **HDMI 域在综合阶段是失败的**，全在 `hdmi_mixer` |
| **布局（place）** | WNS +1.269 ns，0 违反 | **WNS −0.281 ns / TNS −75.052 ns，578 端点违反** | 布局把 setup 救回来了，但引入大量 hold 违反（DDR PHY 的 `ctl_wdata`/`ctl_te`） |
| **布线（route）** | WNS **+0.103 ns**，0 违反 | WNS +0.020 ns，0 违反 | 最终"收敛"，但只剩 **0.8%** 余量 |

**⇒ 这就是为什么说"Logo/OSD 搬进 ERAM"是必须做的**：
它不是一个面积优化，而是**把一条在综合阶段就失败、靠布局侥幸救回、最终只剩 0.103 ns 的组合链彻底砍断**。

> **⚠ 一处必须说清的细节（避免误读）**：
> **HDMI 域是"绝对更紧"，MIPI 域是"绝对延迟更大"**，两者不矛盾：
> - HDMI：延迟 12.858 ns / 预算 13.333 ns → **用了 96.4%**，余 0.103 ns
> - MIPI：延迟 8.483 ns / 预算 16.668 ns → 用了 50.9%，余 7.869 ns（但 Fmax 113.6 MHz ≈ 预算的 1.9 倍）
>
> **⇒ 结论不变**：P1b（Logo/OSD）解决的是"最紧的那条"；
> P1a（AWB）解决的是"绝对延迟最大、且决定 ISP 域能否提速的那条"。**两件都要做，且有先后依赖。**

## 11. PH1P 的 DSP 到底是什么（**本节结论已被网络资料推翻，以网络资料 + IP 默认值为准**）

### 11.1 三个来源，两个数值，必须说清谁对

| 来源 | 说的是什么 |
|---|---|
| **安路官网 PH1P 产品页**（<https://www.anlogic.com/product/fpga/phoenix/ph1p>）产品特色原文 | "可支持两输入加法器、三输入加法器、乘法器和算术逻辑单元 / **支持独立的 27x18, 9x9 乘法器**" |
| **本地 IP 默认值** `F:\al\ip\depot\DSPF9F0D0P0_2.0\Component.xml`（第 1767–1806 行，**resolve="user" 的出厂默认**） | `A_INPUT_WIDTH = 18`、`B_INPUT_WIDTH = 18`、`Y_INPUT_WIDTH = 18`、`Z_INPUT_WIDTH = 54`、`P_OUTPUT_WIDTH = 54` |
| 本地 RTL 模板 `dsp_macro_0.v` 的 **parameter 声明默认值** | `A_INPUT_WIDTH = 26`、`B_INPUT_WIDTH = 26`、`Y = 17`、`Z = 53`、`P = 53`；内部 `a_in = {{(27-A_INPUT_WIDTH){…}}, A}` 补到 **27 bit** |

**判读**：

- 官网的 **27×18** 与 `dsp_macro_0.v` 内部补到 **27 bit** 完全吻合 ⇒ **27 位那一侧是硬件的真实宽度**。
- **IP 生成器的出厂默认是 18×18，不是 26×26。** 这说明 **26 只是 RTL 模板的一个更宽的默认写法**，
  **不是硬件规格**。此前分析把"模板的 parameter 默认值"当成了"器件原语规格"，**这是错的**。
- **本轮更正**：`增量分析与新思路-2026-09-18.md` 的 **N8** 条（"PH1P 的 DSP 是 26×26 → 53 bit 的可配置宏"）
  **应改为"27×18 乘法器 + 54 bit 累加器（端口宽度由 IP 生成器配置，默认 18×18）"**。
- **53 变 54**：`dsp_macro_0.v` 的 53 是模板默认，`Component.xml` 的 54 是 IP 默认。
  两者都是"可配置"，**因此"累加器位宽"本身也不是固定结论** —— 这一点网络资料也没给出定论。

### 11.2 现在还**不能**确定的那一半（诚实标注）

官网写的是"支持**独立的** 27x18, 9x9 乘法器"。**"独立"这个词有歧义**：

- **读法 A**：一个 DSP 内可以**同时**跑一个 27×18 和一个 9×9，即**同一拍出 2 个乘积**（"双乘法器"宏）。
- **读法 B**：DSP 可以在 27×18 模式**或** 9×9 模式之间配置，即仍然是**每拍 1 个乘积**。

**本轮查证结果**：`Component.xml` 里**只有 `USER_INSTRUCTION0..7`（8 条指令）+ `SEL`**，
**没有任何"宽度模式"开关**（可配参数清单里没有 mult-mode / dual-multiplier 之类的项）。
`dsp_macro_0.v` 里也**只有一个乘法器**（`a_in`/`b_in` → 一个 `P`）。

⇒ **读法 B 更可能（每拍 1 个乘积，8 条指令可逐拍切换）**，但**"9x9 模式"或"双乘法器"在本地 IP 里看不到入口**。

**⇒ 行动项（比之前的表述更准确）**：**打开 TD 的 DSP IP 向导界面截图核对**——
看有没有"Multiplier Mode / 27x18 / 9x9"这类下拉项。**这是半天成本、决定后续乘法预算的事。**
在有结论之前，**方案应按"每拍 1 个乘积、27×18、54 bit 累加"来算**，这是目前证据支持的下界（保守但安全）。

### 11.3 对方案的实际影响（这部分的结论不变）

| 情形 | 做法 |
|---|---|
| **可变系数乘法**（AWB 增益） | 用 DSP，**靠"分时复用"**：像素率只有 **0.23 beat/clk**，4 个像素的 R 增益可**串行用同一个 DSP 分 4 拍完成**，B 增益同理 ⇒ **8 个乘法器 → 2 个 DSP** |
| **常量系数乘法**（3×3/5×5 卷积、量化、CSD） | **一律走移位-加法，绝不用 DSP**（`S_logo_y*160` 就是反例，它占掉了 lab3 比 lab1 多的那 1 个 DSP） |
| **单拍内并行多个乘法** | **在证据明确之前，不要假设可以**。要并行就多开 DSP，或分时。 |

**⇒ 好消息**：官网的 27×18（而不是 26×26）**对 8 bit 图像算法完全够用**——
图像乘加最宽是 18×18 级别的系数×像素，27 位那一侧还有大量余量。
**⇒ 结论不变：AWB 从 8 个 DSP 降到 2 个 DSP 是确定可回收的资源，这是本轮最确定的收益。**

### 12.2 ERAM 的真实结构（对"Logo 搬进 ERAM"有直接影响）

`UG902_安路科技PH1A系列FPGA ERAM用户手册`（同系列，命名规则一致）：

- **一个 ERAM SLICE = 2 × ERAM20K + 1 个 FIFO 控制器。**
- **ERAM20K = 固定 20 Kbit/块**（**没有** Xilinx/Altera 那种 18K/36K 分割）。
- 模式：SP（单口 RAM/ROM）、TDP（真双口）、SDP（简单双口）；**A/B 时钟独立**。
- 位宽：x1~x20，SDP 下可到 x40；**SDP 有硬 ECC**。
- **字节使能**：开启后 `addr_a[13:4]` 变成地址、`addr_a[3:0]` 变成 `byteena[3:0]`（**10 bit = 1 字节**）。
- 写模式：SP 支持 WDR/RBW/WBW；TDP 只支持 WDR+WBW；SDP 只支持 WDR。

> ⚠ **手册里一条硬约束，必须遵守**：
> **"ERAM 的地址与数据输入必须与输入时钟同步"**，否则工具**不会对这些路径做时序分析**，
> **ERAM 内容可能不可预测地翻转**。
> **⇒ 这正好解释了为什么 `logo_rom_README.md` 强调"Output Register = OUTREG（默认，同步读）"——
> 那不是可选项，是 ERAM 的硬性要求。** 应把这条写进 P1b 的验收项。

**ERAM vs DRAM（分布式 RAM）的实用差别**（<https://blog.csdn.net/bxlover007/article/details/124608165>）：
> *"不管是 FIFO 还是 RAMFIFO 都不支持读写不同的时钟…只能使用 RAM 进行读写切换；DRAM 也不支持不同的读写时钟"*

⇒ **ERAM 是设计里唯一能跨时钟域做缓冲的资源**；
且**每个 ERAM slice 自带 FIFO 控制器，应该直接用，不要用 LUTRAM 自己搭 FIFO。**
