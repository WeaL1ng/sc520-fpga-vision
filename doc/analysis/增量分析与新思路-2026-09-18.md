
### 1.6 N9：DDR 写通道 25% 浪费（RTL 级证实）

`user_source/hdl_source/data_96bit_to_128bit.v` 的打包逻辑：

```verilog
'd1: O_128b_data <= {S_96b_data_1d, I_96b_data[95:64]};   // 96+32，末 32 bit 为填充
'd2: O_128b_data <= {S_96b_data_1d[63:0], I_96b_data[95:32]};
'd3: ...
```

`S_cnt` 在 0~3 循环，只有 3 拍产出有效 128 bit 字，且每字装 4 px × 24 bit ⇒ **每 4 像素补 32 bit 零，写 4 B/px 而有效 3 B/px**。
⇒ 写带宽 221.2 MB/s 中约 **55.3 MB/s 是零**（占用户口 5.2%）。

**价值**：若能改成紧凑打包（3 拍 96 bit → 重排成 4 拍 128 bit，或改帧缓冲为 24bpp packed），**白捡 5.2% DDR 用户口带宽**——正好可以抵掉 1/2 子采样帧差法新增的读带宽（+110.6 MB/s 的一半都不到，但方向正确）。这是"不改架构、只改打包"的纯收益。

## 2. 新思路（本轮提出的架构级想法）

### 2.1 【新思路 A】在 160×90 缩略图上做**真正的连通域标记**——成本比预想低一个数量级

**背景**：`赛题二-文件全量分析与方案建议.md` §6.3-F 判断"不要做完整连通域标记（two-pass union-find 在 720p 上太贵）"，改用"颜色阈值 + 行列投影/ tile 统计"求包围框。

**但官方 PPT slide 21 给扩展要求 2 画的链路是**：
```
颜色/形状特征提取 → 阈值判定 → 【连通域/坐标计算】 → OSD 结果叠加
```
**"连通域"是官方点名的环节**。用投影统计只能得到"一个全局包围框"，**无法区分多个目标、无法按目标计数、无法报"类别/坐标/数量"三件套**（而 PPT slide 21 明确要求输出"检测结果 类别/坐标/数量"）。

**新思路**：既有方案已经为了运动检测（P7）和抓拍（网络模块）建立了 **8×8 块下采样 → 160×90 缩略图**基础设施。**在这个缩略图上做 RLE（游程）+ 单遍连通域标记，成本极低**：

```
输入：160×90 二值掩码（= 14,400 像素，来自 8×8 块平均后的颜色判定）
① 游程编码：每行把连续 1 压缩成 (x_start, x_end) 段，每行最多 ~20 段
② 单遍 union-find（RLE 版）：
   · 每段与上一行的重叠段做并查集 merge —— 只比较重叠的段，不是像素
   · 标签表：2,048 项 × 11 bit ≈ 22.5 Kbit → 用 LUTRAM 或 2 块 ERAM
   · 每行处理完立即合并，第二遍（等价类替换）也只作用在段上
③ 输出：每个连通域 → 面积 / bbox / 质心 / 填充率 → 排序取 Top-N
```

**成本对比**（估算，需上板校准）

| 方案 | LUT | ERAM | 能力 |
|---|---|---|---|
| 现有方案：颜色阈值 + tile 统计 + 全局 bbox | ~800 | 2 | 单一全局框、计数、填充率判形状 |
| **新方案：阈值 + 8×8 缩略 + RLE 单遍 CCL** | **~700~900** | **2~4** | ⭐ **多目标、每目标各自的框/面积/质心、按目标计数、可跨帧关联（跟踪）** |

**为什么划算**：CCL 的复杂度对**段数**而不是**像素数**敏感。8×8 降采样把 921,600 像素变成 14,400 像素，段数每行只有个位数到几十。**而且下采样前端 P7/网络模块本来就要建**（边际成本接近 0）。

**顺带拿到的能力**
- **高阶要求 2「目标跟踪与信息标注」**：有了多目标 bbox，跨帧做最近邻关联（`|cx_new − cx_old| < TH`）就能给每个目标分配稳定 ID → OSD 显示 `T1 (312,208) 48x40`，这是真正的"跟踪"，而不是"每帧重画一个框"。
- **扩展要求 2 的"数量"**：`N=3` 变成真的 3 个目标，而不是"总命中面积/某常数"。
- **`bound_cut.v` 可参考**（见 §1.7）。

**风险**：合并逻辑（union-find）是控制密集型状态机，时序不友好 → **应放在慢时钟域**（每行只有 160 个像素要处理，`MIPI_RX_BYTE_CLK` 的消隐期或新算法域都绰绰有余）。**这是一个"用时间换面积"的典型场景。**

### 2.2 【新思路 B】片上 RISC-V MCU 的**合规用法**：做"决策层"，不做"算法层"

**背景**：Q&A 明确"赛题二只有扩展要求三才允许额外处理器，且赛题指标要求部分需要在 FPGA 上实现"。既有文档因此建议"AE/AWB/模式切换都别放 MCU"。

**新思路**：这个约束的严格读法是"**赛题指标要求的部分**必须在 FPGA 逻辑里"——但**赛题指标里没有"串口协议解析""菜单状态机""文本缓冲排版"**。所以正确切分是：

| 层次 | 放哪 | 理由 |
|---|---|---|
| **算法层**（灰度/边缘/卡通/颜色检测/运动检测/CCL/直方图） | **FPGA 逻辑**（硬件流水线） | 这是赛题指标，且是"低延迟"叙事的核心。**绝不下放** |
| **统计与反馈层**（AE/AWB 闭环、阈值自适应、延迟测量） | **FPGA 逻辑** | 基础(4)"光线剧烈变化"是显式评分条款，且这是"全硬件闭环"的演示点 |
| **决策/交互层**（按键菜单、模式名与数值的 OSD 文本排版、UART 协议组包、GPS NMEA 解析、阈值下发） | **片上 MCU（RISC-V @300 MHz）** | 纯控制流，**不产生像素**；放 MCU 省下 FPGA 面积（`tlm_pack` ~350 LUT + `osd_render` 排版 + NMEA 解析 ~450 LUT） |
| **不允许**：把任何一帧图像处理交给 MCU | — | 违反"赛题指标要在 FPGA 上实现"，且 MCU 无视频带宽 |

**具体收益**（相对既有方案）

| 项目 | 原方案（FPGA 逻辑） | 改为 MCU | 省 |
|---|---|---|---|
| OSD 动态文本排版（格式化 "LATENCY: 12ms"、坐标、AE 值） | `osd_render` 内做整数→ASCII 转换 ≈150 LUT | MCU 写文本缓冲（内存写），FPGA 只做"字符缓冲 → 字模位" | ~150 LUT |
| 遥测组包（帧头/CRC16/分片状态机） | `tlm_pack` ~350 LUT + `md_ctrl` ~120 LUT | MCU 软件组包，FPGA 只给一个寄存器窗口 | ~450 LUT |
| GPS NMEA 解析 | `GGA.v` 158 LUT + 4 DSP | MCU 软件解析 | ~158 LUT + 4 DSP |
| 串口下行命令解析 / 阈值下发 | 自写命令状态机 ~150 LUT | MCU | ~150 LUT |
| **合计** | | | **≈ 900 LUT + 4 DSP**，并**白送 2 个 UART**（UART0 接 GPS、UART1 接 PC） |

**代价与风险**
- 需**装 FD 软件 + 确认固件下载方式**（FD 支持 PH1P35，见 §1.3），并让 MCU 与 FPGA 通过 **AHB/APB 寄存器块**通信（MCU IP 有 `AHB_Available:1`、`APB_Available:1`）。
- MCU 与 FPGA 时钟域不同（MCU 300 MHz 核 / AHB 150 MHz），**跨域必须走寄存器 + 双触发器或异步 FIFO**。
- **上电即跑的约束**：MCU 固件要与 bitstream **一起固化**（QSPI Flash 够大，128 MB），否则"上电即跑"破功。**这一点必须先确认 FD 的固化能力**，否则整个方案不能用。

> **建议的落地策略**：**不要在主线一开始就用 MCU**。先在 P3（OSD 文本子系统）阶段用 FPGA 逻辑做一个最小可用的文本缓冲，把 P3 交付；**同时花 1~2 天做 MCU 的"hello world + 寄存器读写"验证**（这相当于原方案的 P9 前置验证）。验证通过后，把"遥测组包 + GPS 解析 + 命令解析"逐步迁到 MCU。**这样即使 MCU 路线失败，主线也不受影响。**

### 2.3 【新思路 C】把"显示读旁路"从 RGB 升级为 **RGB+Alpha（32 bpp）**——一次改动换三条链路

这是本轮我最看好的**低成本/高杠杆**改动，理由是它把三件独立的事合并成一件。

**背景**：
- `data_96bit_to_128bit.v` 打包 4 px × 24 bit = 96 bit，**每 4 像素补 32 bit 零**（§1.6 N9）。
- DDR 写 4 B/px、读 3 B/px（`video_out` 拆 32bpp → 24bpp，16 px / 3 次读）。
- P5 目标检测、P7 运动检测、网络模块抓拍，三者都想"旁路显示读流取数"，但**渲染框/文字都需要在 `hdmi_mixer` 里做，而它们的统计结果又要跨回 ISP 侧**，方案里为此做了复杂的跨域搬运。

**新思路**：把**每个像素的 Alpha/标签位**顺路存进 DDR 那个**本来就浪费的 32 bit 空位**。

```
写侧（ISP 域 / 算法域）：
   data_128 = { 4 px × 24 bit RGB , 8 bit 标签 }        ← 32 bit 空洞刚好装 8 bit/4px
   标签位用途（4 px 共享 8 bit）：
     bit[7]   = 边缘（形态学梯度阈值命中）
     bit[6:5] = 颜色类别（01 橙 / 10 红 / 11 蓝）
     bit[4]   = 运动（sigma-delta 命中）
     bit[3]   = 检测框内
     bit[2:0] = 形态学/其它算法标志（或 8×8 块内辅助信息）

读侧（HDMI 域）：
   video_out 同时取出 RGB 与 8 bit 标签 → hdmi_mixer 直接用标签做像素级叠加
```

**收益（一次改动，三处受益）**

| 收益 | 说明 |
|---|---|
| **① 零额外 DDR 带宽拿到"像素共位标签"** | 标签用的是**已经写进去的零**。不增加任何一次 DDR 事务 |
| **② 彻底消除"框与物体错位"问题** | 现在方案靠"统计在 HDMI 域、框也在 HDMI 域、晚一帧可接受"来回避错位；有了标签，**框/高亮/着色与像素严格共位**，且可以做"目标内部半透明着色"（比画空心框更直观） |
| **③ 简化多算法叠加** | "卡通化 + 目标高亮 + 运动区域"可以**同时叠加**（标签是并行的位），而不是互斥的模式切换——**画面上同时展示多种处理结果，答辩视觉冲击强得多** |
| **④ 顺手把 §1.6 的 25% 写浪费变成"有用的 25%"** | 不再需要为"紧凑打包"改动帧缓冲格式（那会牵动 `video_out` 的 16px/3 读逻辑，风险高） |

**代价与风险**
- `hdmi_mixer` 要多接收 8 bit 标签并做像素级判决：**约 +150~250 LUT**，且**必须在 75 MHz HDMI 域内流水线化**（该域**在本轮实测的新工具基线上只剩 0.006 ns**、官方基线上 0.103 ns，**必须先做 P1 把裕量拿回来再动**）。
- 需要修改 `data96_128`/`data_128_96` 的拆包与 `video_out` 的 32bpp→24bpp 逻辑，**但改动是"填零位"变"填标签位"，结构不变**，比改位宽安全。
- DDR 读仍然是 4 B/px（`video_out` 现在就把 32bpp 全读出来了），**所以读侧带宽不变**——这正是它便宜的原因。

> **⚠ 时序前提**：这一项**必须在 P1（Logo→ERAM + OSD 流水线化）完成、HDMI 域裕量回到 ≥1 ns 之后**再做。
> 顺序：P0 → P1 → **C（标签通路）** → P4/P5/P7 全部挂到标签上。

### 2.4 【新思路 D】不用摄像头也能开发与演示——"测试图源 + 环回"模式

**动机**：赛题要求自购 SC500CS（有出货周期），且现场演示最怕"摄像头初始化失败 → 黑屏"。

**资产已在手，但需要看清它到底是什么（本轮逐行核实，修正了一处想当然）**

`2_Example/32_cs500_mipi_hdmi/src/video_source_test.v`（仅 121 行）实测是一个**视频时序 + 渐变图源**，**不是彩条**：

```verilog
module video_source_test #(
    parameter HTOTAL=2200, HACTIVE=1920, HFP=88, HSA=44, HBP=148,
    parameter VTOTAL=1125, VACTIVE=1080, VFP=4, VSA=5, VBP=36 )   // 默认 1920×1080
( input I_clk, input I_rst, input I_tpg_trig_en,
  output reg O_video_user,      // 帧首（tuser）
  output reg O_video_valid,     // 数据有效
  output reg O_video_last,      // 行尾（tlast）——注意是"行尾"，不是帧尾
  output wire[23:0] O_video_data,
  input I_video_ready );
    ...
    assign O_video_data = {8'd0, 8'h0, S_tpg_data};   // R = 0..255 递增，G=B=0  → 红色渐变
```

**它的真实用法**（`32_cs500_mipi_hdmi/src/hdmi_tx.v:146-168`）：喂给 `hdmi_1_4b_transmitter_core_wrapper` 的
AXI-Stream 视频输入口，`I_tpg_trig_en` 硬接 `1'b1`。
**即：它是"给 HDMI IP 灌测试图"用的，不是"接在 ISP 入口"的。**

> ⚠ **另一个本轮才发现的事实**：那个加密的 HDMI 1.4b 发射器 IP（`hdmi_1_4b_transmitter_core_wrapper.enc.v`）
> **本身带一个 `VIDEO_TPG` 参数（默认 `"Enable"`）**，即 **IP 内部就有测试图发生器**；
> 它还有 **EDID 读取接口**（`I_edid_read_trig` / `O_edid_read_valid` / `O_edid_read_data`）。
> 这两点都值得后续挖掘（EDID 读取可用于"显示器能力自检"，是很强的稳定性演示点）。

**所以正确的做法是分两层（成本不高，但要写对位置）**

```
① 【HDMI/OSD 链路的无摄像头验证】—— 最便宜，先做
   在 hdmi_tx 的视频输入口接彩条/棋盘发生器（或试把 hdmi IP 的 VIDEO_TPG 置 "Enable"）
   → 立刻可验证：TMDS 编码 / uivtc 时序 / hdmi_mixer OSD / DDR 读通路 / 显示器兼容性
   → 这已能覆盖 P1（Logo→ERAM + OSD 流水线化）的大部分验证需求

② 【ISP + 算法链路的无摄像头验证】—— 稍贵，但价值更大
   把图源注入点放在【CSI 解包之后、ISP 之前】，这样 demosaic / AWB / 算法 / OSD 全链路都被锻炼到。
   两条可选路径：
     (a) 复用 video_source_test.v 的时序骨架，把输出改成 ISP 期望的格式
         （ISP 输入是 40 bit = 4 px RAW10，或 96/128 bit RGB，取决于注入点）
     (b) 更稳：自写一个 AXI-Stream RGB888 图源直接替换 isp_top 的输入 mux，绕过 RAW10 解包
         （ISP 后半段与全部算法都跑到，只是不验证 MIPI 解包本身）
   → 需要一个 src_sel（原图/测试图）MUX + 按键或上电自动检测（摄像头未初始化则切测试图）
```

**一条捷径**：`video_source_test.v` 的**时序骨架（列/行计数器 + user/valid/last 生成）可以直接复用**，
只要把最后那行 `assign O_video_data = {8'd0,8'h0,S_tpg_data};` 换成彩条/棋盘/移动方块的生成逻辑即可。
**移动方块尤其值得加**——它让 P7 运动检测、P5 目标检测在没有摄像头时也能演示。

**收益**
- **立刻解除"等摄像头到货"的时间依赖**，Day 1 就能开始 P1/P2/P3。
- **P8 自检模式**的彩条页可以复用这个图源骨架，不需要另写（图样要换成彩条）。
- **演示保险**：现场若摄像头/软线接触不良，**一键切测试图，整套算法与 OSD 照常演示**（配合 OSD 显示 `SRC: TEST`）。
- 答辩时可以用"受控输入"演示算法的确定性与可重复性（比对着杂乱现场更有说服力）。

**代价**：图源本身便宜（计数器 + 图案生成 + MUX，**约 150~250 LUT**，可放 `sys_clk_50m` 或 ISP 域）；
**真正的成本在"想清楚注入点"与格式匹配**——建议先做 ①（半天），再做 ②（1~2 天）。

### 2.5 【新思路 E】区域快门：用一个按键把 DDR 占用率**降到 6.3%**

**动机**：DDR 用户口基线 36.3%（写 20.7% + 读 15.6%），加上帧差读会到 57%，而单端口仲裁没有 transaction tag，**唯一的真实风险是"写饿死读"**。

**思路**（极简、零额外硬件、且是很好的答辩素材）
- 加一个"**静态场景 / 冻结刷新**"模式：按键切换后，**停止 DDR 写入，显示侧持续重复读同一帧**（地址不变 → DDR 行命中，实际流量更低）。
- 效果：写 221.2 MB/s → 0；显示读 165.9 MB/s 基本不变（或可降到"只刷新必要区域"）。
- **用户口占用从 36.3% 掉到 ~15.6%**；若再配合"只在新帧到来时写"（本方案本来就是），**一个静态场景下总占用可低至 ~6.3%**。

**它能换来什么**
1. **提供一个"零争用窗口"**：在这个窗口里做帧差法的"读上一帧"实验，能干净地区分"带宽不够"和"仲裁不公平"两种失败模式——**这正是 P7 立项前必须做的实测**。
2. **低功耗叙事**：赛题注意事项写"推荐以优化的逻辑和最低的功耗来实现"。停止 DDR 写入是**真实的功耗下降**（DDR 接口占 FPGA I/O 功耗的大头），且可在 OSD 上显示 `PWR MODE: STATIC / DDR WR: OFF`。
3. **演示价值**：对着静止场景按键，画面完全不变但 DDR 写入停了——直观展示"我们连无用的写都省掉了"。

**代价**：~50 LUT（一个使能门 + 状态位）+ 对 `video_in.v` 的写使能加一个门控。**风险极低**。

> ⚠ 注意：不要用它替代"运动检测"——冻结刷新时运动检测会失效（因为新帧不写入 DDR）。**它定位为"演示 + 功耗 + 调试"功能，不是算法功能。**

### 3.3 P2 之后的顺序调整（重要）

既有方案在 P2 之后走 P3(OSD文本) → P4(卡通化) → P5(检测) → P6(AE) → P7(运动)。**本轮建议插入一项并调整一项**：

```
原:  P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8 → P9
新:  P0 → P1 → P2 → P3 → 【新 C: 标签通路】 → P4/P5/P7(挂到标签上) → P6 → P8
                    └→ 【新 D: 图源 MUX】(可与 P1 并行，见 E3)
                    └→ 【新 B: MCU 可行性 1~2 天】(独立支线，不阻塞主线)
```

**理由**
1. **C（标签通路）必须早做**：它决定 P4/P5/P7 的接口形态。**若等 P5 做完再改，等于返工。** 而它本身很便宜（填零位 → 填标签位 + mixer 加一级判决），前提只是 P1 先把 HDMI 域裕量拿回来。
2. **P4/P5/P7 合并到同一套标签上**：卡通化的边缘位、检测的颜色类别位、运动的位**可以同时存在**，不再是互斥模式。**"一屏同时展示卡通化 + 目标框 + 运动区域"** 比"按键切换看单个效果"的答辩效果好得多，而这**不需要额外算法**，只是把结果放进并行的位里。
3. **B（MCU）走独立支线**：花 1~2 天验证 FD + 固件固化，**成功则省 900 LUT，失败则主线无损**。不要把它排进关键路径。
