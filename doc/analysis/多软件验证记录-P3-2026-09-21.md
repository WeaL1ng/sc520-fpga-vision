## 3. ★ 本轮交叉验证抓出的两个真实缺陷

这是"多软件验证"价值最直接的体现 —— 两个缺陷**都不是靠单看 RTL 或单跑仿真能发现的**。

### 3.1 缺陷 1：新字形比既有字形**小一半**（视觉不一致）

**怎么发现的**：写 `verify_font_roundtrip.py` 时，为了做"往返比对"必须先确认
**原版字形的行范围约定**。反解原始 `osd_char_lib.v` 后发现：

| 字形 | 列范围 | 行范围 |
|---|---|---|
| 原版字母 `A B D E …` | 2..8 | **2..9**（8 行） |
| 原版数字 `0-9`、`C N Q T :` | 2..13 | **1..12**（12 行） |
| 我新增的小写/符号（第一版） | 0..13 | **0..6（仅 7 行）** ⚠ |

⇒ 上板后 `LATENCY: 42 ms` 的字会**明显比 `安路 CNT` 的数字小一半**。

**修正**：把 38 个新字形全部重画为 **8 行、行 2..9**（对齐字母风格），
并在生成器里把"图第 0 行 → 点阵 row 2"写成显式参数 `ART_TOP_ROW = 2`。

> **教训**：往既有字库加字形前，必须**先量出既有字形的真实规格**（列宽、行范围），
> 不能凭"8×16 点阵"想当然。这与铁律二同源。

### 3.2 缺陷 2：延迟文本区**压在 Logo 上**（137×16 像素重叠）

**怎么发现的**：写 `verify_osd_layout.py`，从 `hdmi_mixer.v` 抽取各区域常量算矩形：

```
Logo(安路)    (  7, 34)  146x94  →  列 7..152，行 34..127
延迟文本(P3)  ( 16, 48)  224x16  →  列 16..239，行 48..63
                                    ⇒ 重叠 137 x 16 ⚠
```

我原本以为"Logo 只占左上 160 像素、把文本放在 y=48 就安全" ——
**忽略了 Logo 纵向延伸到 row 127**，结果文本直接压在 Logo 下缘。

**修正**：移到 **(256, 48)**（Logo 右侧、动态文本 CNT 左侧），
重新校验：**5 个区域、10 组两两检查全部不重叠，无越界**。

> **教训**：新增 OSD 区域前，必须**量出所有既有区域的实际矩形**再选位置。
> 这类错误在仿真里很难发现（两边都"有像素"），但上板一眼可见。

## 4. 关键验证详解

### 4.1 `frame_latency`（8/8）—— 重点是"永不显示负延迟"

延迟测量有个**跨域语义陷阱**：`video_out.I_video_out_rp` 由 DDR 仲裁器产生，
与采集域帧号属**不同计数器**，固定偏移（`rp = wp+2`）一旦假设错误，
就会索引到**未来的标签**，32 位无符号相减**回绕成 42 亿 ms**。

TB 专门构造了这些场景：

| 用例 | 构造 | 断言 |
|---|---|---|
| T0 复位 | — | `valid=0` 且输出**占位值**（不是垃圾数字）✅ |
| T1 **标签超前** | 采集 5 帧后才开始显示 | **被跳过**，`valid` 保持 0，无回绕值 ✅ |
| T2 追平 | 显示帧号 ≥ 标签帧号 | `valid=1`，延迟 = **2 ms**（与构造一致）✅ |
| T3 连续 20 帧 | 采集/显示同速 | 无样本 ≥ 1000 ms ✅ |
| T4 采集停止 | 显示继续跑 | 无溢出 ✅ |

### 4.2 字库双向往返（38/38）—— 独立第二实现

| 环节 | 实现 |
|---|---|
| 生成侧 | `tools/gen_osd_char_lib.py`：ASCII 图 → 位运算 → 写 Verilog 16 进制 |
| 校验侧 | `tools/verify_font_roundtrip.py`：**从 Verilog 反解回 ASCII 图**，与生成器定义字符级比对 |

能同时抓住三类错误：**位序反（左右镜像）、行序反（上下翻转）、任何一位抄错**。

额外校验：77 个字形的常量与分支数一致；每个字形 16 行齐全；
外层 `case(I_char)` 与内层 `case(I_row)` 都有 `default`；
`CHAR_SP`（空格）必须全零（唯一例外）。

结果：**往返一致 38/38，结构校验通过，共 77 个字形**。

### 4.3 Logo 位置回归（dx=dy=dw=dh=0）

**为什么这轮特别重要**：P3 改动里 `hdmi_mixer.v` 是重灾区 ——
字库从 39 扩到 77 字形、新增一块文本区、插入流水寄存器。
必须证明**既有 OSD 元素没被破坏**。

方法（三个独立实现）：
1. **ModelSim** 跑两次（`+osd=0` / `+osd=1`），各导出 1280×720 逐像素；
2. **ModelSim** 断言两次 DE 有效像素数**精确 = 921,600**；
3. **Python** 从 `logo_pixel.mif` + `logo_palette.vh` 独立算期望包围盒，
   把两次仿真的**差集**当实测包围盒。

```
EXPECTED  SCREEN bbox : (7, 34, 146, 94)
MEASURED  bbox        : (7, 34, 146, 94)
delta : dx=+0  dy=+0  dw=+0  dh=+0
pixels differing IN win : 6293   (in palette: 6293,  not in palette: 0)
diffs OUTSIDE window    : 888    (= 安路 CNT 动态文字)
[PASS] Logo position and size match exactly - no 1-pixel shift
```

> **说明**：`I_osd_en` 只控制 Logo 与动态文字；延迟文本不受它影响，
> 故在 `osd=0`/`osd=1` 两次运行里**完全相同**，做差时被抵消，**不影响本判定**。

### 4.4 TD 报告独立解析

`tools/verify_td_reports.py` 用 Python 独立解析报告并做交叉核对：

| 校验 | 结果 |
|---|---|
| 资源不超 80% 警戒线 | slice 62.90% / lut6 51.86% / ERAM 44.44% / DSP 20.00% ✅ |
| 全局时序 | SWNS **+1.314 ns**、STNS **0.000**、HWNS +0.020、HTNS **0.000** ✅ 零违规 |
| Path Group 自洽 | 扫描 28 个含统计的 Path Group，**违例端点合计 = 0** ✅ |
| 各域 Fmax ≥ 约束 | MIPI +50.5% / HDMI_PIXEL **+16.5%** / HDMI_SERIAL +97.2% / usr_clk +44.2% ✅ |
| 关键模块 DSP/ERAM | `u_awb` DSP=**8**（8 个并行乘法器仍在）、`u_gray_binary_96` DSP=**0**、`u_logo_rom_eram` ERAM=**7** ✅ |
