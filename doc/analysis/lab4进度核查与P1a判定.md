## 2. 缺陷清单（5 个，其中 D1 是致命的）

### 🔴 D1 · TDM 像素索引步长写错（**致命，已定位，补丁未合入**）

工程 `awb.v:279-281` 原文：

```verilog
wire [7:0] cur_r = word_r[{mul_ph, 5'd16} +: 8];
wire [7:0] cur_g = word_r[{mul_ph, 5'd8}  +: 8];
wire [7:0] cur_b = word_r[{mul_ph, 5'd0}  +: 8];
```

`{mul_ph, 5'd16}` 的数值是 `mul_ph*32 + 16`（**步长 32**），
但 `word_r` 里 4 个像素的步长是 **24**（`B=[24k+:8]`、`G=[24k+8+:8]`、`R=[24k+16+:8]`）。后果：

- `mul_ph=1/2` 取到**别的像素的字节**；
- `mul_ph=3` 的基址是 112/104/96，**超出 96 bit 字范围 ⇒ 输出 `x`**。

**实测：每个输出字的高 24 bit（`px3`）全是 `x`**，158 字节里 16,235 字节不同，最大差 254。

**⇒ 这个缺陷意味着：现在这份 bitstream 烧上去，画面会是错的（至少每 4 个像素里坏 1 个）。**

候选补丁 `fix/awb_stridefix.v`（仅 1 处改动）已备且验证可消除 X：

```verilog
wire [6:0] px_base = (mul_ph == 2'd0) ? 7'd0  :
                     (mul_ph == 2'd1) ? 7'd24 :
                     (mul_ph == 2'd2) ? 7'd48 : 7'd72;
wire [7:0] cur_r = word_r[px_base + 7'd16 +: 8];
wire [7:0] cur_g = word_r[px_base + 7'd8  +: 8];
wire [7:0] cur_b = word_r[px_base + 7'd0  +: 8];
```

**⚠ 但补丁只是让 X 消失，剩下的差异仍然存在（见 D2/D3）。**

### 🟠 D2 · 增益算法与基线不等价（未修）

| 差异 | 基线 | P1a |
|---|---|---|
| 累加哪些像素 | 只累加像素槽 0（`sum_*[0]`） | **4 个槽各累加一份**，4 相各用一个增益 |
| 白点门控 | `rgb_sum[0] < 720` 才累加 | **无门控**，全累加 |
| 复位值 | `sum_* <= 1`（避免除零） | `sum_* <= 0` ⇒ **除零**（`den=0` 时 IP 商为全 1） |
| 增益更新时刻 | 每个 valid 拍都更新 | 每 4 拍更新一次 |

实测：`sum_r[0]` 43514 → **69013**（亮像素也被累加进去了）。
⇒ 修完 D1 后，字节最大差仍有 **163**、平均 **10**，差异全在 R/B 通道。

### 🟠 D3 · `signal_delay` 的 `DELAY_CYCLE` 由 50 改成 54（未修）

同一输入 beat 因此晚 4 拍进入乘法段 ⇒ **采样到的增益是 4 拍之后的**。
即使 D2 修好，只要 `DELAY_CYCLE ≠ 50` 就无法逐位一致。

### 🟠 D4 · 输出节拍 5 拍/字，720p 吞吐追不上（未修）

实际状态机是 `mul_busy` 拉高 4 拍 + 落回后空 1 拍 = **5 拍/字**（不是注释写的 4 拍）。
而设计文档 §1.3 自测输入率是 **0.23 beat/clk ≈ 4.35 拍/beat**。

`5 > 4.35` ⇒ **长期平均追不上，FIFO 填满后丢字**（实测 723 → 715）。

- 报告已定档：**2 个 DSP / 4 拍·字**（`4×0.23 = 0.92 < 1`，但余量仅 8%）
- 若要舒服余量：**4 个 DSP / 2 拍·字**
- 报告还指出设计文档 §4 R4 的「2 DSP、2 拍/字（每拍 2 个 R + 2 个 B）」**算术上不成立**：
  2 拍算完 4 像素的 R 和 B 需要 **4 个乘法器**

### 🟡 D5 · `tuser` 语义变了（未修）

- 基线：`assign O_tuser = I_tuser;` —— 直通，**与输出字不对齐**
- P1a：`tuser` 打包进 FIFO，**与输出字对齐**（更正确，但与基线不同）

下游 `data_96bit_to_128bit` 与 `edge_detect_96` 都吃 `awb_O_tuser`，**需要确认取哪一种**。

## 6. 一个判断：P1a 是否值得继续

**我倾向：短期不值得，除非口径选 B。**

理由：

1. **P1a 的收益是"面积/DSP"，不是"功能"**。而 lab4 当前 slice 72.80%、DSP 9/40 —— **都还很宽裕**。
   设计文档当初把 P1a 排第一，是因为 lab3 基线 HDMI 域只剩 0.006 ns；但 lab4 现在是 **+110 ps**，已经收敛。
2. **代价不小**：要修 D2/D3/D4 才能逐位一致，而 D4 的吞吐余量只有 8%，是个长期隐患。
3. **更该做的是 P1b（Logo→ERAM）** —— 素材已备齐（`logo_pixel.mif` 等 4 个文件），
   而且从 `hdmi_mixer` 移除约 2,500 LUT 的组合 OSD 逻辑是**纯赚**（不减少功能）。
4. **真正的合规硬需求是换掉边缘检测算法**（见决策文档），那个优先级高于 P1a。

⇒ **建议：先把 D1 修掉止血（1 处改动），然后暂停 P1a，转去做 P1b + 算法替换。**
