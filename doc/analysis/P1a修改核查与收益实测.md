# P1a（AWB 重构）修改核查与收益实测报告

> ## ⛔ 本报告结论已被推翻（2026-09-20 晚）—— 请先读这一段
>
> **P1a 是负收益改造，已回退。**
>
> 本报告只做了**资源差分验收**，**漏掉了吞吐验收**，因此得出了"成功"的错误结论。
>
> 上板实测症状：**画面撕裂 / 只有一半在动**（P1a 与 P1b 两个比特流症状相同）。
> 根因：P1a 把 AWB 乘法器从 **8 个并行**改成 **2 个 + 4 相 TDM**，
> 吞吐从 **1.34 拍/字** 降到 **4.18~5.00 拍/字**，而结构上限只有 **4.34 拍/字**；
> AWB 内 512 深 FIFO 每行净积压约 240 字，**两行即溢出**，
> 该 FIFO 满时**静默丢字**（`soft_fifo_...v:77` `wr_en_s = (!full_flag) & we`）
> ⇒ 屏幕撕裂。
>
> 而 `P1a-AWB重构设计.md` 的**风险表 R4 早已警示**：
> 「行有效窗口内峰值 0.29~0.4 beat/clk，**4 拍/字的分时不够**（需 2.5 拍/字）⇒ **推荐 2 DSP / 2 拍·字**」。
> **P1a 实际实现成 4 拍/字，即违背了自家设计的 R4 缓解措施。**
>
> 恢复厂商原版后实测（`_stage/d4_rate2`）：
>
> | | 8 并行（厂商原版） | P1a TDM |
> |---|---|---|
> | 吞吐 | **1.34 拍/字** | 4.18 ~ 5.00 拍/字 |
> | 丢字 | **0** | 13,137 ~ 29,636 |
>
> 而且恢复后**资源反而更好**（全设计 slice 13,347 = 62.91% vs P1a 的 16,466 = 77.61%），
> DSP 从 7.5% 升到 20%（远低于 40 上限）。
>
> **✅ 上板闭环（2026-09-20）**：烧写恢复后的比特流（`20:50:08`）复测，**功能已恢复、撕裂消失**。
> 根因判定与处置均被证实。
>
> **⇒ 详见 `doc/analysis/撕裂根因报告-awb吞吐回归.md`。本文以下内容仅作历史记录保留，结论作废。**
>
> **教训**：用"分时复用"换面积的改造，**吞吐必须与资源同时验收**，
> 且验收激励必须是**真实突发形态**（本例中写侧是「320 拍连发 + 51 拍空档」），
> 按均匀流灌数据会得出假达标的结论。

## 1. 修改内容核查

### 1.1 本次动了两处（缺一不可）

| # | 文件 | 改动 | 原因 |
|---|---|---|---|
| **1** | `awb.v` | **D1 步长修复**：`word_r[{mul_ph,5'd16} +: 8]`（步长 32）→ `px_base = mul_ph*24` 查表（步长 24） | 原代码步长错成 32，`mul_ph=3` 时基址 112/104/96 **超出 96bit 字范围 → 输出 X**（实测每个输出字高 24bit 全为 `x`） |
| **2** | `phy_1/settings.cfg` | 加 `set sp 1` | `DefaultFlow.tcl:80` 用它控制是否重读 ADC/SDC；不加则 P&R **不重读 `.sdc`**，`set_false_path` 不生效 |

> ⚠ `set sp 1` **只能加在 `phy_1`**。加在 `syn_1` 会让 `read_adc` 在 `elaborate` 之前执行，
> 报 `USR-8128 CRITICAL-WARNING: Please import a work model first.` 并立即失败（已实测）。

### 1.2 结构核查：与方案 §2.1 逐项对照

| 方案要求 | 工程实现 | 核查 |

| 8 multipliers → **2** multipliers（R/B） | `#MACRO_MULT` 全设计 = **3**（u_awb 2 + 其他 1） | ✅ |
| 4 相 TDM 分时 | `mul_ph[1:0]`，4 相 + `mul_ph_d1` 结果回写 | ✅ |

| 不预设面积数字，必须实测 | 本报告即实测 | ✅ |

### 2.3 时序收益：P1a 打掉了那条最紧路径

设计文档 §0 的动机是：**全设计最紧路径的起点就是 `u_awb` 的乘法器**（lab2 实测 1.451 ns，14 级、ADDER=10）。

| 目标 | 改前 | 改后 | 结论 |
|---|---|---|---|
| 打断 `u_awb 乘法器 → edge_detect` 的 14 级 ADDER 链 | lab2 该路径 **1.451 ns**（全设计最紧） | ✅ **该路径已从报告里消失** | ✅ **达成** |
| `u_awb` 内部路径 slack | lab3 有三条 **0.02 ns** 的路径（`sum_r[0] → div_gen_G_R_r1` 等） | 最差仍是 **0.02 ns**，但起点变为 `data_d1 → u_awb_fifo`（**ERAM 直连，level=1**） | ✅ 除法器链不再是瓶颈 |
| MIPI_RX_BYTE_CLK 域 SWNS | lab3 = **7.869 ns** | lab4 = **4.974 ns** | 因同时叠加了 edge_detect，不能直接归因 |

**修正一个重要误读**：全设计 WNS 从 +110 ps 掉到 **+10 ps**，**不是 P1a 造成的**。

现在的最差路径在 **`u_hdmi_mixer`**，与 AWB 无关：

```
slack = +0.010 ns   Logic Level = 14 ( LUT6=6 LUT5=2 LUT2=2 LUT4=1 LUT3=1 DSPMULT=1 )
  begin: u_hdmi_mixer/mult0_syn_59.clk        ← OSD Logo 的乘法器（把 Logo 坐标乘 160/146）
  end  : u_hdmi_mixer/O_hdmi_data_reg[4]
  Path Group: HDMI_PIXEL_CLK -> HDMI_PIXEL_CLK   (SWNS +0.010 ns, 0 Viol Endpoints)
```

HDMI 域的 **`Min Period` 从 15.605 ns 收紧到 13.323 ns**（Fmax 64.08 → 75.06 MHz），
说明布局布线为了满足约束做了大量优化，最后"停在边界"。
**这正是设计文档 §0 里说的"lab4 的瓶颈已转移到 HDMI/OSD 域"**，也就是 **P1b（Logo→ERAM）要解决的问题**。

## 4. 未修项与遗留风险

| # | 项 | 状态 | 影响 |
|---|---|---|---|
| **D2** | 增益算法与基线不等价：4 相位各用一个增益、**无白点门控**、`sum_*` 复位为 0（**除零**，IP 商为全 1） | 未修 | 口径选 B ⇒ **不需修**；但"每相位独立增益"属**算法改动**，上板需看颜色 |

| **D4** | 实际 **5 拍/字** > 可用 **4.35 拍/beat** ⇒ **连续输入会丢字**（实测 723 → 715） | **未修，仍是隐患** | ⚠ **这是唯一需要持续关注的**。720p 实拍输入通常有行间间隙，可能不触发；但需上板观察有无撕裂/丢行 |

> 或退到"4 个 DSP / 2 拍·字"（余量充裕）。**建议上板验证后再决定是否需要。**

## 5. 这笔交易值不值

| 视角 | 判断 |
|---|---|
| **DSP 视角** | ✅ **值**。40 个 DSP 里省下 6 个（22.5% → 7.5%），给后续算法（P5 目标检测、P6 AWB 闭环）留出空间 |
| **面积视角** | ⚠ **偏贵**。+1,614 slice，占用率 70.00% → 77.61%，距 80% 警戒线只剩 2.39 个点 |
| **构建时间视角** | ❌ **明显变差**。6 分钟 → 18 分钟，迭代效率降到 1/3 |
| **时序视角** | ⚠ 达成"打断最紧链"的目标；但全设计 WNS 收窄到 +10 ps（原因在 HDMI/OSD 域，非 P1a） |
| **设计文档原意** | 文档当初把 P1a 排第一，是因为 lab3 基线 HDMI 域只剩 0.006 ns、且最紧路径起点在 `awb`。**现在这两点都变了**：lab4 的瓶颈转移到 `hdmi_mixer` 的 Logo |

**建议**：
1. **保留 P1a**（DSP 收益真实且重要），但**暂停继续深挖**（D4 的 8% 余量性价比低）。
2. **优先做 P1b（Logo→ERAM）** —— 它能同时解决：(a) 当前唯一的关键路径（`u_hdmi_mixer` 的 Logo 乘法器）；
   (b) 移走约 2,500 LUT 的组合 OSD 逻辑，正好把 P1a 吃掉的 slice 补回来。素材已备齐。
3. 上板时**重点观察 D4**（连续输入是否丢字/撕裂）。
