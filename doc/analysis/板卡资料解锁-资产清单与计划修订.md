### 3.3 GPS 建议接线（用 DC3，任选一组）

GPS 只收不发，所以只需要 **1 根 UART RX + 3.3V + GND**：

| 信号 | 建议引脚 | 来源 |
|---|---|---|
| GPS TXD → FPGA RX | **U1**（= GPIOA_3，J1 排针第 4 脚） | GPS 例程用的就是这个 |
| 3.3V / GND | J1 第 29 / 30 脚（或 11/12 脚的 5V） | 引脚表 §四 |
| （可选）1PPS | 任选一个空闲 GPIO，如 **T4**（GPIOA_4） | 用于 §GPS 文档的绝对时间戳 |

> 也可改用 USB-UART 之外的空闲 DC3 引脚；GPS 例程 (`gps.adc`) 实测可用 `U1`。

### 3.4 DC3 扩展口（2×40 pin，共 72 IO）

- **J1 = GPIOA_0..35**：V2 V1 U2 U1 T4 T3 T2 R5 R3 R2 R1 P6 P5 P4 P3 P1 N7 N4 N3 N2 N1 M5 M4 M2 M1 L4 K2 K1 H2 D4 C8 B5 A5 B14 B10 A10
- **J2 = GPIOB_0..35**：C18 D15 E12 E16 E17 F13 F14 F18 G17 H17 H18 J13 **J14** J15 J16 J18 D9 K17 K16 K15 K13 L15 L16 P10 P9 P8 R7 R6 T5 U7 U6 U5 U4 V7 V6 V4
- 电源脚：J1/J2 的第 11 脚 = VCC5V，第 29 脚 = 3.3V，第 12/30 脚 = GND

> ⭐ **重要**：官方 lab1/2/3 例程里那两个"按键"`I_button[0]=N2`、`I_button[1]=J14` ——
> **N2 是 J1 排针的 GPIOA_19，J14 是 J2 排针的 GPIOB_12**，都是 **DC3 扩展口的排针引脚，不是板载按键**。
> 也就是说：**官方例程根本没用板载的 4 个按键**，那 4 个按键（D5/A9/B9/C7）是完全空闲的。

```

  → C0 = 125 MHz (0°)      RGMII 发送/协议栈主时钟
  → C1 = 125 MHz (90°)     RGMII TX DDR 相位
  → C2 = 25 MHz            PHY 复位时序等
```
> ⭐ **C0 的 125 MHz 可以直接当"快速算法域"用**，不需要再占一个 PLL。

## 5. 需要修订的技术结论（原 3 条 + 本轮新增修订 4、修订 5）

### 修订 1：官方例程用的**不是**板载按键（新事实）

| | 之前的理解 | 实际情况 |
|---|---|---|
| `I_button[0]` = **N2** | 以为是板载按键 | **N2 = J1 排针 GPIOA_19（DC3 扩展口）** |
| `I_button[1]` = **J14** | 以为是板载按键 | **J14 = J2 排针 GPIOB_12（DC3 扩展口）** |
| 板载按键 | 以为只有 2 个可用 | **KEY1~KEY4 = D5/A9/B9/C7，完全空闲** |

**影响（好消息）**：
- P2「多算法实时切换」（高阶要求 1）**不再需要 DC3 外接按键**，直接用板载 4 键。
- 我原方案里"只能靠 2 个按键，降级方案"的顾虑作废 —— **现在有 4 个键 + 4 个拨码 = 8 个输入，够用**。

### 修订 2：以太网是 **RGMII 千兆**，不是 MII 百兆

| | 之前的判断 | 实际 |
|---|---|---|
| 接口 | 不确定，担心是 RGMII | **确认 RGMII**（`rgmii_interface.v`、`I_a_rgmii_rxc`、`O_a_rgmii_txc`） |
| PHY | 型号未知 | **MotorComm YT8511**（H/C），RJ45 = HR911130A |

| IP 可用性 | `AXI_Ethernet_Lite` 是 MII，用不了 | **确认用不了**；但**有现成的 RGMII 千兆栈** |

### 修订 3（好消息）：千兆可用 → **"实时视频"重新成为可选项**

| 720p60 RGB565 | 885 Mbit/s | 92% ⚠ | ❌ | ⚠ 太紧，不建议 |
| 720p 全彩**单帧**抓拍 | 2.76 MB | — | 232 ms | **23 ms** ✅ |
| 遥测 | ~8 KB/s | ≈0 | ✅ | ✅ |

**但你上一轮已经选了 (A) 竞赛加分 + 只做"抓拍图片 + 医学数据"。** 所以这里只是告知：
- **如果你改主意要实时视频**，现在 `720p60 灰度` 或 `640×360 彩色@60` 是可行的（需重新评估 DDR 读带宽与单端口仲裁，见下）

> ⚠ **DSP 口径说明（**2026-09-18 第三轮已更正**）**：PH1P 的 DSP 是 **27×18 乘法器 + 54 bit 累加**
> （官网："支持独立的 **27x18, 9x9** 乘法器"；`dsp_macro_0.v` 内部把 A/B 补到 **27 bit**；

> **原稿的"26×26 → 53 bit"是把 RTL 模板的 parameter 默认值当成了器件规格，已作废。**
> 且 `SEL` 是**逐拍切换、不是同拍并行** ⇒ **一个 DSP 每拍只出 1 个乘积**，
> **"26 位输入拆成多个子乘法"在本地 IP 里找不到配置入口，不要再作为预算依据。**
> ⇒ **"40 个 DSP 是瓶颈"这条判断仍然成立**；缓解手段只有两条：
> ① 常量系数一律走 CSD 移位-加法；② **靠分时复用**（像素率仅 0.23 beat/clk，AWB 的 8 个乘法器可降到 2 个）。
> 依据：`doc/analysis/核验与纠偏-2026-09-18第三轮.md` §11。

## 7. 这改变了什么取舍

| 模块 | 之前 | 现在 | 建议 |
|---|---|---|---|
| **以太网** | 800 LUT 自写 TX-only，高风险，需原理图 | **1,629 LUT 复用成熟栈，低风险，含 ARP/ICMP/全双工** | **值得做**。多花 800 LUT 买掉全部协议风险 + 拿到千兆 |
| **GPS** | G1 透传（150 LUT），G2 自写解析（450~600） | **G2 直接复用（158 LUT）** | **直接做 G2**，OSD 上能显示坐标 |
| **UART 遥测** | 需 DC3 接线 | **USB-UART 专用引脚 J1/H1，零外部器件** | 立即可以做，先跑通协议 |
| **多算法切换** | 只有 2 个排针"按键"，缺引脚 | **4 个板载按键 D5/A9/B9/C7** | 用板载键，不用外接 |
| **"发信号"** | 需引脚表 | **蜂鸣器 C12 + 4 个 LED** | 50 LUT 拿扩展(3)，照做 |
| **实时视频** | 判定不可能 | **灰度 720p60 / 彩色 640×360@60 可行** | 你已选只做抓拍；若要改，从 640×360 起步 |
| **OSD 文本** | 自建 | 可借鉴 `char_display` + ROM IP 流程 | 省时间 |

### 修订后的推荐优先序

```
P0  P1 Logo→ERAM（不变，最高杠杆）
P0  N1a UART 遥测通道（走 J1/H1，零外部器件）        ← 现在可以立刻开始，没有任何依赖
P0  降落点检测（图像侧，得分主体）
P1  抓拍缩略图上传（ERAM 缩略图方案，零 DDR 读）
P1  4 个板载按键 + 蜂鸣器/LED 报警（拿扩展(3)）
P1  以太网：把成熟 UDP 栈搬进来（先只做发送遥测）
P2  GPS：搬 uart_rx + GGA，OSD 显示坐标 + 遥测带坐标
P2  rPPG 医学数据
P2  AE/AWB 闭环
P3  实时视频（若改主意）：640×360 彩色@60，走显示读旁路
P3  HDMI 音频、精确 PLL、直方图均衡
```
