## 0. 结论先行（三句话）

1. **方向有价值，但"实时视频流"这个具体形态在这块板子上做不成**：720p60 RGB888 = **1.33 Gbit/s**，超过千兆网可用带宽（~957 Mbit/s）。必须改成"**遥测 + 上位机配置 + 按需抓帧**"，视频要降采样/灰度化。
2. **以太网在这块器件上是"软核从零做"**：PH1P **没有硬核以太网 MAC**（CGMAC 文档只有 PH2A），IP 库里只有 `AXI_Ethernet_Lite`（**10/100 Mbps MII**）。而且**没有开发板原理图就完全无法接线**（比按键更硬：按键至少有 2 个已知引脚，以太网一个都没有）。
3. **建议分两层落地**：先做 **L0 = USB-UART 遥测通道（0 面积成本、不依赖原理图）**，把数据模型和 PC 端程序跑通；以太网作为 **P9 可选**，且只在确认了 PHY 接口之后再上。这样竞赛得分不受影响，你的项目也拿到了"数据上传"能力。

## 1. 先算带宽：为什么"实时视频"不成立

**720p60 像素率 = 1280 × 720 × 60 = 55.296 Mpx/s**

| 格式 | B/px | MB/s | Mbit/s | 占 1GbE 线速 | 占 1GbE 可用带宽<br>(UDP+1472B, 957 Mbps) | 结论 |
|---|---|---|---|---|---|---|
| RGB888 720p60 | 3 | 165.9 | 1327 | 133% | **139%** | ❌ **物理上传不了** |
| RGB565 720p60 | 2 | 110.6 | 885 | 88% | **92%** | ⚠ 理论可以，软 MAC 不可能稳定跑到 92% 线速 |
| YUV422 720p60 | 2 | 110.6 | 885 | 88% | 92% | ⚠ 同上 |
| **灰度 720p60** | 1 | **55.3** | 442 | 44% | **46%** | ✅ 舒适（推荐） |
| **640×360 RGB888@60** | 3 | **41.5** | 332 | 33% | 35% | ✅ 舒适，且保色（推荐） |
| 640×360 灰度@30 | 1 | 6.9 | 55 | 6% | 6% | ✅ 轻松 |
| 320×180 RGB888@30 | 3 | 5.2 | 41 | 4% | 4% | ✅ 轻松 |

> **可用带宽怎么来的**：以太网帧开销 = 8(前导) + 14(以太头) + 20(IP) + 8(UDP) + 4(FCS) + 12(帧间隙) = 66 B / 每 1472 B 载荷 → 效率 95.7% → 1000 × 0.957 = **957 Mbit/s = 119.6 MB/s**。

### 1.1 如果换成 100 Mbps 以太网（板上 PHY 通常会协商降速）

100 Mbps 可用 ≈ 95 Mbit/s = **11.9 MB/s**：

| 用途 | 带宽 | 能否 |
|---|---|---|
| 遥测（状态/延迟/AE/检测结果/运动计数） | 1 KB/帧 × 60 = 0.06 MB/s | ✅ 绰绰有余 |
| 640×360 灰度@30 | 6.9 MB/s | ✅ |
| 320×180 RGB888@30 | 5.2 MB/s | ✅ |
| 720p RGB888 按需抓单帧 | 2.76 MB / 11.9 = **232 ms** | ✅ 可接受（"点一下抓图"） |
| 720p60 灰度实时 | 55.3 MB/s | ❌ |
| 720p60 RGB 实时 | 165.9 MB/s | ❌ |

**结论：100 Mbps 已经足够做"遥测 + 降采样视频 + 按需抓帧"，而它的逻辑成本只有千兆的 1/3。** 这是本设计最关键的一个取舍。

- 接口是 **MII / RMII / RGMII / SGMII** 中的哪一种
- 用哪些 FPGA 引脚、是否有 MDIO、PHY 复位引脚、25 MHz/125 MHz 时钟来源

**影响**：
- 若板子是 **RGMII 接线**（国产千兆板最常见），**没有独立的 MII 25 MHz 时钟**，就用不了 `AXI_Ethernet_Lite` 的 MII 接口，只能自己做 RGMII（125 MHz DDR，难度高一个量级）。
- 这是一个纯粹的"资料缺失"问题，**没有任何工程手段可以绕过**。

→ **这条决定了以太网能不能做，优先级高于本方案里其他所有事项。**

### ✅ R3（已解除为阻断项）：DDR 用户口是单端口、无 transaction tag

> **🔔 后续修订（2026-09-18 晚）**：本项**不再构成阻断**——缩窄版方案（`网络模块-方案（缩窄版）.md`）
> 改为"**显示读旁路 + ERAM 缩略图**"，**零额外 DDR 读口**，因此不必改 `mc_to_user_interface`、不必加 transaction tag。
> 同时本机 TD 6.2.1 SP1 重测基线显示 **DDR `usr_clk` 域裕量由 0.576 ns 改善到 2.311 ns（约 3 倍余量）**，
> "DDR 已贴警戒线"的紧迫感下降。
> **但下面"不要为视频流新增 DDR 读口"这个设计结论仍然成立**（单端口 + 无 tag 是硬事实）。
> 依据：`doc/analysis/增量分析与新思路-2026-09-18.md` §1.2(c)。

实测（见分析报告 §3.4；**DDR 速率已按第三轮核验更正**）：
- 存储器是**片内集成 512 Mbit (64 MB) DDR2 x16**；IP 配置写 `DDR2-1066`，但**参考时钟只给了 50 MHz（应 100 MHz）⇒ 实跑 DDR2-533（CK 266.667 MHz）**，
  引脚峰值 **1,066.7 MB/s**（⚠ 原写 2,133 MB/s 作废）
- 控制器**用户口 = 128 bit @ 66.667 MHz = 1,066.7 MB/s** ⇒ **与引脚峰值 1:1，没有"引脚的一半"这回事**（⚠ 原表述作废）
- `mc_to_user_interface` 的命令只有 1 bit 读/写标志（`O_mc_app_cmd[0]`），**没有 transaction tag**
- 现有占用：写 165.9 + 显示读 165.9 = **331.8 MB/s = 31.1%**

新增一路"视频流读取"的代价：

| 方案 | 额外读 | 总计 | 占用户口 |
|---|---|---|---|
| 灰度 720p60 | +55.3 | 387.1 | 36.3% |
| 640×360 RGB888@60 | +41.5 | 373.3 | 35.0% |
| 满幅 RGB888 720p60 | +165.9 | 497.7 | **46.7%**（且要加 tag 路由） |

→ **不要为视频流新增 DDR 读口。** 用 §5.2 的"显示读旁路"方案：**零额外 DDR 带宽**。

## 3. 与赛题评分的关系（必须诚实评估）

| 事实 | 影响 |
|---|---|
| 题面的**基础 4 条 / 扩展 5 条 / 进阶 5 条里，没有任何一条提到"网络"** | 网络**不是必答项**，不做不扣分 |
| **PPT slide 24（进阶要求 2 目标跟踪与信息标注）原文**：「……最后通过 HDMI 接口实时输出至显示器。**以太网接口可用于上位机配置与状态监控。**」 | 官方**明确认可**以太网用于"上位机配置 + 状态监控" → 可挂到高阶(2) |
| 扩展要求 (3)「面向实际应用场景进行系统设计，如结合移动平台，根据视频识别结果实现外部控制」 | 网络 + PC 属于"应用场景设计"，且 **PC 在板外，不算"额外处理器"**，规避了评分风险 |
| 扩展要求 (5) 自主创意 | 可算一项 |
| 硬约束：**最终设计必须固化、上电即跑，不能依赖 PC 下载** | PC 只能当"数据终点"，**所有功能必须能脱离 PC 独立演示** |

**判断**：
- 单看竞赛得分：**网络性价比偏低**——约 800~1,500 LUT（我们 P1 之后也只有约 2,400 LUT 余量）+ 一块 PC 端程序 + 原理图依赖 + 上板调试风险，换来的分不如把 P4（卡通化）/P5（目标检测）/P6（AE 闭环）做扎实。
- 看你的**医疗无人机项目**：网络是核心技术底座，价值完全不同。
- **所以它是"加成 / 项目需要"，不是"赛题必答"。建议放在 P9（可选），或与 P5 并行做一个"遥测最小版"。**

⚠ **一个重要的反向提醒**：如果你的真实目标是"医疗无人机实时视频回传"，那么 **PH1P35 + 1GbE 不是合适的载体**——720p60 RGB 需要 1.33 Gb/s，1GbE 传不了；无人机图传的常规做法是 **H.264 压缩到 1~4 Mbps** 再传，而这块器件上做 H.264 编码不现实（Anlogic IP 库里没有 JPEG/H.264 编码器；`sf1_phy_dsc.v` 是 DSC，只对 SF1 且依赖硬核）。真机项目应该换平台或直接用现成图传/WiFi 模块。

## 4. 成本估算（逻辑资源）

> 以下为**工程估算**，非实测；上板后用 `tools/run_regression.ps1` 校正。

| 方案 | 通信能力 | 估算 LUT | ERAM | 难度 | 备注 |
|---|---|---|---|---|---|
| **L0：USB-UART 遥测** | 1~3 Mbps（≈375 KB/s） | **~200** | 1 | ★ | 板上已有 USB 转 UART，**0 硬件成本** |
| **L1a：100M MII 自写 UDP，TX-only** | 100 Mbps 单向 | **~800~900** | 2 | ★★ | 无 RX → 无需 ARP/ICMP/IDELAY |
| L1b：100M MII 自写 UDP，全双工 | 100 Mbps 双向 | ~1,300~1,500 | 3 | ★★★ | 要 ARP/ICMP/UDP RX |
| L1c：`AXI_Ethernet_Lite` IP | 100 Mbps 全双工 | ~1,200~2,000（IP 自带） | ? | ★★ | **需先验证它在 PH1P 上能否综合通过**（端口是 MII） |
| L2：100M RGMII TX-only | 100 Mbps 单向 | ~900~1,000 | 2 | ★★★ | 需 25 MHz DDR 输出 + PHY strapping 确认 |
| L3：1000M RGMII TX-only | 1000 Mbps 单向 | ~1,100~1,300 | 2 | ★★★★ | 8 bit @ **125 MHz** DDR；**PLL 闲置的 C3 = 1500/12 = 125.000 MHz 正好可用** |

**"TX-only" 是本设计的关键简化**（强烈推荐）：
- 不需要 RX 时钟域、不需要 RGMII RX 的 IDELAY 校准（这是最容易踩坑的地方）
- 不需要响应 ARP / ICMP / 不需要解析 UDP 入包
- **不需要 ARP 的替代做法**：直接用**广播**（目的 MAC `FF:FF:FF:FF:FF:FF`，目的 IP `192.168.1.255`），PC 端 socket 用 `SO_REUSEADDR` 绑定即可收到；或在 PC 上配一条**静态 ARP**。二者都免掉了 ARP 协议实现。
- **下行配置走 UART**（板上已有，UART RX 极便宜），或干脆不放下行，全部配置用板上的 2 个按键 + OSD。
  → 这样"上位机配置"就退化成"按键配置 + 上位机只做监控/记录"，仍然符合 slide 24 的措辞。

## 5. 推荐架构

### 5.1 四层解耦（这样先做 L0、后换以太网，上层代码全不用改）

```
┌─ 数据模型层 ─────────────────────────────────────────────┐
│  telemetry_frame = 固定头(16B) + TLV 负载                 │
│   type 0x01  状态/延迟/AE/AG/帧计数      (~64 B/帧)        │
│   type 0x02  检测结果 bbox/类别/计数/坐标 (~128 B/帧)      │
│   type 0x03  运动统计 tile图/计数         (~256 B/帧)      │
│   type 0x04  外部传感/生命体征(若做)      (~32 B/帧)       │
│   type 0x05  ROI / 整帧图像（按需，大包分片）              │
└──────────────────────────────────────────────────────────┘
┌─ 传输层（打包 + 分片）───────────────────────────────────┐
│  frame_id / pkt_idx / pkt_total / payload_len             │
│  分片阈值按 MTU 1472 B；type 0x05 需要 ~1875 包/帧         │
└──────────────────────────────────────────────────────────┘
┌─ 物理层（可替换）────────────────────────────────────────┐
│  L0: UART (先做)  →  L1: 100M MII UDP  →  L2/L3: RGMII    │
└──────────────────────────────────────────────────────────┘
┌─ PC 端（Python，一次写好）───────────────────────────────┐
│  socket 收包 → 重组 → 解析 TLV →                           │
│  ① 实时曲线（延迟/亮度/AE 闭环过程）                       │
│  ② 检测框叠加显示  ③ CSV/Parquet 记录（答辩可追溯）        │
└──────────────────────────────────────────────────────────┘
```

**为什么要这样分层**：`frame_id / pkt_idx` 这套重组逻辑和 PC 端程序与物理层无关。先用 UART 跑通（此时 `type 0x05` 不可用或很慢），换成以太网后只是物理层替换。

### 5.2 视频从哪里取数：**旁路显示读流，零额外 DDR 带宽**

```
video_out (DDR→显示) ──► hdmi_mixer ──► hdmi_tx ──► HDMI
        │
        └─► [新增] 下采样器 @ HDMI_PIXEL_CLK
              · 灰度：gray = R/4 + G/2 + B/4（免溢出移位加法，官方现成写法）
              · 水平/垂直 2:1 抽取 → 640×360
              · 8:1 抽取 → 160×90（也可给运动检测复用）
              └─► 行缓冲(FIFO) ──► 打包 ──► MAC
```
- 显示口本来就把每一帧的每个像素读出来，**这里取数是免费的**
- 新增 DDR 带宽 = **0**
- 下采样是"丢掉不要的像素"，逻辑极便宜（垂直 2:1 只需每行丢弃，水平 2:1 只需比较 x 的 bit0）
- 这也正是实施方案里 P5（目标检测 tile 统计）和 P7（运动检测 8×8 缩略）用的同一个 tap → **三个功能共用一个取数点**

### 5.3 时钟

| 用途 | 时钟 | 来源 |
|---|---|---|
| 打包/分片逻辑 | 与取数同域（HDMI_PIXEL_CLK 75 MHz） | 已有 |
| MII 100M | 25 MHz TXC（PHY 提供或 FPGA 产生） | 若 PHY 给则直接用 |
| RGMII 100M TX | 25 MHz DDR | PLL VCO 1500 / 60 = 25 MHz（需新开一个输出） |
| **RGMII 1000M TX** | **125 MHz** | **PLL 闲置的 C3 = 1500/12 = 125.000 MHz** ✅ |
| UART | 已有 | — |

> 注意：PLL 的 C2/C3/C6 目前 `*_en` 都接 0（未启用）。方案里 P9 提的"快速算法域"想用 C2=150 MHz，若同时要千兆以太网就要规划 C3=125 MHz——**PLL 输出共 7 个，够用，但要在同一版配置里一次规划好**。
>
> **补注（2026-09-18 晚）**：正因为 **C2/C3（及 C6）在例程里 `*_en` 接 0**，它们是**现成的空闲输出，把使能位改 1 即可无偿启用，不额外占 PLL**
> （依据：`ip_source/PLL/PLL.v`；`33_ethernet_udp_led` 的 PLL 也是用 C0=125 MHz / C1=125 MHz(90°) / C2=25 MHz，同样没有多占一个 PLL）。
> 所以"千兆以太网要占一个 PLL"这个顾虑不成立——**它是从已有 PLL 里拿一路本来闲置的输出**。

## 8. 需要你确认的三件事

1. **这个网络模块的定位是什么？**
   - (A) **竞赛加分项** → 建议只做 **UART 遥测 + 上位机监控**（0 面积），以太网放最后
   - (B) **医疗无人机项目的技术底座** → 那要重新评估平台（见 §3 的提醒：1GbE 传不了 720p 彩色实时视频）
   - (C) **两者都要** → 按 §6 的 N0→N2 先做，N3 验证后再决定 N4

2. **视频要不要"实时"？**
   - 要实时 → 只能**灰度 720p60**（442 Mbit/s）或 **640×360 彩色 60fps**（332 Mbit/s）
   - 不要求实时 → **按需抓全分辨率彩色帧**（11.9 MB/s 下 232 ms/帧），质量最高

3. **能不能接受"上下行分离"**（上行以太网 TX-only、下行 UART）？
   - 能接受 → 以太网部分从 ~1,300 LUT 降到 ~800 LUT，且避开 RGMII RX 的 IDELAY 校准坑
   - 不能接受 → 逻辑和调试成本都要上浮约 60%
