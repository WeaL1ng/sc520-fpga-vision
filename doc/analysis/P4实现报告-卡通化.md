## 1. 算法：三件套，全部零乘法/零除法/零 DSP

```
① 灰度      Y = (77R + 150G + 29B) >> 8        移位加法（77=64+8+4+1 等，严格等式）
② 颜色量化  取高 QUANT_BITS 位后**复制填满** 8 位 → 8 级色块（"区域填充"观感）
③ 边缘      EDGE_OP=1 中心差分   max(|左−右|, |上−下|)          ★当前默认
            EDGE_OP=0 形态学梯度 max(十字5点) − min(十字5点)    （一行切回）
④ 阈值化    edge = (grad > I_cartoon_th)     当前 8'd20
⑤ 合成      cartoon = edge ? 黑 : 量化色
```

### 1.1 ★ 2026-09-21 两处修正（对着上板照片与同工作区参考实现逐条比对得出）

| # | 原来 | 改成 | 依据 |
|---|---|---|---|
| 1 | `R' = (R & 0xF0) \| 0x08`（16 级、**相邻差仅 16**） | **取高 QUANT_BITS 位复制填满**，默认 `QUANT_BITS=3` ⇒ {0,36,73,109,146,182,219,255}（**8 级、相邻差约 36**） | 16 级量化**肉眼几乎看不出**、不像卡通；4 级（相邻差 85）又把 30 的通道差放大成剧烈偏色（**天空变青绿、暗部压成纯黑**）。8 级是两者折中 |
| 2 | **形态学梯度** `max−min` | **中心差分** `max(\|左−右\|, \|上−下\|)` | `max−min` 的响应是**高原** ⇒ 线条粗、且**对孤立噪声不免疫**（噪声尖峰被算成满幅梯度）⇒ 树叶/水纹整片发黑；差分的响应是**尖峰** ⇒ 线细，孤立噪声在差分里**抵消** |

> **量化级数怎么选**（`cartoon_96.v` 的 `QUANT_BITS`）：
> `1`⇒2 级 / `2`⇒4 级（偏色重，不推荐）/ **`3`⇒8 级（默认）** / `4`⇒16 级（≈旧观感）。

### 1.2 合规论述（答辩要能当场讲清）

赛题 2.3 规定"提交的参赛作品中图像处理算法不能和参考实例相同"，官方参考 `lab_ex_2`
**就是 Sobel 边缘检测**。本项目的合规结构是**分层**的：

| 要求 | 由谁满足 | 与参考实例的关系 |
|---|---|---|
| **基础要求②**（至少一种图像处理算法） | `gray_binary_96`：灰度/二值化/反色 | **不含边缘检测**，与 Sobel **不同** ⇒ 红线不成立 |
| **扩展要求①**（卡通化） | 本模块 | 边缘算子是**中心差分**或**形态学梯度**，**均与 Sobel（3×3 加权卷积）不是同一个算子** |

⚠ **选 `EDGE_OP=1` 的代价要说清楚**：交付物里重新出现"线性差分型边缘检测"。
若评审方按"交付物整体不得含边缘检测"从严解释，切回 `EDGE_OP=0`（形态学梯度，
非线性算子）即可 —— **两条路都保留在代码里，切换成本 = 改一个 localparam + 一次重建**。
详见 `红线1合规改造-算法替换.md` §1 的 2026-09-21 更正。

### 1.3 ★ 线宽的**架构上限**（与算子无关，必须如实说明）

本模块沿用 `edge_detect_96` 的"**每拍 2 个采样**"结构 ⇒ 每拍只算 **2 个边缘判决**
（`edge0` 管像素 0,1；`edge1` 管像素 2,3），**一个判决复制给一对像素**：

```
水平最小线宽 ≈ 2 采样 = 4 像素          ← 本架构的硬上限
参考工程 Sobel 每像素一判决 ⇒ 1~2 像素
```

⇒ 本模块能做到"**接近**"参考的细度，**做不到一样细**。想追平必须改成每像素判决，
而那需要单口 ERAM 一拍供出 3 个相邻列 —— 本项目早先试过并放弃（见 §2.1）。
**收益小于代价，不做。**

## 2. ★ 实现过程中撞的坑（值得完整记录）

### 2.1 我写歪了三版，根因是同一个

前两版我试图"省一个行缓冲"，结果都卡在**同一个矛盾**上：

> 3×3 窗口需要**同一行的三个相邻采样**，而单口 ERAM 一拍只能读一个地址。

按"字（4 像素）"计址时更糟：字边界处的邻居属于**另一个字**，
只能填 0 近似 ⇒ **每个字边界都产生一次假边缘**。

**仿真实测证据**：第一版跑出来平坦区 **3200 / 6370 像素被误判为边缘**，
且黑像素严格落在字内 `k=0` 与 `k=3` 位置 —— 一眼就是"边界语义"问题。

### 2.2 答案在**已被移除的 `edge_detect_96.v`** 里

它当初（lab2/lab4 上板验证可用）用了一个很干净的办法：

| 技巧 | 说明 |
|---|---|
| **每拍只取 2 个灰度采样** | `pair0=(gray0+gray1)>>1`、`pair1=(gray2+gray3)>>1` ⇒ 水平方向每拍只需 2 个采样，3×3 窗口的两个历史采样用**移位寄存器**即可 |
| **读地址 == 写地址（同组）** | "读"在 always 块里**先于**"写"求值，且 ERAM 同步读 ⇒ 读回的是**上一拍写入**的内容，**天然没有地址冲突**，也不需要"提前读/滞后读" |
| `x_grp` 从 1 开始、`IMG_WIDTH_GRP-1` 回绕 | 跳过第 0 组，规避边界 |
| 窗口有效条件 | `(y_pos >= 2) && (x_grp != 0) && !I_tuser` |
| **复位不清行缓冲** | 原文警告："A reset loop turns the 10-Kbit buffers into slice registers" ⇒ 会把 ERAM 推断成上万个触发器 |

**⇒ 本模块照此实现，只把 Sobel 换成形态学梯度、把"黑白"输出换成"量化色 + 黑边"。**

### 2.3 第三版：功能对了，但**时序崩了**

第三版沿用 `edge_detect_96` 结构后功能立刻正确（详见 2.4），但综合报出：

| 项 | 实测 | 预算 |
|---|---|---|
| 关键路径 | `u_cartoon_96/x_grp_reg[2]` → `O_tdata_r_reg` | — |
| 逻辑级数 / 延迟 | **29 级 / 19.206 ns** | 16.667 ns |
| MIPI_RX_BYTE_CLK Fmax | **51.509 MHz** | ≥ 59.995 MHz |
| 全局 Setup SWNS | **−2.746 ns** | ≥ 0 |
| STNS | **−93.921 ns** | 0 |

**根因**：把"行缓冲地址译码 + 3×3 窗口 + 形态学 24 个比较器 + 阈值 + mux + 量化"
全塞进**一拍**里。行缓冲读地址（`x_grp`）到输出寄存器之间串了 29 级。

**修法**：在中间插一级流水 `p1_*`，把组合路径切成两段：

```
第 1 段  x_grp → 行缓冲读 → 窗口拼装 → p1_*（寄存器）
第 2 段  p1_* → 形态学梯度 → 阈值 → mux → 量化 → O_tdata_r（寄存器）
```

### 2.4 ★★ 加流水后出现的"整体右移 4 像素"（最隐蔽的一个坑）

加完 `p1_*` 后功能测试立刻变成 64 个像素错位。逐字打印输出定位到**极有特征**的症状：

| 现象 | 观测 |
|---|---|
| 每行**第 0 组**的颜色 | = **上一行最后一组**的颜色 |
| 真实竖边（x=640） | 跑到 **x=644** |
| 第 0 行第 0 组 | `(8,8,8)`，即"量化后的 0"（流水线填充值） |
| 黑像素位置 | 全部落在组 161 而不是组 160 |

**根因**：加了一级流水后两条路径延迟不等：

```
数据：I_tdata(n) → p1_p*(n+1) → q(n+1) → O_tdata_r(n+2)   2 拍
控制：I_tvalid(n) → O_tvalid_r(n+1)                        1 拍
```

⇒ 输出字 k 的内容其实是输入第 **k−1** 组 ⇒ **整幅图右移 4 像素**。

**修法**：控制也走两级寄存器（`tvalid_d1` → `O_tvalid_r`），与数据对齐；
数据寄存器改用 `tvalid_d1` 门控（对齐后的第 1 级）。

> ⚠ **这个 bug 在平坦图案上看不出来**（平坦区平移 4 像素还是同一个颜色），
> 只在**边缘位置**和**每行首尾**暴露。如果只做"有没有黑边"的粗检查，
> 它会一路带到板上，表现为"整个画面横移半厘米"。

### 2.5 另一个被否掉的做法：窗口无效时"直通原色"

我曾给窗口无效的像素（图像最上面 2 行、每行第 0 组）加 `passthru = !window_valid`
直接输出**原色**，理由是"避免填充期杂色"。结果：

| 项 | 实测 |
|---|---|
| 平坦区不符 | **2628** 像素 |
| 输出颜色 | 出现原色 `(48,48,48)` / `(192,192,192)`（未量化） |

**结论**：模块对**任何**输入像素都必须输出符合算法的结果。
正确做法是"**边缘判定**用有效位门控、**输出一律量化**"，而不是"无效就直通"。

### 2.6 最终验证结果

| 指标 | 第一版（按字计址） | 第二版（加直通） | **最终版** |
|---|---|---|---|
| 平坦区符合 | — | 9744 | **10216 / 10216** ✅ |
| 平坦区不符 | ~3200 | 2628 | **0** ✅ |
| 边缘处黑像素 | — | 4 | **24**（真边缘）✅ |
| **边缘外黑像素** | **3200**（假边缘） | 248 | **0** ✅ |
| 黑像素 x 集合 | — | 4~63, 640~699 | **恰好 {640,641,642,643}** ✅ |

## 3. 集成改动（模式 0~4）

新增模式需要把模式号从 **2 位扩到 3 位**，涉及 4 个文件：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `isp/cartoon_96.v` | **新增**（本阶段主体） |
| 2 | `isp/isp_top.v` | 新增 `cartoon_96` 例化；端口 `I_img_mode[1:0]→[2:0]`、新增 `I_cartoon_th[7:0]`；数据通路改为 **mux（mode==4 ? cartoon : gray_binary）**；tready 链再串一级 |
| 3 | `key_mode_ctrl.v` | `O_mode[1:0]→[2:0]`；短按改为**取模 5 循环**（0→1→2→3→4→0），**不用位宽自然回绕**（那会经过未定义的 5/6/7） |
| 4 | `design_top_wrapper.v` | 模式相关 wire/同步器全部 2 位→3 位；`I_cartoon_th(8'd20)`（**原为 8'd40，后按 §1.1 调到 20**）；新增 `u_cartoon_96` 的 `.GRAD_TH(8'd20)` |
| 5 | `hdmi_mixer.v` | `F_mode7seg` 补全 0..9（模式 4 显示 "4"）；`I_mode_disp[1:0]→[2:0]` |

**两条通路并行常开**（都吃 awb 输出），mux 二选一。理由与 `edge_detect_96` 相同：

> ⚠ 若按模式"停喂数据"做输入侧旁路，行缓冲在旁路期停喂，
> 解除旁路瞬间窗口内容与当前像素不对应 ⇒ **画面残留/撕裂**。
> 两个模块都**全时运行**，代价是卡通模块持续耗电，收益是切换干净无残留。

**已知副作用**：两条通路**延迟不同** —— `gray_binary_96` 输出打 **1 拍**，
`cartoon_96` 输出打 **2 拍**（多一级 `p1_*` 流水）。

| 影响 | 说明 |
|---|---|
| 稳态画面 | **无影响**。两条通路各自"控制延迟 = 数据延迟" ⇒ 输出与输入**逐字对齐**，卡通模式的画面只是整体多 2 拍延迟 |
| 切换瞬间 | 下游会**多收到 1 个字（4 像素）**（ct 比 gb 晚 1 拍）⇒ 切换那一行有约 4 像素的横移，**下一行自愈** |
| 帧起始 | 两条通路都在 `I_tuser` 处对齐帧首，不会跨帧累积 |

> 早期版本（见 §2.4）里卡通模块"数据 2 拍 / 控制 1 拍"，那样才会造成**整帧右移**
> 并跨行累积。已修掉，且 `check_cartoon.py` 已加"黑边必须恰好落在 x=640..643"
> 的断言把这个错位锁死。

### 4.2 ★ 上板发现并修掉的一个 P3 缺陷（`frame_latency` 重写）

上板后 `LATENCY` 数字在 **0~10 ms 之间来回扫**，不是稳定值。逐行核对 RTL 后确认：
第一版 `S_held_ms` 存的是**最新**标签，所以
`lat = now_ms − 最新标签时间 = 采集帧内的相位 ∈ [0, P_c)` —— **不含帧缓冲那 2 帧**。

正确做法是按 **DDR BANK 号**索引标签（`video_in.v` 实测 `rp = wp + 2 (mod 4)`，
读写永不撞同一槽位）。完整推导与复盘见 `P3实现报告-OSD文本与延迟可视化.md` §2.1/§2.1b。

| 场景（新 TB 忠实建模集成） | 旧方案(P3) | **新方案(按 BANK)** | 真实延迟区间 |
|---|---|---|---|
| `P_c=10.00 ms` / `P_d=16.50 ms` | min=max=**7.0** | min=21.0 max=30.0 avg=**25.5** | [20.0, 30.0] |
| `P_c=16.70 ms` / `P_d=16.50 ms` | min=**0.0** max=**17.0** | min=33.0 max=50.0 avg=**42.3** | [33.4, 50.1] |

⇒ **板上"0~10 ms 扫动"在仿真里被复现**（旧方案范围恰好 = `[0, P_c]`），
新方案全部样本落在 `[2P_c, 3P_c]`。

**副作用（意外的好消息）**：重写后 `HDMI_PIXEL_CLK` 反而**变快**了 ——
旧模块在显示域**异步读采集域的 32 位毫秒计数**，那条长路径直通
`hdmi_mixer.O_hdmi_data`。改成"测量全在 ddr_clk 域、只把结果用乒乓送过来"后：

| 项 | 重写前 | **重写后** |
|---|---|---|
| `HDMI_PIXEL_CLK` Fmax | 82.284 MHz (+9.7%) | **85.099 MHz (+13.5%)** |
| 全局 Setup SWNS | +1.180 ns | **+1.366 ns** |

### 5.4 时序迭代过程（**两次失败 → 一次收敛**，留档）

| 版本 | MIPI 域 Fmax（gate） | 关键路径 | 结论 |
|---|---|---|---|
| 无流水，串行 max/min | 51.5（布线后） | 29 级 / 19.206 ns | ❌ 严重违规 |
| +`p1_*` 流水，串行 max/min | 48.527 | 27 级 / 20.539 ns，8 级串行比较器链 | ❌ 仍违规 |
| +`p1_*` 流水，**树形 max/min** | **69.411** | 19 级 | ✅ 收敛 |

**关键发现**：串行写法
```verilog
d = a00; if (a01>d) d = a01; if (a02>d) d = a02; ...   // 8 级串行
```
被综合成 **8 级串行 8-bit 比较器链**，每级约 **2.17 ns**
（比较器进位链 0.76 + 高扇出网络 0.66+0.48 + LUT3 0.27），单是 dilate+erode
就吃掉 ~17 ns。改成**树形归约**（行内 2 级 + 行间 2 级 = 深度 4）后语义完全等价，
级数减半 ⇒ MIPI 域 gate 级 Fmax 48.5 → **69.4 MHz**，布线后 **73.3 MHz**。
