## 2. `src\uifdma\uiFDMA.v` and `uifdma_axi_ddr.v`

### 2.1 Direct answer on the "register map"

**There is no register map.** Neither `uiFDMA.v` (426 lines) nor `uifdma_axi_ddr.v` (454 lines) contains any AXI4-Lite/AXI3-Lite slave, any address decoder, any `case (addr)`, or any CSR. A grep for `S_AXI|s_axi|axi_lite|32'h…` over `src\` returns only hits inside the Yosys-generated divider `div_u39_u33.v`. Configuration is done **entirely through a signal-level handshake at run time and through Verilog parameters at compile time**. The "equivalent register map" is therefore:

**Run-time configuration fields (FDMA handshake, one 1-D transfer at a time):**

| Field | Signal | Width | Semantics |
|---|---|---|---|
| addr | `I_fdma_waddr` / `I_fdma_raddr` | `M_AXI_ADDR_WIDTH` (30 in `uifdma_axi_ddr`, but the top wire is 29) | byte address of the first beat of this transfer; latched into `axi_awaddr`/`axi_araddr` on `fdma_wstart`/`fdma_rstart` |
| len | `I_fdma_wsize` / `I_fdma_rsize` | 16 bit | number of **AXI beats (256-bit words)** in the whole transfer. `fdma_wleft_cnt <= I_fdma_wsize`, decremented per `w_next` |
| cmd | `I_fdma_wareq` / `I_fdma_rareq` | 1 bit | request; `fdma_wstart = ~fdma_wstart_locked & I_fdma_wareq` → the engine self-latches, so a level is enough |
| busy | `O_fdma_wbusy` / `O_fdma_rbusy` | 1 | `= fdma_wstart_locked`, held for the whole transfer |
| data | `I_fdma_wdata` / `O_fdma_rdata` | `M_AXI_DATA_WIDTH` (256) | |
| beat valid | `O_fdma_wvalid` / `O_fdma_rvalid` | 1 | `= AXI W/R handshake` (`M_AXI_WVALID & M_AXI_WREADY`, `M_AXI_RVALID & M_AXI_RREADY`) |
| end | internal `fdma_wend`/`fdma_rend` | | last-beat detection (`fdma_wleft_cnt == 1`) |

**Compile-time configuration (parameters, not registers):** `M_AXI_B2B_SET`, `M_AXI_ID_WIDTH`, `M_AXI_ID`, `M_AXI_ADDR_WIDTH`, `M_AXI_DATA_WIDTH`, `M_AXI_MAX_BURST_LEN`.

**Frame/2-D geometry "registers"** live one level up in `uidbuf` and are also **parameters**, not registers: `W_XSIZE`, `W_XSTRIDE`, `W_YSIZE`, `W_XDIV`, `W_BUFSIZE`, `W_BASEADDR`, `W_DSIZEBITS` (and `R_*`).

### 2.3 The DDR IP instantiation is a stub

`uifdma_axi_ddr.v` lines 327–374:

```verilog
    ddr_ip  u_ddr_phy
    (
        .ref_clk        (),
        .sys_rst_n      (),
        .apb_pclk       (),   ... every port is "()" ...
        .paxi_awaddr    (),
        ...
        .ddr_dq         (),
        .ddr_dqs_p      (),
        .ddr_dqs_n      (),
        .ddr_dm         ()
    );
```

Every port of `ddr_ip` is unconnected — including `paxi_awaddr/wdata/wvalid/wlast`, `paxi_araddr/rready`, `paxi_awready/wready/arready/rdata/rvalid/rlast` and all DDR pins. `axi_*` internal wires therefore feed nothing, and the DDR PHY pads are unreachable from the top. This is the direct cause of the `SYN-8511` pad error and of the `HDL-5007 WARNING: input port 'ref_clk' remains unconnected for this instance in ../../../src/uifdma/uifdma_axi_ddr.v(327)`.

The DDR IP is otherwise real and configured as: `PH1P_DDR_TYPE = Integrated`, `PH1P_REF_CLK = 50 MHz`, `PH1P_DDR_SPEED = 800 Mbps` (DDR2-800), `PH1P_COMP_TYPE = x16`, `PH1P_COMP_DENSITY = 512` (512M×16 = 1 GB), single PLL, `PH1P_AXI_ADDR_MAP = ROW_COL_BANK`, `PH1P_DQ_BYTE = 2`; pins come from `td\al_ip\ddr_ip\src\adc\ddr_ip.adc` (not from `pin\pin.adc`).

### 2.4 Burst length

* `M_AXI_MAX_BURST_LEN = 16`, set both in `system_top.v` (`uifdma_axi_ddr#(.M_AXI_MAX_BURST_LEN(16))`, line 82) and in `uifdma_axi_ddr.v` (passed to `uiFDMA`).
* `localparam [3:0] MAX_BURST_LEN_SIZE = clogb2(16) - 1 = 4`.
* `assign M_AXI_AWLEN = wburst_len - 1;` where `wburst_len` is chosen each burst:
  `if (fdma_wleft_cnt[15:4] > 0) wburst_len <= 16; else wburst_len <= fdma_wleft_cnt[3:0];`
* Therefore the AXI burst length is `min(16, remaining)` beats, i.e. **≤ 16 beats = ≤ 512 bytes per AXI burst** on a 256-bit bus. The header comment justifies this: *"AXI总线的burst 大小，对于AXI4，支持任意长度，对于AXI3以下最大16"* (16 for AXI3 compatibility). Long transfers are split automatically, and `axi_waddr` increments by `axi_wburst_size = wburst_len * 32` after each `axi_wlast`.
* Read side is symmetric (`rburst_len`, `axi_rburst_size`), driven by a separate left-counter pair (`fdma_rleft_cnt` for the AR path, `fdma_rleft_cnt_d` for the R path).

### 2.5 Outstanding capability

* **Writes: 1 outstanding burst.** `axi_wvalid` is asserted once per burst and cleared on `axi_wlast`; `M_AXI_BREADY = 1'b1` so write responses are accepted immediately, but there is no second AW issued while a burst is in flight.
* **Reads: 1 outstanding AR (`M_AXI_B2B_SET = 1`).** `uifdma_axi_ddr.v` line 379 sets `.M_AXI_B2B_SET(1)`, selecting the `else if (M_AXI_B2B_SET == 1)` branch, i.e. *"只进行单次burst"* — strictly one AR burst at a time, no back-to-back AR ("读通道增加背靠背burst机制" from the v3.3 changelog is **disabled** here). The parameter's default is 2 (2 back-to-back bursts) but it is overridden.
* Since `AWID`/`ARID` are tied to 0 there is no ID-based reordering; the DDR MC sees a single ID stream.
* `M_AXI_RREADY = axi_rready && I_fdma_rready` with `axi_rready = 1'b1` and `I_fdma_rready` tied to `1'b1` at both instantiation levels → R is never back-pressured.

### 2.6 1-D vs 2-D (stride / line) support

* **`uiFDMA` itself is 1-D only.** It has exactly one address register per direction and no stride/line-length inputs. After each AXI burst it does `axi_awaddr <= axi_awaddr + axi_wburst_size`, i.e. a purely contiguous run of `I_fdma_wsize` beats.
* **2-D / stride transfers are provided by `uidbuf`, not by `uiFDMA`.** `uidbuf` receives `W_XSIZE`/`W_XSTRIDE`/`W_YSIZE`/`W_XDIV` and issues **one FDMA transfer per line**, computing:
  * `FDMA_WX_BURST = (W_XSIZE*W_DATAWIDTH/AXI_DATA_WIDTH)/W_XDIV` → `O_fdma_wsize`
  * `WX_BURST_ADDR_INC = (W_XSIZE*(W_DATAWIDTH/8))/W_XDIV`
  * `WX_LAST_ADDR_INC = (W_XSTRIDE - W_XSIZE)*(W_DATAWIDTH/8) + WX_BURST_ADDR_INC`
  * state machine `S_IDLE→S_RST→S_DATA1→S_DATA2` loops `WY_BURST_TIMES = W_YSIZE*W_XDIV` times, applying `WX_BURST_ADDR_INC` for the first `W_XDIV-1` sub-bursts and `WX_LAST_ADDR_INC` for the last one of each line (`uidbuf.v` lines 242–249).
  * Read side mirrors this (`RX_BURST_ADDR_INC`, `RX_LAST_ADDR_INC`, lines 407–414).
* With the actual `system_top` numbers: `FDMA_WX_BURST = (480*32/256)/1 = 60` beats (60×32 B = **1920 bytes = 480×32-bit words = 1920 RAW8 pixels/line**), `WX_BURST_ADDR_INC = 1920`, `WX_LAST_ADDR_INC = (480−480)*4 + 1920 = 1920`, `WY_BURST_TIMES = 1080`. So write and read each perform **1080 FDMA transfers of 60 beats = 2 073 600 bytes = one 1920×1080 RAW8 frame**, per frame.

## 3. `src\uifdmadbuf\uidbuf.v` + `fs_cap.v`

### 3.1 `fs_cap.v` (73 lines) — VS/FS edge detect with CDC synchroniser

* Parameters: `VIDEO_ENABLE = 1`.
* Ports: `I_clk, I_rstn, I_vs, O_fs_cap`.
* Structure: a 4-deep synchroniser chain `vs_i_r1..vs_i_r4` marked `(* ASYNC_REG = "TRUE" *)`. With `VIDEO_ENABLE == 1`, `O_fs_cap = (vs_i_r4,vs_i_r3) == 2'b01`, i.e. a **1-clock-wide rising-edge pulse in `I_clk`'s domain**. With `VIDEO_ENABLE == 0` it is a plain level pass-through of `vs_i_r4`.
* Purpose: brings the video frame-sync (write VS from `S_hs_rx_clk`, read VS from the 75 MHz pixel clock) into the `I_ui_clk` (DDR/AXI) domain where `uidbuf`'s state machines run.
* Latency: 5 `I_ui_clk` cycles from `I_vs` to `O_fs_cap`.
* There are two instances, `fs_cap_W0` and `fs_cap_R0`, both clocked by `I_ui_clk`.

### 3.2 `uidbuf.v` (499 lines) — DDR frame-buffer controller, **not** a line buffer

**Buffer structure: 3-deep frame buffer in off-chip DDR, plus two small asynchronous burst-elasticity FIFOs (one per direction). There is no on-chip frame buffer and no line buffer in `uidbuf`.**

*Derived:*
* `WYBUF_SIZE = W_BUFSIZE - 1 = 2`; `O_W_sync_cnt` counts `0,1,2,0,…` → **3 frame slots** (`R` identical: `O_R_sync_cnt` 0..2).
* Frame base address: `O_fdma_waddr = W_BASEADDR + {O_fmda_wbufn, W_addr}` (line 155) — an 8-bit buffer number concatenated above a 25-bit in-frame offset, truncated to the 29-bit FDMA address. **Consequence: consecutive frame slots are 2^25 = 33 554 432 bytes (32 MiB) apart** even though a frame only needs 2 073 600 bytes. Same for the read side (`O_fdma_raddr`, line 320).
* Interrupts: `O_fdma_wirq` / `O_fdma_rirq` are **60 `I_ui_clk`-cycle pulses** raised on the `S_DATA2→S_IDLE` transition (`wirq_dly_cnt <= 60`), together with the buffer number `O_fmda_wbuf` / `O_fmda_rbuf`.
* FIFO instances:
  * `u_wfifo` = `wfifo#(DATA_WIDTH_W=32, DATA_WIDTH_R=256, ADDR_WIDTH_W=clog2(1024)=11, ADDR_WIDTH_R=clog2(1024*32/256)=8, AL_FULL_NUM=1022, AL_EMPTY_NUM=2, SHOW_AHEAD_EN=1, OUTREG_EN="NOREG")` → **32-bit write port × 256-bit read port, asynchronous, ERAM-based, 2^11 = 2048 × 32-bit = 8 KiB**. (Note: the parameter comment says "写通道AXI设置FIFO缓存大小" 1024, but because `ADDR_WIDTH_W = clog2(1024) = 11`, the implemented depth is 2048 words — a factor-2 conservatism/off-by-one.)
  * `u_rfifo` = `rfifo#(DATA_WIDTH_W=256, DATA_WIDTH_R=32, ADDR_WIDTH_W=clog2(128)=8, ADDR_WIDTH_R=clog2(1024)=11, AL_FULL_NUM=126, AL_EMPTY_NUM=2, SHOW_AHEAD_EN=1, OUTREG_EN="NOREG")` → **256-bit write × 32-bit read, 2^8 = 256 × 256-bit = 8 KiB**.
  * Both IP parameter files agree: `td\al_ip\wfifo\wfifo\.params_wfifo.txt` (`DATA_WIDTH_W 32 / DATA_WIDTH_R 256`, `AL_FULL_NUM 2045`, `SYNC? no — ASYNC 1`), `td\al_ip\rfifo\.params_rfifo.txt` (`DATA_WIDTH_W 256 / DATA_WIDTH_R 32`). The `src\uifdmadbuf\{w,r}fifo\*.v` copies override the `al_ip` copies (`HDL-7201 CRITICAL-WARNING: overwrite current module 'wfifo' in ../../../src/uifdmadbuf/wfifo/wfifo.v(26)`).
* Flow control / burst trigger: `W_REQ <= (W_rcnt > FDMA_WX_BURST - 1)` → a write FDMA of 60 beats is requested as soon as ≥ 60 32-bit words (240 bytes) are queued; `R_REQ <= (R_wcnt < FDMA_RX_BURST - 1)` → a read FDMA is requested when the read FIFO has room for a 60-beat burst. FIFOs are synchronously reset for ~40 `I_ui_clk` cycles at each frame start (`wrst_cnt < 40`), and the state machine waits for the IRQ to clear (`wrst_cnt < 100`).
* Read/write arbitration: a 4-state round-robin (`WR_S`) that gives the **write channel priority** (line 468 comment `//优先执行写`) when both `I_fdma_wbusy==0 && W_REQ && W_MS==S_DATA1` and the read is also requesting.
* Frame pacing: `uisetvbuf#(.BUF_DELAY(2), .BUF_LENTH(3))` computes `O_bufn = (I_bufn < 2) ? (3 - 2 + I_bufn) : (I_bufn - 2)`, i.e. **the read frame number = write frame number delayed by 2**, giving triple buffering with a **2-frame capture→display latency** (comment in `system_top` line 255: `//设置3帧缓存，读延迟写1帧` — the comment says 1, the code does 2).

**Answer to "frame buffer / line buffer / FIFO, depth × width, how many frames deep":** off-chip frame buffer, **3 frames deep** (1920×1080×8-bit per frame, 32 MiB address slots, read 2 frames behind write), front-ended by two asynchronous ERAM FIFOs (8 KiB each direction) that carry one 60-beat/1920-byte line burst at a time. On-chip **line** buffering exists only later in the pipeline, inside `raw8_2_rgb888` (§4).

### 4.1 `bound_cut.v` — what it actually computes

**It is neither a bounding box nor a crop. It is a border blanking / border mask** (module header: *"边界切除，变为黑色，在RAW转RGB过程中，边界的颜色难以计算，所以切除，显示黑色"* — "cut the border, turn it black; border colours are hard to compute during RAW→RGB, so cut it and show black").

Exact behaviour (`bound_cut.v` lines 58–78):

```verilog
reg [CNT_BITS-1:0] rc_w = 0, rc_h = 0;
wire w_skip = (rc_w < SKIP_COLS) || (rc_w >= H_SIZE - SKIP_COLS) ||
              (rc_h < SKIP_ROWS) || (rc_h >= V_SIZE - SKIP_ROWS);
rc_h <= (r_de == 2'b10) ? rc_h + 1 : (r_vs == 2'b01) ? 0 : rc_h;   // count lines on DE falling edge
rc_w <= I_awb_de ? rc_w + 1 : 0;                                    // count pixels on DE
O_awb_vs/hs/de <= I_awb_vs/hs/de;                                   // plain 1-clk delay, timing unchanged
O_awb_data <= w_skip ? {DATA_WIDTH{1'b0}} : I_awb_data;             // force black
```

* What it computes: a per-pixel boolean `w_skip` that is true for the outermost `SKIP_COLS = 2` pixels on the left and right and the outermost `SKIP_ROWS = 2` lines at the top and bottom of a `H_SIZE × V_SIZE = 1920 × 1080` raster.
* **Coordinates:** `rc_w` = pixel column counter, reset whenever `I_awb_de` is low, incremented per `I_awb_de` pixel. `rc_h` = line counter, incremented on the **falling edge of `I_awb_de`** (`r_de == 2'b10`) and cleared on the **rising edge of `I_awb_vs`** (`r_vs == 2'b01`). Both are counts relative to the start of the active raster, i.e. **units = pixels (columns) and lines (rows)**; they are internal only.
* **Outputs:** only the *masked data* plus a 1-clock-delayed copy of `vs/hs/de`. **No coordinates, no offsets, no bbox, no width/height are output.** There is no cropping: line/field timing is bit-identical in and out, only the pixel values in the border region are forced to `24'h000000` (black).
* **Rate:** 1 pixel per `I_clk` (it is a purely per-pixel pipeline on the 75 MHz pixel clock), 1 clock latency.
* **Important wiring defect in this project:** `system_top` declares `wire [23:0] w_crop_data;` (line 354) and **comments out** the connection `.O_awb_data(w_crop_data)` (line 366), while still driving `hdmi_tx.I_video_in_data` from `w_crop_data` (line 486). `bound_cut`'s data output is therefore dangling and the HDMI data input is undriven. (An older revision of `system_top.v` even declared `w_crop_data` twice — `HDL-5007 WARNING: data object 'w_crop_data' is already declared in ../src/system_top.v(141)` in `td\td_2025-06-14_21-57-23.log`.)

### 4.2 `Line_Shift_RAM_8Bit.v` and `shift_reg_bram.v` — interface, taps, genericity

**Neither is a generic window generator.** They are single-channel, single-line delay memories; the 3×3 window is built explicitly in `raw8_2_rgb888.v`.

`Line_Shift_RAM_8Bit` interface (`Line_Shift_RAM_8Bit.v` lines 2–14):

| Port | Dir | Width | Meaning |
|---|---|---|---|
| `clk` | in | 1 | single clock |
| `rst_n` | in | 1 | async, active low; resets the write pointer to `INIT_ADDR = DATA_DEPTH - DELAY_NUM` and the read pointer to 0 |
| `clken` | in | 1 | clock enable; **both** pointers advance only while high |
| `din` | in | `DATA_WIDTH` | |
| `dout` | out | `DATA_WIDTH` | |

* **Lines/taps: exactly one line of delay per instance** (depth `DATA_DEPTH` samples = `H_SIZE` pixels for a full line), with a sub-line phase trim of `DELAY_NUM` samples (`DELAY_NUM` makes the read pointer lead the write pointer by `DELAY_NUM`). It is *not* a multi-tap window generator: there is only one read address, and `dout` is a single sample.
* Parameterisation is generic in `DATA_WIDTH`, `ADDR_WIDTH`, `DATA_DEPTH`, `DELAY_NUM`, so it can be chained to build a window: `raw8_2_rgb888` chains two of them (`DELAY_NUM=0` then `1`) and then relies on explicit `reg` shift registers (`raw_v_*_d0/d1/d2`) for the horizontal taps. So **the window generator is `raw8_2_rgb888` (a fixed 3×3 Bayer demosaic), not `Line_Shift_RAM_8Bit`**.
* `shift_reg_bram` is a thin Anlogic IP-Generator wrapper around one `EG_LOGIC_BRAM` in `PDPW` mode (port A = write with `wea=1` and a fixed `dib={8{1'b0}}`, port B = read), `REGMODE_A/B = "NOREG"`, `WRITEMODE_A/B = "READBEFOREWRITE"`, 8-bit × 1280 default. It is a **generic dual-port RAM primitive (write A / read B), not a shifter and not a window generator** — the "shift_reg" name is aspirational. It is unused: the instantiation inside `Line_Shift_RAM_8Bit.v` is commented out, and `shift_reg_bram.v` is **not listed in `td\test.al`**, so it is not compiled.

### 4.3 Which `awb` is actually built (proven duplicate-module override)

`td\test.al` compile order: `awb.v` = 27, `Line_Shift_RAM_8Bit.v` = 29, **`awb2.v` = 30**, `div_u42_u30.v` = 31.

* `hdmi_tx` supports two mutually exclusive inputs, selected by `I_video_rgb_enable`:

## 9. Architecture comparison: `32_cs500_mipi_hdmi` vs `lab_ex3_osd_SC500_720P\...\hdl_source\`

### 9.1 Direct answer

**Yes — but with a nuance.** `32_cs500` uses a **generic AXI FDMA + on-chip DDR controller** path (`uidbuf` + `uiFDMA` + `uifdma_axi_ddr` + `ddr_ip`), whereas `lab_ex3` uses **hand-written `video_in.v` / `video_out.v` frame-buffer clients driven through `mc_to_user_interface.v` onto the DDR hard-controller's native `app_*`/`wdf_*` user interface** (`ph1p35_324_ddr_wrapper` → `ddr2`). Neither project uses a hand-written *bulk* FIFO instead of DDR — **both really do use the on-chip DDR as the frame buffer**, and both use 4-ish frame slots and 128-bit DDR beats. The difference is the *bus/abstraction layer*:

* `lab_ex3`: pixel-domain FIFO → explicit 240-beat burst writer → `w155_d512_fifo` command queue → **native MC command interface** (`app_en/app_addr[24:0]/app_cmd/app_wdf_wren/app_wdf_end/app_wdf_mask`), hand-rolled address arithmetic (base addresses `0, 7 000 000, 14 000 000, 21 000 000`, `addr += 8` per 128-bit beat), 4 frame slots with a `wp`/`rp` pointer scheme and a *3-behind* read pointer, plus MIPI-error-driven frame-slot rewind.
* `32_cs500`: pixel-domain FIFO inside `uidbuf` → **`uiFDMA` AXI4 master** (256-bit, ≤16-beat bursts) → `uifdma_axi_ddr` → `ddr_ip`. Address arithmetic is driven by compile-time `X/YSIZE/XSTRIDE` parameters with `{bufnum, offset}` concatenation; no `app_*` signals; no MIPI-error handling; 3 frame slots, read 2 behind (well, 1 behind for `lab_ex3`? lab_ex3 uses `wp+1 → rp = wp-1+4 mod 4`, i.e. 3-behind slot mapping with 4 slots).

| Aspect | `32_cs500_mipi_hdmi` | `lab_ex3_osd_SC500_720P` |

| Frame-buffer client | `uidbuf` (parameterised 2-D/stride engine, 3 frames, 60-beat bursts, `{bufnum,offset}` addressing) | `video_in` + `video_out` (hand-written 240-beat writers/readers, 4 slots at `0 / 7 M / 14 M / 21 M`, `addr += 8` per 128-bit beat) |

| DDR data width | 256-bit AXI beats, ≤16-beat bursts (`M_AXI_MAX_BURST_LEN=16`), 1 outstanding read/write | 128-bit `app_wdf_data`, explicit 240-beat bursts, `I_ddr_user_ready`-throttled |
| DDR device | DDR2-800, x16, 512M, 2 DQ bytes, 1 GB; **`ddr_ip` instance fully unconnected → build fails** | DDR2-800 via `ddr2` + full `ph1p_ddrphy` tree (fully connected, builds) |
| Frame count / latency | 3 slots (`W/R_BUFSIZE=3`), read = write − 2 (`uisetvbuf BUF_DELAY=2`) | 4 slots, `wp`/`rp` mapping (`rp = wp+2 mod 4`), plus MIPI-error rewind of the write pointer |
| ISP | **minimal**: `raw10_unpacket_2lane` (RAW10→RAW8) → `raw8_2_rgb888` (2× `Line_Shift_RAM_8Bit` + 3×3 Bayer demosaic) → `awb` (per-frame 4.12 gains) → `bound_cut` (border black). No BLC, no full demosaic, no colour correction, no OSD. | **full**: `csi_unpacket_2lane` → `raw10_unpacket_2lane` → `uial2axis` → `isp_top` (BLC → `demosaic`/`bilinear_interpolation` with 2× `blk_mem_gen_*` BRAMs + `raw_matrix_3x3_buffer` → AWB with `divider` → `data96_128`/`data128_96` width conversion) → `video_in` |
| Display path | `uivtc` (1920×1080) → `hdmi_tx` → `hdmi_phy_wrapper` → 4× `lane_lvds_10_1` TMDS. **No mixer, no OSD.** `hdmi_tx` internally runs `video_source_test` (active) and the core has `VIDEO_TPG="Enable"`, `HACTIVE=1280/VACTIVE=720`, `VIDEO_VIC=69` | `uivtc` → `hdmi_mixer` (alpha-blends `anlogic_logo_rom` + `osd_char_lib` OSD onto the video) → `hdmi_tx` (1320? no: same 1650/750 720p geometry) → `hdmi_phy_wrapper`. `video_source_test` instantiation **commented out**, `VIDEO_TPG="Disable"`, `VIDEO_VIC=4` |
| Output video interface | HDMI 1.4b (TMDS), 720p-parameterised core fed by a 1080p-timed pipe at 75 MHz | HDMI 1.4b (TMDS) **and** a DSI path (`dsi_tx_packet\config_data.mif`) — the run names are `camera_to_dsi_display` |
| MIPI error handling | none (no `mipi_rx_error_detect` equivalent) | `mipi_rx_error_detect` → frame-slot rewind in `video_in` |
| Camera config | `uicfgcs500` + `uics500reg` (1080p register table), `SC500GainTbl`, `ae_set` | `uicfgcs500_720p` + `uics500reg_720p60` + `uics500regAE`, `SC500GainTbl`, `ae_set` |
| Report artefacts | none (build fails; only `test_phy.ts`, `test.bit`, `test_inst.bid`) | full `*_rtl.area`, `*_gate.area`, `final_timing.rpt`, `place.qor`, `route.qor`, `run.log` |

### 9.4 Conclusion for §9

`32_cs500` is a **Milianke uiFDMA/uidbuf-based DDR framebuffer design**: AXI4 DMA engine, parameterised 2-D/stride buffering, minimal ISP, no OSD, 1080p timing feeding a 720p-parameterised HDMI 1.4b core with its internal TPG enabled — and, as committed, **not buildable** (unconnected `ddr_ip` + missing DDR top-level ports/pins + no effective SDC). `lab_ex3` is an **Anlogic native-MC-interface design with a hand-written `video_in`/`video_out` frame-buffer pair and a full ISP + OSD**, and it does build and has complete QoR/timing reports.
