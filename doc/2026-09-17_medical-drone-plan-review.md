## 一、文件内容总结

两份文件是同一份**竞赛+项目融合方案书**，共 8 章，核心主张是：把"飞援鼓岭"医用无人机山地救援项目与安路赛题二（PH1P35 实时数字图像处理）合并，做一台**医疗模式 / 山地模式双模切换的机载视觉协处理器**。

| 章节 | 主张 |
|---|---|
| 01 融合背景 | 无人机避障用 Python+OpenCV 延迟功耗不达标 → 用 FPGA 做视觉协处理器 |
| 02 双模式架构 | 共享前端（MIPI→灰度/行缓冲→CDC）+ 模式 MUX + 医疗/山地两套算法引擎 + OSD/HDMI；RISC-V MCU 做模式切换、I2C 3A、MAVLink |
| 03 医疗模式 | 伤员搜索（HSV 色标 + 帧差运动 + 形态学 + 投影统计）、生命体征 OSD、红外 CLAHE 增强、物资投放引导 |
| 04 山地模式 | Sobel 避障 + 区域分级、HSV 地形分类（草/岩/水/林/路）、帧差运动检测、灾情航拍信息叠加 |
| 05 共享模块 | 声称共享基础模块本身即可覆盖基础要求 1/2/4 + 4 项进阶要求 |
| 06 可行性 | 估总 LUT 14,200–17,700（占 38,189 的 31%–46%）、ERAM ~720Kb，结论"资源完全可行" |
| 07 路线图 | 7 阶段，竞赛做 1–4 阶段、项目做 5–7 阶段 |
| 08 对照表 | 自评"基础 4/4 + 扩展 5/5 + 进阶 5/5 全覆盖，具备冲击满分的厚度" |

**方案的真正亮点**：① "共享前端 + 算法 MUX"的架构方向正确（行缓冲只建一次）；② 在垂直消隐期切换以避免撕裂；③ 15 条外部参考文献，方向选择有调研依据；④ "一次开发、双重产出"的竞赛/项目协同思路合理。

## 四、方案与现实的主要差距（按严重度排序）

### 1. 双摄 / 红外路线基本不可行（严重）
板上只有一个 MIPI FPC40 输入，芯片的 2 个 MIPI 实为 1 个 RX + 1 个 TX 硬核（顶层只例化 RX，HDMI 走 TMDS 不走 MIPI TX）。加上"摄像头只能用 SC500/SC520CS"的明文限制、第三方红外模组不在允许清单内，**方案 医疗-3（红外 CLAHE）、山地-2 的部分假设、扩展要求 1 的落地路径全部悬空**。扩展要求 1（风格化/视觉增强）需要换一条不依赖红外的实现路径。

### 2. DDR2 带宽估算过于乐观（严重）
方案称"720p@60 双帧乒乓约 300MB/s，占用率 19%"。实际应算三份流量：写 1 帧 + 显示读 1 帧 + 帧差读 1 帧 ≈ **1.49Gbit/s × 3 ≈ 4.5Gbit/s**。DDR2 x16@800Mbps 理论 12.8Gbit/s，但软核控制器（`ph1p35_324_ddr_wrapper`，usr_clk 66.667MHz）实际效率通常只有 50% 上下，且要伺候显示刷新不能被饿死（`video_in.v` 注释里已记录过"1080p 连续流把 wr_busy 拉死导致显示饿死"的踩坑）。**帧差法的可行性需要在真实平台上实测，不能按理论值拍板。**

### 3. 资源估算没有把官方基线算进去（严重）
官方 **lab3（含 OSD，已覆盖基础要求 1/2/4）已用 70.00% slices**，lab2（含 Sobel）60.93%。方案"共享 6,700 + 山地 7,500 ≈ 14,200 LUT"是在**空工程**上做的加法。真实起点是 70%，只剩约 6,300 slices（30%）要装下 Sobel + HSV 转换 + 帧差 + 投影统计 + 连通域 + 双模式 MUX 的全部算法。方案的"46% 裕量充足"结论不成立。

### 3b. 时序比面积更紧，且目标组合从未被构建过（严重）
- **没有任何一个例程同时含 Sobel 和 OSD。** lab2 与 lab3 是并列分支、不是叠加关系（lab3 的 ISP 链路明确"不含边缘检测"），而目标设计两者都要。
- 更麻烦的是它们吃紧的是**不同**的域：lab2 的最差路径在 `MIPI_RX_BYTE_CLK` 域（`u_awb/mult5` → `u_edge_detect_96`，裕量 1.451ns），lab3 的最差路径在 `HDMI_PIXEL_CLK` 域（`u_hdmi_mixer` 内，裕量 0.103ns）。**合并后两个域会同时恶化，且都已接近 0。**
- lab3 全局最差路径已定位：`hdmi_mixer.v:619` 的 `S_logo_addr = S_logo_y * LOGO_W + S_logo_x`——**乘法器→加法器→Logo ROM 读→输出寄存器全在同一个组合云、单周期完成于 75MHz 域**，12.858ns / 13.333ns 预算，其中布线占 57%。同文件 651-654 行还有 `* 10'd16` 与 `/ 10'd24` 等常量除法器，属同一类问题。
- **关键矛盾**：方案要新增的算法（HSV 转换、投影统计、连通域、双模式 MUX）恰恰都是这种"大组合云"形态。**照方案写法直接加，几乎必然破时序。**

### 3c. 好消息：可用的空闲资源很充裕（重要）
| 资源 | lab3 占用 | 空闲 | 用途 |
|---|---|---|---|
| slice reg（FF） | 31.53% | **68%** | 流水线打拍几乎免费 |
| ERAM | 37.04%（40/108） | **68 块** | 行缓冲、字模、文本缓冲、直方图 |
| DSP | 22.50%（9/40） | **31 个** | 乘法交 DSP，别用逻辑搭 |
| PLL | 50.00%（3/6） | **3 个** | 新增时钟域可行 |
| IO | 36.25%（58/160） | 102 个 | 外设扩展有余量 |

证据：**OSD 模块加了 2,494 slices 但只加了 67 个 FF**——说明它几乎纯组合逻辑，这正是它吃掉 4.57ns 裕量的根因。**把它流水线化几乎不花面积，却能收回绝大部分裕量。** 所以这是"先修时序、再加功能"，而不是"没空间了、砍功能"。

### 4. OSD 部分被低估且描述失实（中等）
- 官方实现是**色键**不是 Alpha 混合，方案反复写"Alpha 混合 0~255 半透明"与实际不符。
- 官方字模硬编码在 `function` 里，**无法显示动态数值**。方案要做"心率数值 + 脉搏波形 + 坐标 + 延迟 ms"，必须自建：可写文本缓冲 RAM + 字模 ROM + UART/MCU 写通道 + 波形循环缓冲。估"500 LUT + 40Kb"明显不足，实际按 1,000–1,500 LUT + 20–40 个 ERAM 块预留更稳。

### 5. "共享前端"这条正确思路没有被贯彻到底（中等）
方案说共享前端，但资源表里"灰度化+去噪"、"行缓冲"仍按模块单独估算。真正的做法是**一套行缓冲 + 窗口输出引擎服务全部算法**（灰度/边缘/卡通/颜色统计共用 3×3 或 5×5 窗口），用 MUX 选算法。这一项如果做对，能省下的资源比方案估的更多。

### 6. 让 MCU 承担核心决策有评分风险（中等）
Q&A 明确：赛题二只有在**扩展要求三**（控制小车/机械臂等复杂外设）时才允许额外处理器，且"赛题指标要求部分需要在 FPGA 上实现"。方案把模式切换、3A 算法、MAVLink 都放在 MCU，等于把相当一部分"系统能力"外包出去了。建议把这些下沉到 FPGA 状态机，MCU 只做数据桥（收数据 → 写 OSD 缓冲）。

### 7. 时间线描述与实际竞赛节奏脱节（中等）
方案写"FPGA 竞赛通常在 2026 下半年启动""飞援鼓岭项目 2027.01–2028.03"，并建议"竞赛做 1–4 阶段"。而 2026 Q&A 日期为 2026-09-10、**报名 9.22 截止、随后发板**——竞赛现在就在进行中，今天是 9/17。方案把竞赛当成未来事项，路线图的阶段划分需要按"现在已有板/有例程"重排。

### 8. 把外部引用数据当成本平台结论（中等）
方案第 06 章的"FPGA 3.1ms vs Python 6.3ms""延迟 1–5ms""功耗 1–3W"全部引自 arXiv/CSDN/GitHub 的第三方数据，不是 PH1P35 实测。竞赛评测看现场演示，**这些数字不能作为自评依据**，更支撑不起"冲击满分"的结论。

### 9. 切换无撕裂只做了一半（细节但易踩）
方案说在 VBLANK 内切换。但只切 MUX 不够——**算法内部的行缓冲/窗口寄存器里残留的是上一模式的像素**，切换后前几行会产生伪边缘/假色块。正确做法：算法选择做成 shadow 寄存器、在 vsync 沿更新，并同时复位/冲掉各算法引擎的行缓冲有效标志。

### 10. 口径与自评不严谨（细节）
- 分辨率在 1024×600 与 720p 之间来回切换，未统一。
- "自评 4/4 + 5/5 + 5/5、冲击满分"无依据；其中扩展要求 1 的落地路径已因红外路线失效。
- "红外模组需额外 MIPI 接口"的自我提醒方向是对的，但结论没有据此调整方案。

## 五、思路与建议

### 5.1 策略：把"双模式"收敛为"单链路 + 参数集切换"

竞赛要求基础 3/4、扩展 1/5，且必须整合为一个可固化镜像。双套完整算法引擎的资源与调试风险不值得。建议：

- **保留**"同一个共享前端 + 可切换算法通路"的架构（这是方案的精华，也直接对应"多算法切换"进阶项）。
- **降级**："医疗模式/山地模式"从"两套引擎"变为"两组算法参数集与显示主题"——例如同一套 Sobel/颜色统计引擎，切换的是阈值、色彩映射、OSD 文案。这样切换逻辑小、演示说辞仍然完整。
- **场景叙述**保留"山地救援"单场景即可，医疗/生命体征可作为 OSD 演示元素（不需要真实医疗器械）。

### 5.2 高性价比创新点排序（按实现成本 ÷ 演示效果）

1. **延迟可视化（强烈推荐，几乎是白捡的分数）**
   FPGA 内打时间戳：在 MIPI 帧起始写一个 ms 计数器快照，在 HDMI 输出该帧时相减，OSD 显示"端到端 N ms"。PPT 明确列为进阶要求 3，且是 FPGA 相对 Python 最有说服力的证据，成本 < 300 LUT。
2. **多算法实时切换 + 状态 OSD**
   按键切：原图 → 灰度 → Sobel 边缘 → 二值化 → 卡通化，OSD 同步显示算法名 + 分辨率 + 帧率。例程已给框架，成本主要在 OSD 动态文本（见 5.3）。
3. **卡通化（替代红外，拿下扩展要求 1 的正路）**
   3×3 Sobel 得到边缘图 → 5×5 邻域彩色均值做区域填充 → 边缘叠加。比红外 CLAHE 便宜、不依赖额外硬件、视觉效果直观，正好命中"边缘提取与区域填充（卡通化）"这一官方原话。
4. **目标检测 + 外设联动（扩展要求 2 + 3 一起拿）**
   颜色阈值（橙/红/蓝）+ 行列投影求包围框（**不必做完整连通域标记，投影统计性价比高得多**）→ OSD 画框 + 坐标文字 → 用检测结果驱动板载 LED/数码管/蜂鸣器，或用 DC3 扩展口驱动小舵机。外设联动优先用板载资源，避免引入额外处理器带来的合规争议。
5. **硬件运动检测（帧差法，视带宽实测结果决定）**
   若实测 DDR 带宽够，做半分辨率子采样帧差（每 2×2 取 1 像素，读带宽降到 1/4）+ 形态学去噪 + 运动区域框 + 计数。这是最能体现"纯硬件并行"的展示点，但**必须先做带宽实测再立项**。

### 5.3 关键模块的具体实现要点

**OSD 子系统（重点改造对象）**
```
字模 ROM（eram，ram_style="block"）  ← 把 hdmi_mixer 里的 function 字模搬到数组
文本缓冲 RAM（64×32 字符）            ← MCU/UART 或按键可写
渲染器：行/列计数 → 字符索引 + 局部坐标 → 字模位 → 像素
```
- 复用官方 `hdmi_mixer.v` 里"局部坐标 → scale → col/row → 取位"的结构，但把 `S_pf_scale_x / 10'd24` 这类**常量除法改成移位或预计算 LUT**（多个除法器堆在组合逻辑里是时序隐患）。
- 若要真正的半透明，加一级 `out = osd*α + video*(1-α)`，用移位近似（α 取 1/4、1/2、3/4）即可，不必真乘法。

**行缓冲与窗口引擎（共享核心）**
- 一套 3 行（或 5 行）行缓冲 + 列延迟链，输出 3×3 / 5×5 窗口给所有算法。
- 官方 `edge_detect_96.v` 里"每拍 4 像素、用 pair 平均降到 2 样点/拍"的降采样技巧值得沿用，能显著省行缓冲。
- 挂在 ISP 像素时钟域（`MIPI_RX_BYTE_CLK`，60MHz），不要跨到 DDR 域。

**模式/参数切换（无撕裂的正确做法）**
- 算法选择寄存器 + shadow 副本，vsync 沿更新。
- 更新时同时置位各引擎的"行缓冲失效"标志，冲掉残留窗口数据。
- 切换期 OSD 显示"SWITCHING"状态，避免观众误判花屏。

**摄像头初始化与自检（稳定性得分点）**
- SC500CS 需要 24MHz 参考钟 + 复位 + I2C 寄存器序列（复用 `uics500_cfg`，可参考 `uics500reg_1080p30.v` 做 720p/1080p 双表）。
- 上电即演示的场景下必须加：初始化完成标志、失败重试、LED 指示、错误计数 OSD。
- 建议做一个"自检模式"（按键进入）：色条图 + 全链路 status 位 + 帧计数 + 延迟数字。现场排查一个按键就能定位是哪一级断了。

**AE / 自动曝光**
- 可在 FPGA 内做：帧内亮度均值统计 → 与目标区间比较 → 步进微调曝光寄存器，复用 `mc_to_user_interface.v` 的 I2C 写通道。**不必依赖 MCU**，规避 5.4 的评分风险。

### 5.4 资源与带宽的正确预算方法

**结论：真实约束是时序，不是面积。** 基线已经测好了（见第 3 节表格），不需要重跑。正确顺序是**先把时序修回来，再加功能**。

**第一步——修时序（性价比最高，几乎不花面积）**
1. `hdmi_mixer.v:619`：把 `S_logo_y * LOGO_W` 换成**逐行预计算的行基址寄存器**（每行 hsync 更新一次，逐像素只做 `行基址 + S_logo_x` 一次加法），消掉像素率路径上的乘法器；再把 Logo ROM 读与输出判决各打一拍。
2. `hdmi_mixer.v:651-654` 及同类：`* 10'd16` 用移位，`/ 10'd24`、`/10'd15`、`/10'd8` 改成**预计算 ROM 查表**（局部坐标只有 24 个取值），消掉常量除法器。
3. lab2 侧 `u_awb/mult5 → u_edge_detect_96` 长链：在 AWB 与边缘检测之间插一级寄存器。
4. 修完必须重新跑一次 P&R，确认 HDMI_PIXEL_CLK 与 DDR usr_clk 两个域都回到 1ns 以上再继续。

**第二步——新算法用空闲资源实现**
- 流水线用 FF（68% 空闲）、行缓冲放 ERAM（68 块空闲）、乘法交 DSP（31 个空闲）、需要新时钟域时用 PLL（3 个空闲）。
- **算法处理位置优先放 `MIPI_RX_BYTE_CLK` 域**：lab3 在该域 Fmax 达 113.6MHz（需求仅 60MHz）；但 lab2 证明 Sobel 会把它压到 65.7MHz，所以该域同样要流水线，不能堆组合逻辑。

**第三步——预算与警戒线**
- **带宽按三份流量实测**：写 1 帧 + 显示读 1 帧 + 帧差读 1 帧。用计数器统计 DDR 用户口实际占用周期再定帧差方案。
- **警戒线**：slices ≤ 85%；每个时钟域 setup 裕量 > 0.5ns。破线则降分辨率（720p → 1024×600）或降帧率（60 → 30）。
- 面积层面真正紧的是 slices（剩 30%）与 lut6（剩 40%），**ERAM/DSP/FF/PLL 都不紧**。
